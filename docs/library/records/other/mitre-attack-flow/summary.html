Overview

Attack Flow is a machine-readable language for how adversary actions combine into an attack, defined as an extension to STIX 2.1 so that flows interoperate with existing threat-intelligence tools. A flow document has exactly one attack-flow object (name, description, start_refs, and a scope label). Its building blocks, as defined in the JSON schema, are:

  • attack-action: one execution of a behavior (name is the only required action-specific property; the common properties are still required; usually technique_id and tactic_id, optional refs to the ATT&CK objects, execution_start / execution_end, a command, the assets it touches), linked to what follows through effect_refs;
  • attack-condition: a state or outcome after an action, with an optional (experimental) detection pattern of any type, branching with on_true_refs / on_false_refs;
  • attack-operator: AND (all incoming paths must succeed) or OR (any one is enough);
  • attack-asset: the subject or target of an action.

An arrow from one action to another is a dependency: "the second action cannot be executed until the first action completes successfully" (introduction.rst), which the documentation calls a more powerful concept than one action happening before another. An acyclic graph therefore gives a partial order; independent branches stay unordered, and timestamps are optional.

scope values in the schema: incident, campaign, threat-actor, malware, emulation-plan, attack-tree, other (attack-tree added in 2024 and emulation-plan in 2025 without a version change; language.rst still lists five). Attack trees are drawn with the same blocks: goals as actions without techniques, joined bottom-up through operators. Flows can be hypothetical (emulation plans, attack trees, "what-if" scenarios at the "Speculation" confidence level) as well as observed. Techniques usually come from ATT&CK, but Workbench collections, other knowledge bases (e.g. VERIS) and ad-hoc actions are allowed.

The tools (Attack Flow Builder, visualisations, a corpus of example flows) added ATLAS, D3FEND and Fight Fraud in v3.1 (April 2026), AI-assisted drafting from incident reports, technique recommendations and tags in v4.0, and D3FEND countermeasures and red-team tests in v4.1 (October 2026).

Limits

  • Review boundary: full FX-1 artifacts are available in distilled/. Automated extraction and checking do not constitute human acceptance; each artifact keeps reviewed_by blank until a person signs it. See the extraction index for the pinned-source scope, normative count and known source defects.
  • Describes attacks, not systems: no DFD, components or trust boundaries, and no risk scoring.
  • Schema versioning: the schema labelled 2.0.0 was widened in place, so an older copy rejects newer flows; its published URL ($id and the extension's schema field) currently returns 404.
  • Builder conventions outside the schema: detections, mitigations, countermeasures and red-team tests are custom x- objects linked by generic related-to relationships (the language page documents x-detection and x-mitigation only), and published flows carry an undefined ttp_frameworks property; a STIX importer must allow custom objects, read related-to edges as well as effect_refs, and cannot learn the ATT&CK version from a flow.
  • Confidence: the Builder's v4 scale adds "AI Generated" at 0 and moves "Speculative" to 10 and "Very Doubtful" to 20, while the documented scale has "Speculation" at 0 and "Very Doubtful" at 10; nothing in a flow says which scale it used. The generation guide has analysts validate AI drafts by updating confidence. That convention does not supply tmodel's separate, auditable human-review record or establish that a generated action was accepted.
