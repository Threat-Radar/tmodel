# Skill: publish from a manifest

v0 playbook for publishing tmodel material **from this repository**.
It is not an external bot skill and it does not add a deploy workflow.

Nothing in this file accepts a `DEC-*`. SDL citations point at
[`spec/MAP-0001`](../../spec/MAP-0001-sdl-requirements-crosswalk.md) (draft evidence
from RPT-0013), not at an accepted decision.

## When to use

Use this when adding or refreshing a GitHub Pages HTML page, and later a PDF
slide deck, whose inputs are named in a manifest. The first real content source
is the WAVE 1 bibliography (#86). A knowledge-graph dashboard is later (#75),
and only after the WAVE 2 gate (#84).

Bibliography HTML is generated by `render_bibliography.py`; report pages by
`render_report.py`. `.github/workflows/ci.yml` validates archdoc front matter
**and runs the identity guard** on every PR/push. Do not invent a Pages deploy
workflow in the same change as a content edit.

## Report pages (markdown → static HTML, revisioned)

Longer-form reports (e.g. the SDL report) are published from their archdoc
markdown, not hand-written HTML:

- List the source in `reports.yaml` (`src`, `out`, `title`, optional `links`).
- `python3 docs/publishing/render_report.py` writes `docs/reports/<slug>.html`.
- The page carries a **Revision** = the source's front-matter `version` and the
  `updated` date. These pages are **static**: regenerate only when the source
  changes (bump the source's `version` when you do — that is the revision number),
  **not** on every build. There is no per-build deploy.
- The renderer emits **only the body** — front-matter person fields (authors,
  decision_makers, reviewers) are never published.

## Privacy — no personal identity in published pages without approval

**Rule (sponsor, 2026-10-05): a published page must not contain a project person's
name, handle, or email unless it is explicitly approved.** Public *bibliographic*
authors of cited external standards are fine; the project's own people are not.

- Protected identities live in **`publishing/identities.yaml`** (repo root, *outside*
  `docs/`, so the list itself is never published). **This tracked file lists GITHUB
  IDS ONLY — never real names** — because the repo is world-viewable and the list must
  not itself leak identities. To clear an id for publication, add it under `approved:`
  **with sponsor sign-off**, in its own PR.
- Real names are **never committed anywhere** in this repo. To also match names in the
  guard, put them in an untracked `publishing/identities.local.yaml` (gitignored);
  `check_identities.py` merges it when present.
- `check_identities.py` scans `docs/**/*.html` and generated JSON, JavaScript,
  and CSS under `docs/app/`, and **fails CI** on any protected identity not in
  `approved`. Run it before opening a publishing PR.
- When authoring a record/report/manifest that will be published, prefer the
  **publisher/organization** over personal author names.

> **Pages-scope note:** GitHub Pages currently serves `main:/docs`, which also
> exposes the publishing tooling under `/docs/publishing/`. That is harmless (no
> personal data in the scripts/manifests — `identities.yaml` is github-ids-only and
> holds no real names). A future improvement is to publish only a built
> subtree. Tracked, not done here.

## Security bar

Follow the published SDL crosswalk. MAP-0001 is still draft; these are the
rows this pipeline is written to satisfy:

| MAP-0001 row | How publishing complies |
|---|---|
| 2 Security requirements | A manifest states audience, inputs, and what must not ship (secrets, trackers, unreleased data). |
| 3 Threat modeling | The publish surface is static hosting plus a reviewed git commit. No account, no upload endpoint, no telemetry. |
| 4 Secure design | Defense in depth: no remote scripts, no remote fonts, no third-party pixels. The app bundle and JSON are same-site committed assets. |
| 8 Approved toolchain | HTML is authored in-repo. PDF rendering, when built, runs with local tools only. |
| 13 Release integrity | A real binary later carries sha256, version, and the manifest id. A mock must not ship a file that pretends to be a binary. |
| 14 Secure defaults | Pages are public-read and otherwise inert. No optional analytics flag. |
| 15 Release gate | A human reviews the PR before the page is treated as current. |
| 16 Source integrity | No secrets, tokens, or credentials in the page, the manifest, or the history. |

Also:

- Links to files in this site are relative (`publishing/SKILL.md`, not a host-specific absolute path).
- An absolute link is only for a stable off-site page, such as the GitHub repository.
- Enabling GitHub Pages (folder `/docs` on `main`) is a separate human step. The HTML must already be valid for that.

## Manifest

One YAML file per published item, or one file with several `items` once there
is more than the landing page. Fields in v0:

- `schema` — `tmodel.publishing/v0`
- `id` — stable id (`pub-…`)
- `title`, `kind` (`site-page` now; `slides` later), `status` (`mock`, `draft`, `current`)
- `template` — path of the HTML (or, later, slide) template in-repo
- `source.wave` — `1` bibliography or, later, `kg`
- `source.bibliography_issue` — GitHub issue for the bibliography pass while wave is 1
- `source.record_ids` — library or report ids actually rendered. Empty while the page is still a product mock.
- `outputs` — path and format committed for Pages
- `security` — flags that must stay false: remote scripts, trackers, secrets
- `review.human_required` — always true for `current`
- `pdf` — `status: not-built` until the slide pipeline exists

See [manifest.example.yaml](manifest.example.yaml).

## HTML pipeline (v0)

1. Copy `manifest.example.yaml` to a real manifest name when the page leaves mock status. Keep the example.
2. Edit the template (`docs/index.html` or a new file under `docs/`). One self-contained HTML file per content page: CSS in the file, no `<script>`, no remote URL in `src` or `@import`. `docs/app/` is the deliberate exception: it is generated by `render_app.py` from the local Vite app and may load only its generated same-site script, stylesheet and JSON assets.
3. Point `outputs[].path` at that file. Relative links only, so the page works at the Pages root (`/docs` served as `/`) and in the GitHub blob view.
4. Open the file in a browser from disk. Confirm the distribution block cannot download a binary.
5. Open a PR. State which manifest and which bibliography records (if any) changed. Do not mark a `DEC-*` accepted.

The landing page is still hand-authored. The bibliography is the first generated item; see below. Do not add a Pages deploy workflow in the same change.

## Browser app preview

`render_app.py` is the sole owner of `docs/app/`. It fails instead of silently
omitting a model or an incomplete library, sorts JSON keys, strips engine-local
model paths, and refuses known local-path or credential markers. The Pages-mode
frontend is read-only: it adapts its existing engine providers to same-origin
JSON, hides SDL/proposal/review controls that have no static equivalent, and
never falls back to loopback or a Tauri API. The library inspector is bounded to
fields already present in the public table rather than publishing full records.
Generation always reads the repository's pinned `library` submodule;
`TMODEL_LIBRARY` is deliberately ignored for this public artifact.

Regenerate `docs/app/` whenever any of its inputs change: `spec/vectors/**`,
engine behavior that shapes the model catalog, graph, attack paths, or library
table, the pinned `library` commit, or the Pages-mode frontend. From the
repository root, initialize the pinned submodule and local toolchains, then run:

```sh
git submodule update --init library
python3 -m venv engine/.venv
engine/.venv/bin/python -m pip install -e './engine[dev]'
npm ci --prefix apps/desktop
engine/.venv/bin/python docs/publishing/render_app.py
engine/.venv/bin/python docs/publishing/render_app.py --check
```

If the environments already exist, only the final two commands are needed.
`bin/publish-site` also regenerates the preview as part of the complete site
pipeline. A standalone `npm run build:pages` writes scratch output under
`apps/desktop/dist/`; it does not publish or replace `docs/app/`.

On applicable pull requests and pushes to `main`, `.github/workflows/app.yml`
rebuilds the preview in a temporary directory and byte-compares that output
with the committed `docs/app/`. CI therefore verifies that the committed Pages
snapshot is complete and current, which is the CI publishing contract for
#204. It does not write regenerated files back to the branch, commit them, or
deploy them through a separate Pages workflow; contributors must regenerate
and commit `docs/app/` with the input change.


## Bibliography renderer

WAVE 1 (#86, tracked for this render on #91). Not a knowledge graph (#84).

**Where each page comes from.** The page for one record is an extraction
artifact, so it lives with its source. The library's `bin/render-html` builds
`records/<body>/<id>/summary.html` next to `record.yaml` and `summary.md`.
That file is untracked, like the library's `index/`. This repo never
re-templates it. `render_bibliography.py` renders it in the pinned submodule
and copies it to `docs/library/records/<body>/<id>/summary.html`. It changes
two things: it fills the page's `<!-- site-nav -->` slot with the site nav,
and it turns links to records the manifest does not list into plain text. To
change what a record page shows, change the library (`bin/_record_html.py`)
and move the pin. Do not change it here.

The bibliography itself belongs to this site: the A–Z index and the topic,
type, body, and crosswalk views under `docs/bibliography/`. Those pages come
from `bibliography.yaml`. Nav comes from `site.yaml`.

1. When the `library` pin moves, run `python3 docs/publishing/render_bibliography.py --sync`. It appends each new library record with its `record.yaml` type and a default topic: `record.topic`, else the first controlled subject tag, else the first other subject tag, else `topic: ~` (shown as "no topic tag yet"). It never edits an existing entry, so a reviewer's topic choice stays. To change a topic, edit `bibliography.yaml`. `records[].type` must match `record.yaml`. `records[].topic` must be `record.topic` if that field is set, otherwise a tag the record already has.
2. Run `bin/publish-site` from the repo root. Commit the manifest, the script, and the HTML together. A second run with no hand edits must be a no-op.
3. Do not hand-edit `docs/bibliography/`. Categorization rules and the v1 vs later views are in [bibliography-review.md](bibliography-review.md).
4. Output is self-contained HTML: CSS in the file, no `<script>`, no remote assets, relative links. `docs/.nojekyll` stays so Pages does not run Jekyll over the HTML.
5. A human reviews the pages, then this skill and the review note are updated. Re-run as references arrive. The first render is not final.

## PDF slideware pipeline (not built)

Described so the manifest has somewhere to grow. Do not implement this in v0.

1. A manifest item with `kind: slides` names a template that will live beside this skill.
2. Render **locally**. Preferred tools, in order, once one is chosen on a maintainer machine: Typst, or Pandoc into HTML then a local HTML-to-PDF engine (WeasyPrint or Prince with an offline license). No hosted render API. No network during the render.
3. Inputs are the same source block as HTML. WAVE 1 fills slides from bibliography summaries, tags, and the applicability table (#86). Later, each figure and number comes from the KG, and a KG update means regenerate from the manifest rather than hand-editing the deck. That dashboard behavior is WAVE 2 / #75, not this file.
4. Provenance on the deck: manifest `id`, input record ids, tool name and version. Commit the PDF only when a reviewer needs the bytes; otherwise the manifest plus the local command is the recipe.
5. The same release gate applies: human review, no secrets, checksum noted if the PDF is an artifact that ships.

## Content rule

A published item acts like a dashboard only once its manifest `source.wave` is `kg`. Until then it must say which bibliography records it used, or say that it is a product mock with an empty `record_ids` list. Do not invent KG edges to fill a page.
