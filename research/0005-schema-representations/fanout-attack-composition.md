# RPT-0005 fan-out, agent 2: dimensions 4 and 7

Scope: dimension 4 (MITRE ATT&CK Enterprise, CAPEC, D3FEND, STIX 2.1, TAXII 2.1) and dimension 7 (the security-relevant part of SPDX 3.0.1 and CycloneDX 1.7). Everything below was checked on 2026-10-05 against downloaded artifacts (STIX bundles, XML + XSD, OWL/TTL, JSON Schema, specification HTML), parsed with python3 (and rdflib 7.6.0 in a scratch venv for the RDF). Files and SHA-256 hashes are in section 10; the files are in `scratchpad/fanout/agent2-files/`. No WebFetch summaries were used: every page was fetched with curl and read from its own text. WebSearch was attempted twice and failed (session limit; section 9), so currency checks rely on the artifacts and their publishers' own listings.

RPT-0004 already covers SPDX and CycloneDX naming, dependencies, completeness, hardware, build identity and the VEX status comparison; this file cites it and does not repeat it.

Findings that bear on tmodel:

- **ATT&CK no longer links to CAPEC.** In v12.1, 104 active techniques carried a `capec` external reference; from v13.0 (April 2023) on, none does. In 19.2, the 36 remaining `capec` references sit only on revoked or deprecated techniques. MITRE's ATT&CK team confirmed it in `mitre/cti` issue #221 (2023-09-07): the references "were removed in v13 of ATT&CK … and it's an oversight that this wasn't mentioned in the release notes … The CAPEC team maintains their own mapping from CAPEC to ATT&CK". ATT&CK also has no CWE, CVE-as-data or D3FEND links. The weakness → attack pattern → technique chain must be assembled from CAPEC's side (section 8).
- **Relations are first-class, cited objects.** Each relationship is a STIX SRO with its own id, `created`, `modified`, `created_by_ref`, and (for 18,960 of 21,262) `external_references` citing the source of the claim; `description` (19,925) carries the procedure text ("APT29 used … to …"). This is per-statement provenance, stronger than CWE's per-entry `Content_History`, but every statement has the same author (MITRE).
- **Supersession is machine-readable.** A replaced object gets `revoked: true` plus a `revoked-by` SRO to its successor (157); a dropped one gets `x_mitre_deprecated: true` with no successor. Example: v19.0 revoked `T1562.001` "Disable or Modify Tools" `revoked-by` the new `T1685`. One edge breaks ATT&CK's own rule that `revoked-by` must join objects of the same type (ADM `relationship.schema.ts`): `malware` S9000 "Ngrok" `revoked-by` `tool` S0508 "ngrok".
- **An id can change meaning without revocation.** In 19.x, `TA0005` is named "Stealth" (`x_mitre_shortname: stealth`), where in 18.1 it was "Defense Evasion"; a new `TA0112` "Defense Impairment" took part of the old scope. `TA0005` was not revoked and its `x_mitre_version` is `1.0` in both. A tmodel mapping to `TA0005` made before April 2026 silently changes meaning. Mappings must pin the ATT&CK release, not just the id (echoes RPT-0014's finding on OWASP and ATLAS id drift).
- **Detection is now its own layer.** `x-mitre-detection-strategy` `detects` `attack-pattern` (one strategy per technique: 697 = 697), and each strategy lists `x-mitre-analytic` objects via the embedded `x_mitre_analytic_refs`; analytics point at data components through `x_mitre_log_source_references` and carry tunable `x_mitre_mutable_elements`. This is a ready source for a Detection/Indicator concept (Table 2, part 2).
- **No paths and no order.** A technique's `kill_chain_phases` names its tactic (the adversary's goal); `x-mitre-matrix.tactic_refs` orders the 15 tactics as columns. Campaigns and groups `uses` sets of techniques with no sequence. ATT&CK supplies AttackStep classes, not AttackPaths.
- **ICS assets are device classes.** ICS `x-mitre-asset` (e.g. "Virtual Private Network (VPN) Server", `x_mitre_sectors`, `x_mitre_related_assets`) is a component type that techniques `targets`, not a thing of value in a product; closer to Component than to ARCH-0001's Asset.

Findings that bear on tmodel:

- **CAPEC is frozen, and its ATT&CK mapping with it.** 3.9's release note says it "Updated CAPEC to ATT&CK mappings based upon ATT&CK 12.0". Against ATT&CK 19.2, the 189 distinct ATT&CK ids it maps to are now 179 active, 9 revoked (15 mappings, e.g. `T1562.001` → `T1685`) and 1 absent from Enterprise (`T1513`). None of the 272 mappings fills the optional `Mapping_Fit` element (Exact, CAPEC More Abstract, CAPEC More Specific, Imprecise, Perspective). A tmodel import must follow ATT&CK's `revoked-by` edges to repair them and cannot inherit a fit grade.
- **The CAPEC ↔ CWE link is the one maintained on both sides.** CAPEC 3.9 has 1,214 `Related_Weakness` links (1,212 distinct pairs) from 450 patterns to 336 CWEs. CWE 4.20 (2026-04-30) mirrors them exactly in `Related_Attack_Patterns` (1,212 pairs each way, 0 differences), and all 336 CWEs still exist as weaknesses. But 30 of them (369 links, 30%) are now Usage `Discouraged` and 42 `Allowed-with-Review` under CWE's mapping notes, so a CAPEC-derived Weakness edge needs re-checking against CWE's rules (pilot).
- **The weakness edge has OR semantics.** The XSD: "The association implies a weakness that must exist for a given attack to be successful. If multiple weaknesses are associated … any of the weaknesses (but not necessarily all) may be present." This is ARCH-0001's `exploits` (pattern → weakness), with a disjunction qualifier the edge has to carry.
- **CAPEC has the nearest thing to AttackStep and AttackPath in dimension 4.** `Execution_Flow` gives ordered steps inside one pattern (with a phase); `CanPrecede` (162) and `CanFollow` (10) order patterns. Relation natures in the data: `ChildOf` 533, `CanPrecede` 162, `PeerOf` 19, `CanFollow` 10, `CanAlsoBe` 3 (`ParentOf` is in the enumeration but not stored). Unlike CWE, relations carry no `View_ID`; the only qualifier is `Exclude_Related` (260 uses).
- **Feasibility inputs are qualitative.** `Likelihood_Of_Attack`, `Typical_Severity`, `Skills_Required` (High/Medium/Low/Unknown) and `Resources_Required` resemble the inputs of a Common Criteria attack-potential rating (R-013), but as fixed categories and prose; mapping them is DEC-003's question.
- **Deprecation names its successor only in prose**, like CWE: CAPEC-106 has only `Description` and `Content_History`, and the description says "deprecated as it referes to an existing chain relationship between 'CAPEC-93 …' and 'CAPEC-63 …'".

Findings that bear on tmodel:

- **Defence-to-offence links are inferred, not stated.** In the ontology a defensive technique has restrictions to artifacts (`analyzes`, `filters`, `hardens`, `isolates`, …; 210 of 272 techniques have at least one) and an offensive technique has restrictions to artifacts (`modifies`, `produces`, `may-modify`, `accesses`, …; 348 of 874 Enterprise techniques). D3FEND publishes the joins as `d3fend-full-mappings.csv`: 16,249 rows; for ATT&CK Enterprise, 6,812 distinct (countermeasure, technique) pairs over 207 countermeasures and 326 ATT&CK ids. 13,130 of the 16,249 rows join through the artifact hierarchy rather than the same artifact (e.g. Credential Hardening `hardens` `Credential`; T1003.005 `accesses` `Encrypted Credential`, a subclass). The site says "We are working on open sourcing the SPARQL queries soon", so the inference rule is not yet inspectable. For tmodel, every D3FEND `mitigated_by` edge is a derived claim with an artifact path as its evidence, and should be imported as such.
- **Coverage of ATT&CK 19.2 is partial and slightly stale.** 311 of 697 active Enterprise techniques (44.6%) have at least one inferred countermeasure. 15 ATT&CK ids in the 1.6.0 CSV are revoked or deprecated in 19.2 (e.g. `T1562.001`), although D3FEND 1.5.0 "Update[d] MITRE ATT&CK to v19.0". ATLAS techniques are imported as classes but have no rows in the CSV.
- **Digital artifacts are the closest catalog to Asset and Component, at type level.** `d3f:DigitalArtifact` (903 classes: `Credential`, `Process`, `NetworkTraffic`, `PackageURL`, …) names the kinds of things attacks touch, with `d3f:contains`, `d3f:has-input`/`has-output` and `d3f:carries` between them. MITRE's own blog (2025-12-16) describes a three-step threat-modeling method using the ontology and its D3FEND CAD tool: model artifacts, link an attacker's kill chain to them, then add countermeasures along the artifact chain. That is ARCH-0001's model drawn with D3FEND types.
- **Deprecation is semi-machine-readable.** 232 classes have `owl:deprecated true`, all imported offensive techniques; 189 of them carry `rdfs:seeAlso` to a successor and an `rdfs:comment` such as "This technique has been revoked by T1685". No defensive technique or artifact is deprecated.
- **Neither key is fully stable.** Between 1.2.0 and 1.6.0, one `D3-` id changed under a stable IRI (`ChangeDefaultPassword`: `D3-CFP` → `D3-CDP`), and two IRIs were renamed under stable ids (`EndpointBasedWebServerAccessMediation` → `Endpoint-basedWebServerAccessMediation`, `D3-EBWSAM`), with no deprecation record for either.
- **CWE and CAPEC copies.** D3FEND imports CWE as 943 classes (CWE 4.17, per the 1.2.0 changelog; CWE 4.20 has 969 weaknesses), 26 with a `weakness-of` artifact restriction. CAPEC is present only as one class, `d3f:CAPEC-663`, whose `d3f:capec-id` is wrongly `"CAPEC-553"`.
- **Control mappings are fit-graded.** The 117 `d3f:NISTControl` individuals link to defensive techniques with `narrower` (110), `broader` (35), `related` (21) and `exactly` (14), the kind of graded mapping CWE and CAPEC only offer as an unused option.

Findings that bear on tmodel:

- **Provenance and versioning are in every object.** Every SDO and SRO has `created`, `modified` (required), optional `created_by_ref`, `confidence` (0 to 100), `revoked`, `external_references`, markings. Relationships are objects, so each edge carries its own author, time and confidence. This is the strongest per-statement provenance among the dimension 4 formats.
- **Review has a native carrier, but not tmodel's verdict.** `opinion` holds `opinion` ∈ `strongly-disagree`, `disagree`, `neutral`, `agree`, `strongly-agree`, an `explanation`, `authors` and `object_refs` (which may point at relationships). The spec: "an assessment of the correctness of the information in a STIX Object produced by a different entity". It expresses agreement, not accept/reject/needs-work, and has no field for the impact a human assigns (R-019). `note` adds free text by anyone.
- **Revocation has no successor field.** `revoked` is permanent ("future versions of the object with this id MUST NOT be created") but the spec defines no pointer to a replacement; ATT&CK added `revoked-by` for that. `duplicate-of` links equivalents across producers without saying which survives.
- **No weakness, path, risk or product applicability.** There is no Weakness object (CWE only as an external reference), no ordering of attack patterns beyond `kill_chain_phases`, no score on `vulnerability`, and the `software` SCO has `name`, `cpe`, `swid`, `vendor`, `version` but no purl and no version ranges. These would all be extension definitions.
- **ATT&CK uses the deprecated extension route.** ATT&CK's `x_mitre_*` properties and `x-mitre-*` objects are the §11 mechanism; a tmodel extension of STIX should use `extension-definition`, which gives the extension an id, a `schema` and a `version`.

Findings that bear on tmodel:

- **A transport, not a model.** TAXII carries STIX and adds only server-side metadata (`date_added`, manifest versions). It bears on DEC-008-style distribution (live lookup vs mirror), not on DEC-001.
- **Retention is undefined.** §1.6.11: "There are no requirements defined in this specification for how long a TAXII server needs to store a specific object". A tmodel mirror cannot assume a TAXII server keeps old versions; ATT&CK works around this with one API root per release.

Findings that bear on tmodel (beyond RPT-0004):

- **Each VEX or score statement is an attributable element.** A VEX statement is a `Relationship` subclass from a `Vulnerability` to "elements representing the VEX products" (`to`), optionally narrowing to the part where the vulnerability was found with `assessedElement`; it has its own `spdxId`, required `creationInfo`, `suppliedBy`, and published/modified/withdrawn times. The spec adds an inheritance rule: if a statement lacks `createdBy` or `created`, the document's `CreationInfo` is authoritative. This is the per-instance applicability Assertion that #17 asks for, with withdrawal but no explicit supersession edge.
- **Human review has a slot.** `Annotation` with `annotationType: review` ("Used when someone reviews the Element") has a required `subject`, a `statement` and the element's `creationInfo` (who, when). It has no verdict or impact field, so ARCH-0001's Review needs an `Extension` or a convention in `statement`.
- **Threat models are only referenced.** `ExternalRefType` (46 values) includes `securityThreatModel` ("A reference the security threat model … for a package"), `securityAdversaryModel`, `riskAssessment`, `securityPenTestReport`, `cwe`, `securityAdvisory`, `securityFix`, `vulnerabilityExploitabilityAssessment`. SPDX can point from a Package to a tmodel model, not carry it.
- **AI and Dataset profiles add asset properties.** `DatasetPackage.confidentialityLevel` and `hasSensitivePersonalInformation` are asset-value inputs; relationships `trainedOn` and `testedOn` record model lineage, which is the path data poisoning follows (RPT-0014); `AIPackage.safetyRiskAssessment` is a self-declared risk tier, `autonomyType` whether the system acts "without human involvement".
- **Vulnerability-centred attribution edges.** `foundBy`, `reportedBy`, `coordinatedBy`, `publishedBy`, `republishedBy` ("i.e. NVD"), `exploitCreatedBy`, `fixedBy` (to Agents) give a Party model for the disclosure process.
- **Producers exist; consumers were not found.** OpenEmbedded-Core emits SPDX 3 VEX (`sbom30.py` builds `VexFixed`, `VexAffected`, `VexNotAffected` relationships); Trivy reads CycloneDX, OpenVEX and CSAF VEX but not SPDX; RPT-0004 found Dependency-Track and GUAC cannot read SPDX 3.

Findings that bear on tmodel (beyond RPT-0004):

- **CycloneDX models the system side of a threat model.** `services[].data[]` is a typed data flow (`flow`, `classification`, `source`/`destination` by URI or BOM-Link); `services[].trustZone` names a zone and `x-trust-boundary` says "by using the service, a trust boundary is crossed". The boundary is a property of a service, not of a flow. cdxgen sets `x-trust-boundary` from code analysis (`lib/inventory/analyzer.js`), so real BOMs can carry it.
- **Per-field provenance arrived in 1.7.** `citations[]` attribute any BOM value, located by JSON Pointer or path expression, to an `attributedTo` (component, service, tool, organization, person) or a `process` in `formulation`, with a required `timestamp`. Without them, a VEX `analysis` has times (`firstIssued`, `lastUpdated`) but no author of its own.
- **Review, claims and attestations.** `annotations[]` (required `subjects`, `annotator`, `timestamp`, `text`; optional signature) can attach a review to any `bom-ref`. `declarations` maps `requirements` to `claims` (`target`, `predicate`, `mitigationStrategies`, `reasoning`, `evidence`, `counterEvidence`) with `conformance` and `confidence` scores (0 to 1) and a `rationale`, signed by `assessors` and an `affirmation`; `evidence` has `author` and `reviewer`. This is a requirement/control-to-evidence chain that dimension 6 (agent 3) may want; for this dimension it is a Review/Assertion carrier.
- **Threat models by reference.** `externalReferences[].type` (47 values) includes `threat-model`, `adversary-model`, `risk-assessment`, `pentest-report`, `vulnerability-assertion`, `exploitability-statement`, `poam`. ML risks appear as `modelCard.considerations.ethicalConsiderations[]` (`name`, `mitigationStrategy`).
- **Weakness only through a vulnerability**, as bare integers (`cwes`, `minimum: 1`), and no field for ATT&CK, CAPEC or D3FEND ids except `properties`.
- **Tool support is real for VEX.** Trivy consumes CycloneDX VEX files (and emits CycloneDX SBOMs); Dependency-Track imports (`PUT`/`POST /v1/vex`) and exports (`GET /v1/vex/cyclonedx/project/{uuid}`) CycloneDX VEX.

### 1.8 Dimension questions answered

**Dimension 4.**

1. *Object and relationship types.* ATT&CK: section 1.1 (14 object types, 7 relationship types). CAPEC: `Attack_Pattern`, `Category`, `View`; natures `ChildOf`, `ParentOf`, `CanFollow`, `CanPrecede`, `CanAlsoBe`, `PeerOf`; plus `Related_Weakness` and `Taxonomy_Mapping`. D3FEND: defensive techniques and tactics, digital artifacts and events, agents, imported offensive techniques and CWE, NIST controls; 199 artifact-relation properties. STIX: 19 SDOs, 2 SROs, 18 SCOs; relationship vocabulary in Appendix B. TAXII: resources and endpoints only.
2. *Cross-references, maintainers, currency.* Section 8. In short: CAPEC ↔ CWE is current on both sides (CWE 4.20 mirrors CAPEC 3.9 exactly); CAPEC → ATT&CK is pinned to ATT&CK 12.0 and 15 of 272 mappings now point at revoked techniques; ATT&CK → CAPEC was removed in v13 (2023); D3FEND → ATT&CK is inferred through artifacts, updated to ATT&CK v19.0 (D3FEND 1.5.0, 2026-07-31), covers 44.6% of active 19.2 techniques.
3. *Deprecation and revocation.* ATT&CK: `revoked` (STIX boolean) + `revoked-by` SRO to successor; `x_mitre_deprecated` (boolean) with no successor. STIX: `revoked` (permanent, no successor), `duplicate-of`. CAPEC: `Status` ∈ `Deprecated`, `Obsolete` (also `Draft`, `Incomplete`, `Stable`, `Usable`), successor in `Description` prose. D3FEND: `owl:deprecated true` + `rdfs:seeAlso` successor (189 of 232) + `rdfs:comment` "revoked by T…"; renamed IRIs disappear with no tombstone. TAXII: none (servers may delete; §1.6.11).
4. *STIX extension and ATT&CK's use of it.* STIX 2.1 §7.3 `extension-definition` with five `extension_types`; §11 custom properties/objects deprecated. ATT&CK uses only the deprecated §11 route (`x_mitre_*`, `x-mitre-*`, custom relationship types) and documents its schema in the ADM Zod library; local ATT&CK content is supported by Workbench's organization namespace.
5. *Catalogs behind ARCH-0001 types.* Weakness: CWE (pilot), reachable from CAPEC `Related_Weakness` (`exploits`, OR semantics, current). AttackPattern/AttackStep: CAPEC (`Attack_Pattern` ≈, `Execution_Flow` ≈; frozen since 2023) and ATT&CK (`attack-pattern` ≈ as step classes; current, but ids drift and no CWE link). Mitigation: ATT&CK `course-of-action` (44 generic mitigations, `mitigates` with technique-specific text) ≈; D3FEND `DefensiveTechnique` = as a countermeasure catalog, linked by inference ≈; CAPEC `Mitigations` txt. No catalog gives AttackPath.

**Dimension 7.**

1. *How vulnerabilities and VEX attach to components.* SPDX: `Vulnerability` element; `hasAssociatedVulnerability` from Artifact to Vulnerability; VEX and score statements are `VulnAssessmentRelationship` subclasses from Vulnerability to product elements, narrowed by `assessedElement`. CycloneDX: top-level `vulnerabilities[]` with `affects[].ref` (a `bom-ref` or BOM-Link) and per-version `status` (affected/unaffected/unknown, `vers` ranges), and one `analysis` per vulnerability entry (state, justification, response). Status vocabularies compared in RPT-0004.
2. *Identifiers onto Product and Component.* Component: CycloneDX component/service, SPDX Package/File/Snippet (and AIPackage, DatasetPackage). Product: CycloneDX `metadata.component`, SPDX `Sbom.rootElement` (RPT-0004 §6). Identifiers: purl (CycloneDX `purl`; SPDX `packageUrl` or `externalIdentifier` type `packageUrl`) keys a package version; CPE (`cpe`; `cpe22`/`cpe23`) keys NVD matching; SWID (CycloneDX SWID fields; SPDX `swid` = CoSWID) keys installed software; hashes (`hashes`; `verifiedUsing`, `contentIdentifier`) pin bytes. Only SPDX's `spdxId` is a global element id; CycloneDX needs BOM-Link. Details in RPT-0004 §1.1, §1.2, §6; not repeated.
3. *Other profiles or types bearing on threat modeling.* SPDX: AI profile (`safetyRiskAssessment`, `autonomyType`, `useSensitivePersonalInformation`), Dataset profile (`confidentialityLevel`, `hasSensitivePersonalInformation`, `knownBias`), `trainedOn`/`testedOn`, `Annotation` review, `securityThreatModel` reference, Build profile (RPT-0004 §6). CycloneDX: services with `trustZone`, `x-trust-boundary` and typed data flows; `declarations` (claims, evidence, attestations); `definitions.standards`; `citations`; `annotations`; `modelCard` considerations; `threat-model` external references; `cryptographic-asset` components (CBOM).
