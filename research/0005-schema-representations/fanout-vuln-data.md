How CWE is extended or worked around in practice (all checked against artifacts):

1. **Closed catalog, extension by MITRE only.** CWE's XSD admits no local ids (pilot). Within the catalog MITRE adds *views* instead: 59 views in 4.20 (38 Graph, 17 Implicit, 4 Explicit), among them CWE-1003 "Weaknesses for Simplified Mapping of Published Vulnerabilities" (the view NVD has historically used, per the CWE FAQ) and CWE-635 "Weaknesses Originally Used by NVD from 2008 to 2016" (Obsolete). A view narrows or regroups; it cannot add a weakness.
2. **NVD invents two pseudo-CWE ids.** `NVD-CWE-noinfo` and `NVD-CWE-Other` appear in `weaknesses[]`. Live count on 2026-10-06 (API `cweId=` filter, `totalResults`): 36,258 and 30,007 CVEs, of 401,518 CVEs in total. So at most 16.5% of all CVEs (66,265 of 401,518; the two sets may overlap) carry an NVD-minted placeholder in a field that otherwise holds CWE ids. This is the largest local extension of CWE in the data.
3. **CVE records allow free text beside the id.** `problemTypes[].descriptions[]` has `cweId` (pattern `^CWE-[1-9][0-9]*$`, optional) and a free `type` ("CWE", "text", "OWASP", ...) plus `description` text. A CNA that has no CWE writes text. Real record CVE-2026-86551 (ZTE) uses `type: "CWE"` with the id *and* the title in `description`.
4. **Consumers that validate hard cannot carry local ids at all.** CISA KEV `cwes[]` requires `^CWE-([0-9])+$`; CSAF 2.1 `vulnerabilities[].cwes[]` requires `id` (`^CWE-[1-9]\d{0,5}$`), `name` and `version`; CSAF 2.0 `cwe` requires `id` and `name`; CycloneDX `cwes[]` is an array of integers. A local weakness has to be dropped or mapped to a CWE id before it reaches these formats.
5. **OSV has no CWE field.** GitHub's advisories put `database_specific.cwe_ids` (example GHSA-jfh8-c2jp-5v3q: CWE-20, -400, -502, -917) in the open per-database object, so CWE is a convention of one database, not of the schema.
6. **SARIF has a real mechanism.** SARIF 2.1.0 distinguishes a standard taxonomy (CWE, stored in `run.taxonomies[]`) from a tool-defined custom taxonomy, and `reportingDescriptorRelationship.kinds` has well-known values `superset`, `subset`, `equal`, `disjoint`, `relevant`, `incomparable`, `canPrecede`, `canFollow` (read in the schema, `reportingDescriptorRelationship`). A tool can therefore define its own weakness ids and state `subset`/`superset`/`equal` against a CWE id. This is the closest published model for a tmodel local weakness; it is richer than CWE's own `Mapping_Fit` in that it is directional.
7. **Static-analysis tools tag, they do not extend.** CodeQL's metadata guide says to tag a security query with the most specific Base or Class weakness in View 1000, as `@tags external/cwe/cwe-079` (zero-padded). The downloaded real query (`codeql-js-Xss.ql`, `@id js/xss`) tags `external/cwe/cwe-079` and `external/cwe/cwe-116`. Custom queries just reuse the tag pattern; no custom-id convention is documented in that guide.
8. **CWE's own outward mapping model.** 1,660 `Taxonomy_Mapping` elements in 4.20 map CWE entries to other taxonomies (largest: Software Fault Patterns 305, PLOVER 304, CERT C 228, ISA/IEC 62443 199). Direction is CWE-to-other, with `Mapping_Fit`; an organisation's local taxonomy is not a listed target (`TaxonomyNameEnumeration` is fixed).

Net for tmodel (evidence, not a proposal): none of the checked consumers gives local weaknesses a home inside CWE. The three working patterns are placeholders in the same field (NVD), a parallel taxonomy with relationship kinds (SARIF), and an open `database_specific`-style bag (OSV/GHSA).

Findings that bear on tmodel:

- **Applicability is a typed version timeline, not a status per product.** `ranges[].events` are ordered change points; the spec gives the `IsVulnerable` pseudocode (`introduced` ≤ v → vulnerable; `fixed` ≤ v → not; `last_affected` < v → not; `limit` bounds). Version ordering depends on `type` (SEMVER, ECOSYSTEM, GIT with full 40- or 64-hex commit ids). There is no `not_affected`, no justification, and no status other than affected-in-range. For tmodel's `applies_to_product` this gives a precise affected-version set per package but cannot say "this product is not affected although it contains the package".
- **Several databases can say the same thing about one vulnerability.** `aliases` (symmetric, transitive: "affect any given software component the same way"), `upstream` (transitive, not symmetric: distro advisory to upstream CVE) and `related` (symmetric, not transitive) are three different relation semantics on one record. Two records with the same `id`: the later `modified` is authoritative, so supersession within one id is by timestamp.
- **Withdrawal has no successor.** `withdrawn` is a timestamp; the spec says "any rationale ... should go into the summary text". Real example GHSA-9xgp-hfw7-73rq has `withdrawn` equal to `published` and `modified`, and keeps its `affected[]`. A rejected CVE mirrored by GitHub (GHSA-vf43-p6cg-xhx2) carries only prose in `details` ("Rejected reason: DO NOT USE THIS CVE RECORD ..."), empty `affected`, and `aliases: ["CVE-2026-51230"]`. Unlike CVE's `replacedBy`, an importer cannot recover a `supersedes` edge without parsing text (`txt`).
- **Severity is a list of typed vectors with a source.** `severity[]` takes `type` (CVSS_V2, CVSS_V3, CVSS_V4, Ubuntu), `score` (a vector string, regex-validated per type, or Ubuntu's lowercase priority) and optional `source` (NVD, CNA, SELF; omitted means the home database). There is no numeric score field and no date per severity. If any `affected[].severity` is set, the top-level `severity` must not be.
- **No weakness field.** See 1.0 item 5.
- **Review state is a database convention.** GitHub's records carry `database_specific.github_reviewed` and `github_reviewed_at` (real examples). OSV itself defines no review field.
- **purl is first-class for the package, not for the instance.** `package.purl` is "without the `@version` component" (spec text); version goes in ranges. This matches CVE 5.2.0's `packageURL` and CSAF 2.1's `purls` in leaving the version out of the product name (see section 8).

Findings that bear on tmodel:

- **Score structure and nomenclature.** v4.0 requires labelling a score by the metric groups used: CVSS-B, CVSS-BE, CVSS-BT, CVSS-BTE. The spec says the application of Threat and Environmental metrics "is the responsibility of the CVSS consumer" and that providers such as the NVD "typically provide only the Base metrics". So almost every score in the wild is CVSS-B, which is generic (per vulnerability), while ARCH-0001 §6 wants a per-product and per-environment score. The Environmental group (security requirements, modified base metrics) and Threat group are the format's own slots for that.
- **Scale and severity.** Both versions: 0.0 to 10.0; qualitative bands None 0.0, Low 0.1-3.9, Medium 4.0-6.9, High 7.0-8.9, Critical 9.0-10.0 (v3.1 Table 14, v4.0 Table 22); using the bands is optional.
- **The trust-boundary hook.** v3.1 `scope` (UNCHANGED/CHANGED) is defined through "security authority" and "security scope": "whenever the impact of a vulnerability breaches a security/trust boundary and impacts components outside the security scope" a Scope change occurs. v4.0 replaces it with separate impacts on the vulnerable system (`vuln…Impact`) and on subsequent systems (`sub…Impact`), and adds `SAFETY` to the subsequent-system values and a `Safety` supplemental metric. These are a one-bit flag and a second impact set, not a TrustBoundary entity, but they are the only trust-boundary signal in any vulnerability-score format checked.
- **The score carries no author.** Neither schema has a field for who scored it or when. Attribution always comes from the container: CVE's `providerMetadata` (CNA vs `CISA-ADP`), NVD's `source` and `type` (Primary or Secondary), OSV's `severity[].source` (NVD, CNA, SELF), CSAF's `metrics[].source` (a URL, 2.1) or `document.publisher`, CycloneDX `ratings[].source`.
- **Where the score lives.** Inside the CVE record: `metrics[]` with `cvssV2_0`, `cvssV3_0`, `cvssV3_1`, `cvssV4_0` (the CVE schema imports FIRST's schemas by `$ref`; **the imported copy has drifted**: CVE's `imports/cvss/cvss-v4.0.json` is the 2023-10-11 revision (`$id …cvss-v4.0.json?20231011`), while FIRST's current file is Revision 2 (`?20260226`); the enum `modifiedSubConfidentialityImpact`/`modifiedSubIntegrityImpact`/`modifiedSubAvailabilityImpact` lists `NONE` in CVE's copy and `NEGLIGIBLE` in FIRST's, so a Revision 2 score that uses `NEGLIGIBLE` would not validate against CVE 5.2.0's schema (compared by script on 2026-10-06)). Inside NVD: `cvssMetricV2/V30/V31/V40`, each with `source`, `type`, `cvssData` (NVD schema API version 2.2.4). Inside CSAF: `scores[]` (2.0: `cvss_v2`, `cvss_v3`) and `metrics[].content` (2.1: `cvss_v2`, `cvss_v3`, `cvss_v4`, `epss`, `ssvc_v2`, `qualitative_severity_rating`), each with `products[]`, so a score is per product. Inside CycloneDX: `ratings[]` with `method` (CVSSv2, CVSSv3, CVSSv31, CVSSv4, OWASP, SSVC, other). Inside SPDX 3.0.1: `CvssV2/V3/V4VulnAssessmentRelationship` with `vectorString`, `score`, `severity`. Inside OSV: `severity[]` (vector only).
- **Several scores per vulnerability are normal.** Red Hat's CSAF for CVE-2021-44228 gives CVSS 3.1 base 9.8 for the products it covers; CISA-ADP's CVE container gives 3.1 base 10.0 (scope CHANGED); the Siemens advisory SSA-661247 gives 10.0 with temporal vector `E:H/RL:O/RC:C`. Same CVE, three numbers, three authors.
- **FIRST's JSON schema bundles human labels.** Enum values are words (`NETWORK`, `ADJACENT_NETWORK` in v3.1 but `ADJACENT` in v4.0, `PROOF_OF_CONCEPT`), while the vector string uses letters; both must be checked for consistency (the schema does not enforce it; CSAF 2.0 and 2.1 have a mandatory test "Inconsistent CVSS" for this).

Findings that bear on tmodel:

- **A probability is not a severity.** FIRST: "Not a 'severity' score and not a complete risk score." It is a population-level estimate keyed on the CVE only, so it cannot be product- or environment-specific; as a RiskScore input it is the "likelihood" half only, and calibrated, not ordinal ("a score of 0.05 represents a genuine 5% probability ... within 30 days").
- **Time dimension is in the data model.** Scores change daily and the API supports `date=` and a 30-day series, so an import must store (score, date, model version) or the number cannot be reproduced; the model version changes, and FIRST says history is useful "when reconstructing a prioritization decision". Real data: CVE-2021-44228 is 0.99999 at percentile 1.0 on 2026-10-05.
- **Embedded in other formats with the same two fields.** CSAF 2.1 `metrics[].content.epss` {`percentile`, `probability`, `timestamp`}; SPDX 3.0.1 `EpssVulnAssessmentRelationship` {`probability`, `percentile`}; neither carries the model version.
- **Percentile is a rank, not a second probability.** Both fields are strings in the API and in CSAF 2.1 (regex `^(([0]\.([0-9])+)|([1]\.[0]+))$`).

Findings that bear on tmodel:

- **Product naming has no version range.** The schema has no range, `lessThan` or `vers` field (grep of the spec for "range" returns nothing; the roadmap lists "Version Range Support" as a future item). A statement names exact products, usually by a purl that includes the version (spec example `pkg:apk/wolfi/git@2.39…`). Real examples: Trivy's own VEX names `pkg:golang/github.com/aquasecurity/trivy` (no version) with `subcomponents` `pkg:golang/helm.sh/helm/v3`; Deckhouse names `pkg:golang/github.com/opencontainers/runc@v1.2.9`. Coverage of "all versions in a range" must be enumerated.
- **Four statuses and five justifications, enforced by the schema.** `status`: `not_affected`, `affected`, `fixed`, `under_investigation`. `justification`: `component_not_present`, `vulnerable_code_not_present`, `vulnerable_code_not_in_execute_path`, `vulnerable_code_cannot_be_controlled_by_adversary`, `inline_mitigations_already_exist`. The schema's `allOf` demands, for `not_affected`, a `justification` or an `impact_statement`, and for `affected` an `action_statement`. The spec discourages `impact_statement` as it "breaks VEX automation".
- **Time is the supersession mechanism.** "VEX is designed to be a sequence of statements, each overriding, but also enriching the previous ones"; timestamp and document `version` order them; `timestamp` cascades from document to statement. There is no explicit `supersedes` edge between documents or statements.
- **Attribution is one string.** `author` plus `role` (strings), optional `supplier`, `tooling`. The roadmap says the string "has proven to be unsuitable" for multi-stakeholder approval. Signing is outside the format: the document is carried as the predicate of an in-toto attestation (ATTESTING.md); the signing envelope is in-toto's, not OpenVEX's.
- **Statement ids are optional.** A `@id` on a statement makes it referable, but the real Deckhouse document has none. For tmodel's `Assertion` that means an importer must mint ids.

Findings that bear on tmodel:

- **Product naming is the richest of the four encodings.** A `product_tree` gives each product a `product_id`, a `name`, and a `product_identification_helper` with `cpe`, `hashes`, `model_numbers`, `purl` (2.0) or `purls` (2.1, array), `sbom_urls`, `serial_numbers`, `skus`, `x_generic_uris`. `branches[]` nest categories `vendor` > `product_family` > `product_name` > `product_version` or `product_version_range` (a `vers` string) > `architecture`, `host_name`, `language`, `patch_level`, `service_pack`, `specification`, 2.0 `legacy`, 2.1 `platform`. Component-of-product is `relationships[]` (2.0: `default_component_of`, `external_component_of`, `installed_on`, `installed_with`, `optional_component_of`) or 2.1 `product_paths[]` (a path of `subpaths`). Statements then refer to `product_id`s only. Real Red Hat VEX for CVE-2021-44228: 2,357 product entries carry a `purl` (e.g. `pkg:maven/org.apache.logging.log4j/log4j-core`), 2,254 products are `known_not_affected`, 122 `fixed`, 4 `known_affected`, and all relationships are `default_component_of`. Products are enumerated, not given as ranges, even though `product_version_range` exists.
- **A VEX is one profile of an advisory document.** Profile "VEX" requires `product_tree`, `vulnerabilities`, at least one of `product_status.{fixed, known_affected, known_not_affected, under_investigation}`, a `cve`/`ids`/`notes` entry, for every `known_not_affected` product an impact statement as machine-readable `flags[]` or as a `threats[]` entry with `category: impact` and `details`, and for `known_affected` an action statement in `remediations[]`. Same rule as CISA's, but split across three arrays that all reference `product_ids`/`group_ids`.
- **Document-level lifecycle, not statement-level.** `tracking.status` is `draft`, `interim` or `final`; `tracking.version`; `revision_history[]` {`date`, `number`, `summary`, `legacy_version`}; `initial_release_date`, `current_release_date`. Red Hat's VEX is version 3, `final`, with 3 revision entries ("Last generated version"); Siemens SSA-661247 is version 21 with 21 entries. Statement-level time exists only as `flags[].date`, `remediations[].date`, `discovery_date`, `release_date`.
- **Attribution.** `document.publisher` {`category` (2.0: coordinator, discoverer, other, translator, user, vendor; 2.1 adds multiplier), `name`, `namespace`, `contact_details`/`contact`, `issuing_authority`}; `generator` {`engine`, `date`}; 2.1 `involvement` (an action timeline between entities) and `acknowledgments`. Signing is by detached OpenPGP file at distribution level, not in the JSON.
- **Supersession.** 2.0: only `revision_history` plus `tracking.status`. 2.1: Profiles 7 and 8: a withdrawn or superseded document must carry exactly one `notes` item titled "Reasoning for Withdrawal" or "Reasoning for Supersession", at least two `revision_history` items, and for supersession a `references` item with `category: external` whose `summary` starts with "Superseding Document" (profile text). The supersedes link is a typed reference with prose, so `txt`.
- **Scores are per product** (`products[]` on each `scores`/`metrics` item), so CSAF is the only format here that carries a different CVSS or EPSS value for different products in one statement set.
- **Weakness.** 2.0 has one `cwe` per vulnerability {`id`, `name`}; 2.1 has `cwes[]` {`id`, `name`, `version`}: a vulnerability may have several, tied to a catalog version. See 1.0 item 4.
- **Maturity risk.** CSAF 2.1 is a draft that changes names (`cwe` to `cwes`, `scores` to `metrics`, `purl` to `purls`, `relationships` to `product_paths`); an importer built against 2.0 will not read 2.1 unchanged.

Findings that bear on tmodel:

- **State vocabulary differs from the other three.** `analysis.state`: `resolved`, `resolved_with_pedigree`, `exploitable`, `in_triage`, `false_positive`, `not_affected`. `analysis.justification`: `code_not_present`, `code_not_reachable`, `requires_configuration`, `requires_dependency`, `requires_environment`, `protected_by_compiler`, `protected_at_runtime`, `protected_at_perimeter`, `protected_by_mitigating_control`. `analysis.response[]`: `can_not_fix`, `will_not_fix`, `update`, `rollback`, `workaround_available`. Nine justifications versus five elsewhere, and none is word-for-word the same; section 8 has the side-by-side.
- **Applicability is a second, independent list.** `affects[]` {`ref`, `versions[]` {`version` or `range` (a `vers` string), `status` (`affected`, `unaffected`, `unknown`)}}. So CycloneDX is the only VEX encoding that carries a version range with a status per range natively, but the state and the justification (`analysis`) sit on the vulnerability, not on the `affects` entry: one `analysis` covers every `affects[]` target. A statement with different states for different components must be split into separate `vulnerabilities[]` entries with the same `id`; the CISA-use-case examples in `CycloneDX/bom-examples` mark "Case 9: multiple product lines, multiple vulnerabilities, multiple statuses" as "Not Supported".
- **Attribution is thin.** `analysis` has `state`, `justification`, `response`, `detail`, `firstIssued`, `lastUpdated` and no author. The author is the BOM's `metadata.authors`/`tools` or the vulnerability's `tools` and `credits`; `source` is the *publisher of the vulnerability*, not of the analysis. BOM-level signing is a JSF `signature` property on the BOM root (enveloped signature).
- **Supersession is BOM versioning.** A new BOM with the same `serialNumber` and a higher `version`; `analysis.lastUpdated`. No statement-level supersedes edge.
- **Trivy's mapping of CDX state to a four-status model** (source `pkg/vex/cyclonedx.go`): `resolved` and `resolved_with_pedigree` to fixed; `exploitable` to affected; `in_triage` to under investigation; `false_positive` and `not_affected` to not affected; anything else to unknown. `false_positive` and `not_affected` are collapsed, though CDX treats the first as a scanner error and the second as a real non-impact.
- **Scoring is richer than the other VEX encodings.** `ratings[]` {`source`, `score`, `severity` (critical, high, medium, low, info, none, unknown), `method` (CVSSv2, CVSSv3, CVSSv31, CVSSv4, OWASP, SSVC, other), `vector`, `justification`}: the only place where the score carries its own source and a free-text justification.

Findings that bear on tmodel:

- **A VEX statement is an edge.** `from` is the `Vulnerability`; `to` is a list of products; the relation type is fixed per class (`affects`, `doesNotAffect`, `fixedIn`, `underInvestigationFor`; assessments use `hasAssessmentFor`; `hasAssociatedVulnerability` links a component to a vulnerability). This is the nearest of the four encodings to ARCH-0001's typed-edge model, with edge properties (`security_justificationType`, `suppliedBy`, `publishedTime`, `assessedElement`) on the edge itself. It is also the only one where a statement is a first-class, individually identified (`spdxId`) object.
- **Product vs. subcomponent is explicit.** `to` is the product (VEX sense); `security_assessedElement` is the subcomponent where the vulnerability is found (Core `SoftwareArtifact`). The example: product `urn:product-acme-application-1.3`, assessed element `urn:npm-elliptic-6.5.2`. Versions are whatever the element is; there is no range field in the Security profile.
- **Justification enum.** `VexJustificationType`: `componentNotPresent`, `inlineMitigationsAlreadyExist`, `vulnerableCodeCannotBeControlledByAdversary`, `vulnerableCodeNotInExecutePath`, `vulnerableCodeNotPresent`: the same five concepts as OpenVEX and CSAF in camelCase (read in the `.ttl`, 5 `NamedIndividual`s).
- **Inheritance and attribution.** If a VEX relationship lacks `createdBy`, tools "must consider the entity listed in the CreationInfo section of the document as the VEX author"; likewise the document date. `suppliedBy` is one `Agent` (max 1). Per-element `CreationInfo` carries `createdBy`, `created`, so SPDX 3 attributes every statement natively, with a `withdrawnTime` for retraction.
- **Withdrawal is a timestamp** (`withdrawnTime`), with no successor field; a replaced statement is a new relationship.
- **Other assessments ride the same pattern.** `SsvcDecisionType`: `act`, `attend`, `track`, `trackStar`; `ExploitCatalogType`: `kev`, `other`, with `exploited` boolean and `locator`; `CvssSeverityType`: `critical`, `high`, `medium`, `low`, `none`. The SSVC type carries only the final decision, not the decision points (see 1.11).
- **Real producer.** OpenEmbedded-Core's `sbom30.py` builds `security_Vulnerability`, `VexFixed…`, `VexAffected…` (with `security_actionStatement="Mitigation action unknown"`) and `VexNotAffected…` objects with `security_vexVersion="1.0.0"`, and `spdx30_tasks.py` rejects a justification not in `security_VexJustificationType.NAMED_INDIVIDUALS`. No standalone SPDX 3 VEX document from a vendor was found to read; the evidence for the schema reading is the spec examples and this code (a gap, section 12).

## 8. VEX cross-encoding comparison

Sources: OpenVEX 0.2.0 schema and spec; CSAF 2.0 errata 01 and 2.1 CSD03 schemas and Profile 5 text; CycloneDX 1.7 schema (`impactAnalysisState`, `impactAnalysisJustification`, `impactAnalysisResponse`, `affectedStatus`); SPDX 3.0.1 `.ttl` and class pages; baseline: CISA "Minimum Requirements for VEX" (2023) and "VEX Status Justifications" (June 2022).

### 8.1 Status values (dimension 3, question 1)

| Concept (CISA baseline) | OpenVEX 0.2.0 | CSAF 2.0 / 2.1 `product_status` | CycloneDX 1.7 `analysis.state` | SPDX 3.0.1 class (relationship type) |
|---|---|---|---|---|
| Not affected | `not_affected` | `known_not_affected` | `not_affected` (also `false_positive`, see below) | `VexNotAffectedVulnAssessmentRelationship` (`doesNotAffect`) |
| Affected | `affected` | `known_affected` (also `first_affected`, `last_affected`, `recommended`) | `exploitable` | `VexAffectedVulnAssessmentRelationship` (`affects`) |
| Fixed | `fixed` | `fixed` (also `first_fixed`) | `resolved`, `resolved_with_pedigree` | `VexFixedVulnAssessmentRelationship` (`fixedIn`) |
| Under investigation | `under_investigation` | `under_investigation` | `in_triage` | `VexUnderInvestigationVulnAssessmentRelationship` (`underInvestigationFor`) |
| (none in CISA baseline) | — | 2.1 `unknown` | `false_positive`; and per-version `affects[].versions[].status` `affected`/`unaffected`/`unknown` | — |

Findings: the four CISA statuses map one-to-one in OpenVEX, CSAF and SPDX (names differ in case and prefix: `known_` in CSAF, class name in SPDX). **CycloneDX does not agree**: its state names are different words (`exploitable`, `resolved`, `in_triage`), it has two extra values (`resolved_with_pedigree`, `false_positive`), and `affected` and `unaffected` live on a second field (`affects[].versions[].status`) that also has `unknown`. CSAF has finer-grained version-boundary statuses (`first_affected`, `last_affected`, `first_fixed`, `recommended`) that the others lack. A real consumer's mapping (Trivy, `cyclonedx.go`) is resolved and resolved_with_pedigree to fixed, exploitable to affected, in_triage to under investigation, false_positive and not_affected to not affected, everything else to unknown. CSAF 2.0 (mandatory test 6.1.6 "Contradicting Product Status") requires that the same product id is not a member of contradicting status groups, whose sets "MUST be pairwise disjoint" within one vulnerability.

### 8.2 Justification codes (dimension 3, question 1)

| CISA justification (June 2022) | OpenVEX `justification` | CSAF `flags[].label` | SPDX `VexJustificationType` | CycloneDX `analysis.justification` (nearest) |
|---|---|---|---|---|
| Component_not_present | `component_not_present` | `component_not_present` | `componentNotPresent` | `code_not_present` (nearest; CycloneDX does not distinguish component from code) |
| Vulnerable_code_not_present | `vulnerable_code_not_present` | `vulnerable_code_not_present` | `vulnerableCodeNotPresent` | `code_not_present` |
| Vulnerable_code_not_in_execute_path | `vulnerable_code_not_in_execute_path` | `vulnerable_code_not_in_execute_path` | `vulnerableCodeNotInExecutePath` | `code_not_reachable` |
| Vulnerable_code_cannot_be_controlled_by_adversary | `vulnerable_code_cannot_be_controlled_by_adversary` | `vulnerable_code_cannot_be_controlled_by_adversary` | `vulnerableCodeCannotBeControlledByAdversary` | no equivalent; closest is `protected_by_mitigating_control` (?, judgement) |

Findings: **OpenVEX, CSAF and SPDX agree exactly on the five CISA codes** (CSAF and OpenVEX spell them identically; SPDX is camelCase). All four enumerations were read from artifacts: OpenVEX schema `enum`, CSAF 2.0 and 2.1 schema `flags[].label` enum (identical in both versions), SPDX `.ttl` named individuals, CISA PDF text. **CycloneDX 1.7 has nine codes that do not match**: two CISA codes collapse into `code_not_present`, one has no equivalent, one fans out into four, and three CycloneDX codes (`requires_*`) express "affected only under a configuration, dependency or environment" which CISA's list does not provide. The mapping from CycloneDX to the CISA five is therefore lossy in both directions. The CycloneDX side of this table is my reading of the enum names (no CycloneDX document gives the mapping); the cell marked `?` is a judgement call. Note also that **the justification attaches differently**: OpenVEX per statement; CSAF per `flags[]` group (a label plus a list of `product_ids`/`group_ids`, not per statement); SPDX per relationship; CycloneDX per vulnerability entry (shared by all of its `affects[]`).

### 8.5 How a VEX statement maps onto per-instance applicability (dimension 3, question 4)

Evidence only. tmodel's LinkML draft (`Assertion` plus `Review`) was not re-read here; I rely on the pilot's description (a multi-source assertion with a human review) and on ARCH-0001 §3 and §7.

- **A VEX statement is the (vulnerability, product, status, justification, author, time) tuple.** All four encodings carry all six, but only SPDX 3 and OpenVEX make the tuple a single object; in CSAF it is spread over `product_status`, `flags`, `threats`, `remediations` and `document.tracking` (join by `product_id`); in CycloneDX over `vulnerabilities[]`, `analysis` and `affects[]`.
- **Fit with `applies_to_product`.** `applies_to_product` as a bare edge loses the status (`not_affected`, `fixed`, `under_investigation`) and the justification. All four VEX encodings treat the status as the edge type or an edge property: SPDX makes the relationship class carry it (`doesNotAffect`, `affects`, `fixedIn`, `underInvestigationFor`), which is the closest to ARCH-0001's typed edges.
- **Fit with Assertion plus Review.** The VEX tuple is an Assertion (who claimed it, when, on what evidence: `impact_statement`, `analysis.detail`). None of the four has a Review: a different party's accept/reject of the claim, with reviewer and date, has no field. Closest: CSAF `tracking.status` (document) and CSAF 2.1 `involvement`; SPDX `withdrawnTime`; OpenVEX 1.0's planned "multi-stakeholder approval" (roadmap, not in 0.2.0). A tmodel `Review` must therefore reference an imported statement by an id that two of the four encodings (OpenVEX, CycloneDX) do not require, and CSAF does not provide per statement.
- **Per-instance applicability needs a version model the VEX formats mostly lack.** For "is CVE X applicable to product version Y": OSV `ranges`/`IsVulnerable` or CVE `versions[]` give the vulnerable range; VEX then overrides it for a given product with `not_affected` and a justification. In real data the VEX side is large: Red Hat's CSAF for CVE-2021-44228 lists 2,254 products as `known_not_affected`, 122 as `fixed` and 4 as `known_affected`.
- **Four statuses are the stable core, the justification list is the unstable part.** The five CISA codes are common to three encodings; CycloneDX's nine do not map cleanly (8.2). If tmodel adopts the CISA five as its own vocabulary, CycloneDX import loses information (the three `requires_*` codes and four-way mitigation detail).
