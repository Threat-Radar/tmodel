# RPT-0004 fan-out, agent 5: dimensions 3 and 4 (tools and radar)

Scope: dimension 3 (Syft, Grype, Trivy, Dependency-Track, GUAC, deps.dev) and dimension 4 (how radar, the `tradar` repository, uses them), and Table 5. Everything below was checked on 2026-10-08. Release data came from the GitHub API (`gh api`), documents were fetched with `curl` and read from their own text, schema and source files were parsed with `python3` and `jq`, and the three command-line tools were run on four inputs. No fetch-tool summary is used as evidence; WebSearch worked (no quota problem) and its summaries were used only to find things, then checked at the source (section 9 lists two search claims that did not hold).

Abbreviations used throughout: SBOM (software bill of materials), purl (package URL), CPE (Common Platform Enumeration, the naming scheme the NVD uses), NVD (US National Vulnerability Database), CVE (Common Vulnerabilities and Exposures id), CWE (Common Weakness Enumeration id), GHSA (GitHub Security Advisory), OSV (Open Source Vulnerabilities format and database), VEX (Vulnerability Exploitability eXchange), CSAF (Common Security Advisory Framework), KEV (Known Exploited Vulnerabilities catalog), EPSS (Exploit Prediction Scoring System), VDR (Vulnerability Disclosure Report), OCI (Open Container Initiative), SLSA (Supply-chain Levels for Software Artifacts), API (application programming interface), DB (database), DT (Dependency-Track), GUAC (Graph for Understanding Artifact Composition).

Files and caches live in the agent 5 scratch folder (`scratchpad/fanout/agent5/`): `bin/` (downloaded tool releases), `cache/` (separate Grype and Trivy databases), `inputs/` (the log4j jar), `runs/` (all tool outputs), `docs/`, `dtrack/`, `guac/`, `depsdev/`, `releases/`, `tradar/` (fetched sources). Digests: `runs-sha256.txt` (54 outputs) and `sources-sha256.txt` (139 fetched files).

Findings:

- **Syft writes and reads SPDX 3, and has since v1.46.0.** The help text only shows SPDX 2.x examples ("`syft scan alpine:latest -o spdx-json` show a SPDX 2.3 JSON formatted SBOM"), but an unknown format name makes both 1.52.0 and 1.54.1 print the full list, identical in both: "`spdx-json @ 2.2, 2.3, 3.0`", "`spdx-tag-value @ 2.1, 2.2, 2.3`", "`cyclonedx-json @ 1.2, 1.3, 1.4, 1.5, 1.6, 1.7`", "`cyclonedx-xml @ 1.0, 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 1.7`" (`docs/help/syft-1.54.1-formats-error.txt`, `7f857290…adde5`). `-o spdx-json@3.0` writes a document whose `@context` is `https://spdx.org/rdf/3.0.1/spdx-context.jsonld` and whose `CreationInfo.specVersion` is `"3.0.1"`. The release note of v1.46.0 (2026-06-26) reads "SPDX 3 Support [Issue #4250] [PR #4269 @kzantow]" (Markdown links removed), and PR #4269 (merged 2026-06-22) says: "reading SPDX 3 uses a custom decoder, implemented here, as the tools-golang does not have a backwards conversion to 2.3 at this time" and "writing SPDX 3 just uses the tools-golang conversion from our existing 2.3 populated model". In the source, `DefaultVersion = "2.3"` and `V3_0 = "3.0"`, with the comment "is JSON, v3 only supported in JSON format" (`versions.go:7-30`); the JSON decoder branches with `if strings.HasPrefix(version, "3") { return decodeSpdx3(version, reader) }` (`spdxjson/decoder.go:47-49`). Syft 1.54.1 builds against `github.com/spdx/tools-golang v0.6.0-rc4` (`go.mod:82`), a release flagged as pre-release on GitHub (2026-06-18) whose notes say "This is _hopefully_ the last RC before initial SPDX 3.0 support is merged". This contradicts 0.1.0 §3 (section 9).
- **The SPDX 3 output is valid against the published JSON Schema but uses only the 2.3 feature set.** All four SPDX 3 outputs validate with 0 errors against `spdx.org/schema/3.0.1/spdx-json-schema.json` (SHA-256 `582c64e809d5b3ef9bd0c4de13a32391b47b0284a3e8d199569fb96f649234b1`, the same file RPT-0005 pinned; validator `jsonschema` 4.25.0, draft 2020-12). In all four, `completeness` is unset on every relationship (235 of 235 for alpine), `software_sbomType` is absent, `profileConformance` is `["core", "software"]`, and there is no `LifecycleScopedRelationship`, `Build` or security element. Our reading: this follows from the PR's "conversion from our existing 2.3 populated model". SHACL validation was not run (section 10).
- **The same scan carries different data in each format.** On `alpine:latest` (Syft 1.54.1): the CycloneDX file has 16 `library` components, 1 `operating-system` component and 78 files; the SPDX 2.3 file has 17 packages (16 apk packages plus the image itself as a package) and no operating-system package. Only SPDX gives the image root a SHA256 checksum (equal to the manifest digest) and the purl `pkg:oci/alpine@sha256%3A260479a1…?arch=arm64&tag=latest`; the CycloneDX root has the digest only as its `version` string (next finding). Package suppliers appear only in SPDX (13 of 16 apk packages, written as `Person:` followed by the maintainer's name and email address, not reproduced here); CycloneDX has no `supplier` but fills `publisher` (16 of 16) with the same apk maintainer string. Package hashes: none in CycloneDX; in SPDX 2.3 a `packageVerificationCode` on 16 packages plus the root checksum; in SPDX 3 a `verifiedUsing` on 17 packages (16 `PackageVerificationCode` with `sha1`, 1 `Hash` with `sha256`). CPEs: CycloneDX puts 1 per package in `cpe` and 65 more in `syft:cpe23` properties; both SPDX versions carry all 81 as `cpe23Type` (2.3) or `cpe23` `externalIdentifier` (3). The dependency edges are the same 24 (dependent, dependency) pairs in all three files; SPDX 2.3 writes them in the reverse direction as `DEPENDENCY_OF` (checked with a script that keys both ends by purl, `runs/edges.py`).
- **Supplier coverage in SPDX depends on the shape of the maintainer's e-mail address.** Syft sets an SPDX supplier only when the maintainer string matches `^(?P<name>[^<>()]*)( <(?P<email>[^@]+@\w+\.\w+)>)?( \((?P<url>.*)\))?$` (`originator_supplier.go:203`); an address whose domain has a hyphen or more than one dot (for example one Alpine maintainer's personal address, not reproduced here, or `deity@lists.debian.org`, the APT team's mailing list) fails, and the package gets `NOASSERTION`. Applying that pattern to the maintainer field in Syft JSON predicts the SPDX supplier presence for 16 of 16 Alpine and 88 of 88 Debian packages (our test, `python3`). Result: 13 of 16 Alpine and 48 of 88 Debian packages get a supplier.
- **For a tagged image, the CycloneDX root carries the tag, not the digest.** `debian:12-slim` gives `metadata.component` = `{type: container, name: debian, version: 12-slim}` with no purl or hash, while the SPDX 2.3 root of the same scan has the SHA256 checksum `a1b86db5…be82a` and purl `pkg:oci/debian@sha256%3Aa1b86db5…?arch=arm64&tag=12-slim`. For `alpine:latest` the CycloneDX version is the digest. The source explains it: `versionIfUnset` keeps a version unless it is empty or `"latest"`, and tries the tag, then the digest in the reference, then the manifest digest (`image_source.go:61-87`).
- **Element ids: the CycloneDX `bom-ref` is stable across runs, the SPDX 3 `spdxId` is not.** Two scans of the same image 22 minutes apart (same Syft version) gave different CycloneDX `serialNumber`s (expected) but the same zlib `bom-ref`, `pkg:apk/alpine/zlib@1.3.2-r0?arch=aarch64&distro=alpine-3.24.2&package-id=7e5e1d854f96ea7f`. In SPDX 3 the local part `Package-apk-zlib-7e5e1d854f96ea7f` repeats, but the document namespace (`namespaceMap`) contains a random UUID per run (`https://anchore.com/syft/image/alpine-0420eb59-…#` and `…alpine-aaca9706-…#`), so the full `spdxId` IRI of the same package differs between scans.
- **Placeholder hashes.** For four tradar requirement files that Syft saw but did not digest (`requirements.txt`, `requirements-ai.txt`, `requirements-dev.txt`, `docker/requirements-ai-docker.txt`), both SPDX outputs carry a SHA-1 of forty zeros (`"checksumValue":"0000000000000000000000000000000000000000"`; SPDX 3 `hashValue` the same), and the CycloneDX output leaves the four files out.
- **Lockfile hashes are dropped.** tradar's `uv.lock` has 781 `hash = "sha256:…"` entries; none of Syft's 65 `python-uv-lock-entry` packages carries a hash or digest field (Syft JSON metadata keeps `index` and `dependencies` only).
- **No hardware or firmware cataloger.** `syft cataloger list -o json` lists 71 cataloger names; none contains `firm`, `uefi`, `bios`, `device` or `hardware` (the binary and kernel ones are `binary-classifier-cataloger`, `elf-binary-package-cataloger`, `pe-binary-package-cataloger`, `go-module-binary-cataloger`, `cargo-auditable-binary-cataloger`, `dotnet-deps-binary-cataloger`, `linux-kernel-cataloger`).
- **Version change since 0.1.0 does not change composition facts.** On `alpine:latest` (same manifest digest `sha256:260479a1cfaf304c4c20da7f8405d3ce313513dcd534bb743257bdd2fe0f3e2d` as 0.1.0 and the pilot), every CycloneDX count we computed (component types, purl, CPE field and properties, package hashes, supplier, publisher, licences, files and file hashes, dependency entries and edges) is identical between Syft 1.52.0 (pilot `alpine.cdx.json`) and 1.54.1. On tradar, 1.54.1 reproduces 0.1.0's 76 packages, 996 CPE candidates (10 `nvd-cpe-dictionary`, 986 `syft-generated`) and 104 edges.

Findings:

- **How each match was made is recorded per match.** Every match has `matchDetails[]` with `type` (`exact-direct-match`, `exact-indirect-match`, `cpe-match`), `matcher`, `searchedBy` and `found` (`vulnerabilityID`, `versionConstraint`), plus `vulnerability.namespace`, `fix.state`, `epss` (on all 30 alpine matches) and `knownExploited` when a CVE is in a KEV catalog (2 of 7 log4j matches; absent on alpine). The document records the DB: `descriptor.db.status` = `{schemaVersion: v6.1.10, from: …, built: 2026-10-08T06:33:47Z, valid: true}` and `descriptor.db.providers` with a `captured` time and an `input` digest for each of 26 providers: alma, alpine, amazon, arch, bitnami, chainguard, chainguard-libraries, debian, echo, eol, epss, fedora, github, govulndb, hummingbird, kev, mariner, minimos, nvd, oracle, photon, rhel, secureos, sles, ubuntu, wolfi.
- **CWEs are in the JSON report, not in Grype's CycloneDX report.** JSON matches carry `vulnerability.cwes[]` = `{cve, cwe, source, type}` with `type` `Primary` or `Secondary` (30 of 30 alpine matches, 208 of 229 Debian, 17 of 17 tradar, 7 of 7 log4j). Grype's CycloneDX output of the same runs has 0 `cwes` entries (30, 229, 17 and 7 vulnerabilities checked). One Debian value is the NVD placeholder `NVD-CWE-Other`, which CycloneDX's integer `cwes` field cannot hold.
- **Grype reads SPDX 3 input through Syft's decoders.** `grype sbom:<file>` gave the same matches from Syft's SPDX 3 file as from its CycloneDX file for alpine (30), Debian (229) and log4j (7); the installed Grype 0.119.0 also read the alpine SPDX 3 file (30 matches, same DB). For tradar it gave 15 matches from either SPDX file instead of 17 from CycloneDX: the 2 lost matches are GHSA-8q5r-mmjf-575q (CVE-2026-47751) on `anthropics/claude-code-action@v1` in two workflow files, found by `stock-matcher` in namespace `github:language:github-action`. `syft convert` of either SPDX file returns the 9 GitHub Actions as type `UnknownPackage` (purl `pkg:github/…` kept), while the CycloneDX file round-trips them as `github-action` through the `syft:package:type` property. Our reading: the package type does not survive Syft's SPDX encoding, so Grype does not route those packages to the GitHub Actions namespace.
- **A configuration key was a silent no-op in 0.119.0.** Issue #3746: "Setting `match.dpkg.using-cpes: true` (or `GRYPE_MATCH_DPKG_USING_CPES=true`) does not change matching." PR #3747 (merged 2026-09-30, in 0.120.0) wires it in and states "The default stays `false`, so default matching does not change." The 0.120.0 notes also list "`match.rpm.using-cpes` has no effect [Issue #3752] [PR #3753]". So 0.1.0's reading of `grype config` ("off by default for Debian and RPM") holds for the default, but in 0.119.0 the setting could not be turned on.
- **VEX input formats.** `--vex` takes "a list of VEX documents to consider when producing scanning results" (`grype --help`); the processor accepts CSAF (`csaf.IsCSAF`) and OpenVEX (`openvex.IsOpenVex`) and otherwise fails with "unsupported VEX document format" (`vex/processor.go:49-56`). Ignore rules can carry `vex-status`, `vex-justification` and "`reason`: optional human-readable note recorded on the ignored match (does not affect matching)" (`grype config` output, lines 71-90).
- **Grype rebuilds the scan source from the SBOM root.** Scanning Syft's CycloneDX file of `debian:12-slim` gives `source.target` = `{userInput: "debian", manifestDigest: "12-slim"}`: the tag lands in a field named `manifestDigest`. For alpine the same field holds the real digest and `imageID` holds the CycloneDX `bom-ref` (`caf3142caa4aa41f`). This matters for radar (section 1.7, claim C19).
- **Inputs and outputs (help text).** Inputs include `sbom:path`, `purl:path`, a single purl and a single CPE; outputs `json table cyclonedx cyclonedx-json sarif template` (deprecated `embedded-cyclonedx-vex-json embedded-cyclonedx-vex-xml`); `--by-cve` re-orients results by CVE.

Findings:

- **Trivy does not read or write SPDX 3.** Fed Syft's SPDX 3 file, Trivy 0.75.0 logs `Detected SBOM format format="unknown"` and stops with `FATAL … SBOM decode error: unknown scanning is not yet supported`. In the source, SPDX JSON is recognised only when the top-level `SPDXID` is `"SPDXRef-DOCUMENT"` (`pkg/sbom/sbom.go:105-117`), the SPDX code imports `github.com/spdx/tools-golang/spdx/v2/common`, the writer sets `SPDXVersion: spdx.Version` (`marshal.go:235`; our output says `SPDX-2.3`), and the module pins `github.com/spdx/tools-golang v0.5.7` (`go.mod:101`). Discussion #8498 "SPDX 3?" (Ideas, opened 2025-03-05, no accepted answer on 2026-10-08): a Trivy contributor (GitHub association CONTRIBUTOR) replied on 2025-03-06 "We prefer to use SPDX Golang Tools, because we can more accurately manipulate and set fields for the SPDX. They already work on SPDX 3 … We are waiting for these changes." (link markup removed; the elided part is a link to tools-golang PR #247).
- **Trivy also loses OS packages from a Syft SPDX 2.3 file.** On Syft's SPDX 2.3 file of alpine, Trivy logs `Detected OS family="none" version=""` and `WARN Unsupported os family="none"` and reports nothing; on the CycloneDX file of the same scan it detects Alpine 3.24.2 and 16 packages. Discussion #11140 (opened 2026-08-25) reports the same on a Debian-based image, and the reply by a Trivy contributor (GitHub association CONTRIBUTOR, 2026-08-27) gives the cause: "Trivy finds the operating system in SPDX only by the `SPDXRef-OperatingSystem-` prefix of a package entry, and only Trivy's own SPDX output creates such an entry." The Syft change that would add such an entry, PR #3462, has been open since 2024-11-18.
- **On Debian, Trivy finds 31 of its own 235 findings (13%) when it reads Syft's CycloneDX.** `trivy image debian:12-slim`: 235 findings, 106 ids (102 CVE, 4 Debian `TEMP-` ids). `trivy sbom` on Syft's CycloneDX of the same image: 31 findings on 10 packages, all among the image result. Trivy's own scan records a source package name different from the binary name (`SrcName`) for 62 of 88 packages (for example `libgnutls30` → `gnutls28`); reading Syft's file, `SrcName` equals the binary name for 88 of 88, although Syft's purl carries `upstream=gnutls28` and a `syft:metadata:source` property. Discussion #11139 (nginx:1.25, 409 versus 137 CVEs) describes the same mechanism: "Trivy reads `aquasecurity:trivy:SrcName` from CycloneDX properties, Syft writes the source package into the PURL `upstream=` qualifier instead, and without the property `SrcName` falls back to the binary package name." (statement of the discussion's author, citing an earlier maintainer explanation; our run confirms the effect).
- **Trivy's own SBOMs are richer than Syft's in two fields.** Trivy's CycloneDX 1.7 output for alpine has `hashes` on 16 of 16 packages (SHA-1) and `supplier` on 16 of 16; Syft's CycloneDX has neither. The zlib SHA-1 `a9e1bc32bb315bfdac6224f92785e4d9a334bf29` equals the base64-decoded apk `pullChecksum` that Syft keeps only in Syft JSON (`Q1qeG8MrsxW/2sYiT5J4Xk2aM0vyk=`); which bytes it covers is agent 2's question. Trivy's SPDX 2.3 output names maintainers as `Organization:`, even when the maintainer is a person (a name and email address, not reproduced here).
- **purl strings differ between Trivy and Syft for the same installed package.** Alpine: 0 of 16 full purl strings are identical, 16 of 16 agree before `?` (Syft `distro=alpine-3.24.2`, Trivy `distro=3.24.2`). Debian: 22 of 88 identical, 77 of 88 agree before `?`; the other 11 all differ by epoch encoding (Syft `pkg:deb/debian/zlib1g@1%3A1.2.13.dfsg-1?…&upstream=zlib`, Trivy `pkg:deb/debian/zlib1g@1.2.13.dfsg-1?…&epoch=1`).
- **Formats and data sources (help text).** Output formats: `table json template sarif cyclonedx spdx spdx-json github cosign-vuln`. Scanning commands: `config filesystem image kubernetes repository rootfs sbom vm`. `--vuln-severity-source` lists 35 values (34 sources and `auto`): nvd, redhat, redhat-oval, debian, ubuntu, alpine, amazon, oracle-oval, suse-cvrf, photon, arch-linux, alma, rocky, cbl-mariner, azure, ruby-advisory-db, php-security-advisories, nodejs-security-wg, ghsa, glad, aqua, osv, k8s, wolfi, chainguard, bitnami, govulndb, julia, bottlerocket, echo, echo-osv, minimos, rootio, rapidfort, auto. Each finding carries `DataSource` = `{ID, Name, URL}`, `CweIDs`, `Status`, and in CycloneDX output `vulnerabilities[].cwes` as integers (`[787]` for zlib).
- **VEX.** "Currently, Trivy supports the following formats: CycloneDX, OpenVEX, CSAF" and, for CycloneDX, "Trivy only supports the Independent BOM and VEX BOM format, so you need to provide a separate VEX file alongside the SBOM" (`vex/file.md:8-12, 29`); `--vex` also accepts `"repo"` and `"oci"` sources.
- **Warnings on third-party SBOMs.** Both 0.74.0 and 0.75.0 log `Third-party SBOM may lead to inaccurate vulnerability detection` and `Recommend using Trivy to generate SBOMs` on Syft's files.

Findings:

- **Formats.** "CycloneDX is the only format supported for uploading SBOMs to Dependency-Track." and "All versions of the CycloneDX BOM specification are supported for upload." (Reference, File Formats). Exports: a BOM "with its services and dependency graph", a BOM with vulnerabilities, a VDR, and a VEX, all CycloneDX, plus the Dependency-Track-native Finding Packaging Format. 5.1.0 added "CycloneDX 1.7 support" (PR #6703). In the 5.2.0 tree, every path that contains `spdx` (20 paths) belongs to licence-expression or licence-list handling (`parser/spdx/expression/*`, `parser/spdx/json/SpdxLicenseDetailParser.java`, validators); there is no SPDX document parser. The test `uploadNonCycloneDxBomTest` uploads SPDX 2.2 tag-value and expects HTTP 400 "BOM is neither valid JSON nor XML" (`BomResourceTest.java:1307-1328`).
- **SPDX 3: still an open issue, on hold.** Issue #1746 "Add support for SPDX v3": open, labels `enhancement, help wanted, on hold, p2`, last updated 2026-02-19. Its proposal is "an optional and automatic translation layer that converts SPDX into CycloneDX for ingestion into DT". On 2025-08-10 a member of the DependencyTrack organization (GitHub association MEMBER) wrote "4.14 is the last planned minor release of v4 … All new functionality is being implemented in v5".
- **What changed in v5 that touches composition data** (Concepts, "About changes in v5", `001782676…dc962`): "v5 commits to PostgreSQL and drops H2, MySQL, and Microsoft SQL Server"; search runs in PostgreSQL and "Lucene's fuzzy matching disappears with it"; "Fuzzy vulnerability analysis. v4's internal analyzer optionally fell back to Lucene-based fuzzy matching against the internal vulnerability database when a component lacked a CPE. Dropping Lucene removes this capability."; new "Component integrity verification": "Dependency-Track flags components whose hashes diverge from what the upstream package repository publishes"; REST API v1 changes ("Few endpoints removed, response schemas change, and list endpoints enforce pagination by default"); and "REST API v2 is new in v5" (Reference, Breaking changes in v5). The v2 OpenAPI sources at 5.2.0 cover `components`, `projects`, `vulns`, `vuln-data-sources`, `kev-data-sources`, `vuln-policies`, `extensions` and others (`api/src/main/openapi/resources/`); their contents were not examined.
- **5.1 and 5.2 composition-relevant changes** (release notes): 5.1.0 "Add CycloneDX 1.7 support" (#6703), "Implement initial KEV support" (#6516), "Add VulnCheck KEV data source" (#7027), "Add JVN (Japan Vulnerability Notes) vulnerability data source" (#6640), "Add Checkmarx SCA vulnerability analyser" (#6804), "Add component scope evaluation policy" (#6853), "Align VEX semantics with CISA guidance and tooling ecosystem" (#7076); upgrade note: "Dependency-Track mirrors KEV catalogs by default … the CISA and ENISA Known Exploited Vulnerabilities catalogs daily at 02:00 UTC". 5.2.0 "Add checksum matching support for Snyk vuln analyzer" (#6835: "opt-in Snyk checksum-qualified PURL matching for Maven components"), "Fix N+1 queries in dependency graph endpoint" (#7275), "PEP 503-normalize PyPI package names for vuln matching" (#7546), "Add `analyzer_identity` in `NEW_VULNERABILITY` notifications" (#7206), "Enforce a max size for BOM and VEX uploads" (#7545; 100 MiB default per the 5.2.0 upgrade notes).
- **Data model.** A component has one `cpe` (validated as CPE 2.2 or 2.3), one `purl` (up to 1,024 characters), a `swidTagId`, one field per hash algorithm (`md5` to `streebog_512` and `blake3`), `supplier`, `authors`, `publisher`, `scope`, `classifier`, `directDependencies` stored as a JSON string, `parent`/`children`, and a required `project` (`Component.java:121-182` for authors to classifier, `208-318` hashes, `331` cpe, `341` purl, `361` swidTagId, `423` directDependencies, `438-442` parent and children, `478` project). Classifiers include `DEVICE`, `FIRMWARE`, `DEVICE_DRIVER`, `MACHINE_LEARNING_MODEL`, `DATA`, `CRYPTOGRAPHIC_ASSET` (`Classifier.java:27-41`). Projects: "A name and version together identify a project globally"; "Versions are opaque strings"; "Projects cannot depend on projects. … If service A consumes service B, that fact is not expressible as a project relation." (Concepts, About projects).
- **Matching needs a CPE for NVD and a purl for GHSA and OSV.** "A component with neither a CPE nor a PURL is not evaluated." and "Most modern BOM generators emit PURLs but not CPEs. As a result, components from package ecosystems … produce few or no findings from NVD data" (About vulnerability data sources). For deb and rpm purls "an epoch qualifier is folded into the version as epoch:version before comparison". Analyzers: internal ("Uses both CPE and PURL matching"), OSS Index, Snyk and Trivy (each "Uses PURL matching"), VulnDB ("Uses CPE matching") (Reference, Analyzers). Our reading: with one `cpe` per component, a Syft CycloneDX file contributes only its first CPE candidate (for log4j-core that is `cpe:2.3:a:apache:log4j-core:…`, while the other candidates sit in `syft:cpe23` properties).
- **Provenance and review are first-class.** "For each attribution, the finding stores the analyzer identity, the date the analyzer attributed the finding … and a reference URL the analyzer supplied." Analysis state, justification, vendor response and details form the triage decision, and "The history records who made the change, when, and what changed, and it includes the free-form comments reviewers add as they work." (Concepts, About vulnerability findings).
- **Identity does not survive export.** "The references inside an exported document are Dependency-Track's own component identifiers. … They are not the identifiers from any BOM you uploaded." and "A statement reaches a finding on the strength of the vulnerability ID." (Concepts, About VEX).
- **Integrity verification covers few ecosystems.** "Verification covers four hash algorithms: MD5, SHA-1, SHA-256, and SHA-512", with upstream hashes for Maven (SHA-1), npm (SHA-1, SHA-512) and PyPI (MD5, SHA-256; the purl needs a `file_name` qualifier). Our reading: Syft's CycloneDX files in our runs carry no package hashes, so this check has nothing to compare for them.
- **v4 support.** "v4 will reach end-of-life in December 2026, *~6 months* after v5 GA." (`README.md:31` at 5.2.0).

Findings:

- **Nodes ("nouns") and evidence ("verbs").** The `Node` union has 23 members (`path.graphql:27-50`): 6 noun types (`Package`, `Source`, `Artifact`, `Builder`, `Vulnerability`, `License`) and 17 evidence types (`IsOccurrence`, `IsDependency`, `VulnEqual`, `CertifyVEXStatement`, `HashEqual`, `CertifyBad`, `CertifyGood`, `PkgEqual`, `CertifyScorecard`, `CertifyVuln`, `HasSourceAt`, `HasSBOM`, `HasSLSA`, `HasMetadata`, `PointOfContact`, `VulnerabilityMetadata`, `CertifyLegal`). The schema calls the latter "GUAC evidence trees (GUAC verbs)" (`path.graphql:191-192`). The `Edge` enum has 86 values, and "Edges are defined in both directions, which means nodes can be traversed from either direction" (`path.graphql:52-64`); `path(subject, target, maxPathLength, usingOnly)` and `neighbors(node, usingOnly)` are the graph queries.
- **How things are identified.** Package: "We map package information to a trie, closely matching the pURL specification … but deviating from it where GUAC heuristics allow for better representation of package information", with levels type, namespace, name, version (`PackageVersion` = `purl`, `version`, `qualifiers`, `subpath`), and "Two nodes that have different qualifiers and/or subpath but the same version mean two different packages in the trie (they are different)." (`package.graphql:20-101`). Artifact: "Artifact represents an artifact identified by a checksum hash." with `algorithm` and `digest`: "Both fields are mandatory and canonicalized to be lowercase." (`artifact.graphql:20-33`). Source: type, namespace and name, where "The tag and commit fields are optional, but it is an error to specify both" (`source.graphql:20-65`). Vulnerability: a type and an id, both lowercase, with a special `novuln` type "to attest that no vulnerability has been found during a vulnerability scan" (`vulnerability.graphql:20-52`).
- **Equality is asserted, not inferred.** "PkgEqual is an attestation that two packages are similar.", "HashEqual is an attestation that two artifacts are identical.", "VulnEqual is an attestation to link two vulnerabilities together as being equal" (`pkgEqual.graphql:20`, `hashEqual.graphql:20`, `vulnEqual.graphql:20-24`). A hash is linked to a package only by an `IsOccurrence` attestation, by design: "It was decided that mapping to hashes as leaf nodes should not be part of the software tree … This is due to the fact that saying a package has an occurrence of an artifact with hash is an opinion, and software trees need to remain factual." (`guac-ontology-definition.md`).
- **Provenance of each fact.** All 17 evidence types carry `origin` ("Document from which this attestation is generated from"), `collector` ("GUAC collector for the document") and `documentRef` ("Reference location of the document in the persistent blob store (if that is configured)"); 11 of 17 carry `justification`; 12 of 17 carry a time (`knownSince`, `timeScanned`, `timestamp`, `since`, `startedOn`/`finishedOn`); `IsOccurrence`, `IsDependency`, `VulnEqual`, `HashEqual` and `PkgEqual` have no time field (script over the schema). `CertifyVuln.metadata` adds `timeScanned`, `dbUri`, `dbVersion`, `scannerUri`, `scannerVersion` (`certifyVuln.graphql:37-59`).
- **How documents about the same thing merge.** In the keyvalue backend, nouns are looked up by a key before they are created: package type by type, namespace by parent and namespace, name by parent and name, version by parent and `version,subpath,sorted qualifiers` (`pkg.go:314-352, 509-519`), artifact by `algorithm:digest` (`artifact.go:124-126`). Evidence keys include the provenance: `IsDependency` is keyed on package, dependency package, dependency type, justification, origin, collector and documentRef (`isDependency.go:46-56`), and the ent backend has the same unique index (`ent/schema/dependency.go:74-80`). Our reading: two documents that name the same purl converge on one package node, while the same dependency claimed by two documents stays two evidence nodes. Combined with section 1.3, a Syft SBOM and a Trivy SBOM of one Alpine image would create different `PackageVersion` nodes, because their `distro` qualifiers differ.
- **The "actor tree" is not implemented.** The ontology page describes three trees (software, evidence, actor), but the definition page is headed "GUAC Actor Tree (Not in v0.1 BETA)", and the v1.1.0 schema has no identity or trust node type (`Builder`, a URI, is the only actor-like noun).
- **Readers.** README "Supported input documents": CycloneDX, DSSE, deps.dev API, in-toto ITE6, OpenSSF Scorecard, OSV, SLSA, SPDX, CSAF/CSAF VEX, OpenVEX. The CycloneDX parser never reads CPEs (0 occurrences of `cpe` in `parser_cyclonedx.go`), skips components of type `operating-system` ("Currently there is no use-case to capture OS for GUAC", lines 223-229), mints a GUAC purl for components without one, and maps CycloneDX VEX states with `resolved`→FIXED, `exploitable`→AFFECTED, `in_triage`→UNDER_INVESTIGATION, `not_affected`→NOT_AFFECTED, `resolved_with_pedigree`→FIXED, `false_positive`→NOT_AFFECTED (lines 42-49; v1.1.0 notes: "fix: Missing VEX status mappings for resolved_with_pedigree and false_positive (#2813)"). The SPDX parser stores security external references as `HasMetadata` with key `cpe`, `Origin: "GUAC SPDX"` (`parse_spdx.go:405-416`, main).
- **SPDX 3 has not landed.** The SPDX parser on `main` imports `github.com/spdx/tools-golang/spdx/v2/common` (`parse_spdx.go:34`) and `go.mod` pins `tools-golang v0.5.7`. Issue #1850 "[feature] Add SPDX 3.0 support": open, labels `enhancement, help wanted, long-term`; the `help wanted` label was added on 2026-10-06; the last comment is from 2024-12-18; a contributor (GitHub association CONTRIBUTOR) wrote on 2024-04-22 "This will depend on https://github.com/spdx/tools-golang's support for spdx 3.0 parsing".
- **Storage backends.** Directories under `pkg/assembler/backends` at v1.1.0 and `main`: `arangodb ent helper keyvalue neo4j neptune`. README: keyvalue "(supported, complete, optimized)", "a non-persistent in-memory backend"; ent "(supported, complete optimized)" with PostgreSQL ("GUAC only supports ent with PostgreSQL"); arangoDB "(unsupported, incomplete, optimized)"; neo4j/openCypher "(unsupported, incomplete)"; keyvalue on Redis and on TiKV "(experimental, complete)". `neptune` is a wrapper that obtains an AWS token and calls the neo4j backend (`neptune.go:95-116`). The CLI default is keyvalue: `set.String("gql-backend", "keyvalue", "backend used for graphql api server: [keyvalue | arango (experimental) | ent (experimental) | neo4j (unmaintained)]")` (`store.go:50`); the flag text calls ent "experimental" while the README calls it supported.

**Q2. deps.dev.** It holds package versions, requirements, resolved dependency graphs (npm, Cargo, Maven, PyPI in the API; Go too in BigQuery), licences, OSV advisories, OpenSSF Scorecard results and OSS-Fuzz data for projects, and SLSA and PyPI attestations, through API v3 and v3alpha (HTTP and gRPC) and the BigQuery dataset `bigquery-public-data.deps_dev_v1`. Its graphs are generic resolutions, so they do not describe a given product's locked composition (0 of 4 versions matched tradar's lock).

**Q3. GUAC's graph model.** 6 noun types and 17 evidence types (23 node types), 86 `Edge` enum values (each link is named in both directions), purl-trie packages, digest artifacts, VCS sources, and `PkgEqual`, `HashEqual` and `VulnEqual` attestations for equality.
