# RPT-0004 fan-out, agent 3: dimension 5 (the bridge)

Scope: dimension 5 of [dimensions.md](dimensions.md) (read at version 0.2.0 for the brief and 0.3.0 at the end of the run). It asks how a component in a software bill of materials (SBOM) is matched to a vulnerability (a CVE, Common Vulnerabilities and Exposures, record) and to a weakness (a CWE, Common Weakness Enumeration, entry), what scanners record about each match, how affected versions are written, and how often matching methods disagree. Evidence only; nothing here decides anything.

**Date of checks:** 2026-10-08. **Method:** every URL was fetched with `curl` or the GitHub API (`gh api`) and read from its own text; schemas, data feeds and tool outputs were parsed with `jq` and `python3`. Downloads sit in the agent's scratch folder (`fanout/agent3/files` and `fanout/agent3/big`), with SHA-256 values in sections 1 and 8. No fetch tool summary is relied on. WebSearch worked for eight queries and then stopped with a session limit (section 7); the rest was done by fetching known URLs and the arXiv, Crossref and OpenAlex APIs. Several sites refused automated fetches (Alpine's wiki and GitLab, Debian's Salsa, the ACM Digital Library and two university repositories); what they would have settled is listed in section 10.

**What RPT-0005 already covers (cited, not redone).** The structure of CVE, NVD (National Vulnerability Database), CWE and OSV (Open Source Vulnerability format) records and the VEX (Vulnerability Exploitability eXchange) encodings is RPT-0005's: [pilot.md](../0005-schema-representations/pilot.md) (CVE Record Format 5.2.0, NVD CVE API 2.0, CWE 4.20) and [fanout-vuln-data.md](../0005-schema-representations/fanout-vuln-data.md) (§1.0 NVD and CVE terms and feeds, §1.1 OSV 1.9.1, §1.6 VEX in CycloneDX 1.7, §1.8 CPE, §1.9 purl, §8.3 product identification in VEX). This file adds only what a component-to-vulnerability match needs. Identifier schemes as such (purl, CPE naming, `vers`) are agent 2's; tool runs are agent 5's (no scanner was run here; the pilot's Grype output was read).

**Short names.** CNA: CVE Numbering Authority (the organisation that publishes a CVE record). ADP: Authorized Data Publisher (an organisation that adds a container to someone else's CVE record). CPE: Common Platform Enumeration. purl: Package URL. GHSA: GitHub Security Advisory. CSAF: Common Security Advisory Framework. KEV: CISA's Known Exploited Vulnerabilities catalog. DT: Dependency-Track. EVR: epoch, version, release (the parts of a Debian or RPM version). SADP: a supplier CNA acting as an ADP (the CVE Program's pilot, 1.10).

Findings:

- **A product is named by vendor and product, or by package collection and package name.** `definitions.product.allOf[0]`: `anyOf` `required: ["vendor","product"]` or `required: ["collectionURL","packageName"]`; `allOf[1]`: `versions` or `defaultStatus` must be present. `collectionURL`: "URL identifying a package collection (determines the meaning of packageName)." `packageName`: "Name or identifier of the affected software package as used in the package collection." In 5.2.0 the product object is closed (`additionalProperties: false`; in 5.1.1 the key is absent).
- **`packageURL` exists, but only since 5.2.0, and has no purl syntax check.** `definitions.product.properties.packageURL.description`: "A Package URL, a unified URL specification for identifying packages hosted by known package hosts. The Package URL MUST NOT include a version." It refers to `uriType` (`"format":"uri"`, 1 to 2048 characters); no `pkg:` pattern (our reading: the schema checks a URI, not a purl). The 5.1.0 and 5.1.1 product property lists have no `packageURL` (compared with `jq ... | keys`).
- **`packageURL` is rare in practice.** In the snapshot, 4,079 of 384,424 published records carry it in the CNA container (3,971 of the 75,545 published in 2026, 5.3%). By assigner: VulnCheck 3,219, EEF 320, apache 207, openjs 114, CPANSec 79. No `packageURL` carries a version (checked: no `@` in the last path segment, 0 of all values).
- **CPE data now sits in the CVE record itself.** 5.1.1 added `cpeApplicability` to CNA and ADP containers. `definitions.cpeApplicabilityElement.description`: "Affected products defined using an implementation of the CPE Applicability Language, mostly copied/forked from the NIST NVD CVE API v2.0 schema (optional)." Its `cpe_match` has `vulnerable`, `criteria`, `matchCriteriaId` and the four range keys `versionStartExcluding`, `versionStartIncluding`, `versionEndExcluding`, `versionEndIncluding`; only `vulnerable` and `criteria` are required. The older `cpes` list says: "NOTE: Consider using the newer cpeApplicability block for defining CPE data using the CPE Applicability Language which includes more options for defining CPE Names." Snapshot: 36,967 published records have CNA `cpeApplicability` (20,247 of 75,545 in 2026, 26.8%: the Linux kernel CNA 7,364, VulnCheck 4,571, Oracle 3,067, Microsoft 2,963); 11,441 have `cpes` (7,054 in 2026). No ADP container carries `cpeApplicability` (0).
- **Many records name nothing an SBOM can match.** 144,341 published records list every product as vendor and product `n/a` with no `packageName` (2,816 of them published in 2026). Example: CVE-2025-60876 (BusyBox), CNA `mitre`: `"affected": [{"vendor": "n/a", "product": "n/a", "versions": [{"version": "n/a", "status": "affected"}]}]`. BusyBox is named only in the description, and a supplier ADP adds Siemens products (1.10).
- **GitHub's CNA names repositories, and writes ranges as text.** CVE-2022-31114 (`GitHub_M`, published 2026-06-03): `{"vendor": "Laravel-Backpack", "product": "CRUD", "versions": [{"version": ">= 5.0.0, < 5.0.13", "status": "affected"}, …]}`. The range is free text in `version`, with no `versionType` or `lessThan`. Heuristic count over 2026 records with versions (regular expression for `<`, `>`, `=`, "before", "through", "prior", "up to", "and earlier", "to"): 12,205 of 75,024 records put a range expression in `version`, 11,212 of them from `GitHub_M`. Our reading: a purl from an SBOM (for example `pkg:composer/backpack/crud`) cannot be matched to this record without the corresponding GHSA record (1.5).
- **`versionType` is a free string.** "The version numbering system used for specifying the range. … 'Custom' indicates that the version type is unspecified and should be avoided whenever possible." Examples in the schema: custom, git, maven, python, rpm, semver. Snapshot, records using each value (all published): `custom` 70,257, `semver` 57,008, `git` 18,893, `original_commit_for_fix` 17,106 (the Linux kernel CNA: 17,104), `rpm` 2,009, `maven` 977, `python` 207, `dpkg` 28, plus values such as `Server`, `26.2 series` and `firmware`. No registry of values exists in the schema.
- **ADPs add products and CWEs.** ADP containers by short name: `CVE` 250,701, `CISA-ADP` 195,907, `siemens-SADP` 1,360, `redhat-SADP` 1,170. CISA-ADP adds `affected` to 20,175 records, every one with `cpes` and `versions` and none with `packageURL`. Example CVE-2015-2051: `{"cpes": ["cpe:2.3:h:dlink:dir-645:*:*:*:*:*:*:*:*"], "vendor": "dlink", "product": "dir-645", "versions": [{"status": "affected", "version": "0", "versionType": "custom", "lessThanOrEqual": "1.04b12"}], "defaultStatus": "unknown"}` (a hardware CPE, note for agent 4).
- **`dataVersion` in the wild.** Published records: `5.1` 257,015, `5.2` 127,409. `5.0` appears only on 14,058 rejected records. (RPT-0005 pilot says "Records in the wild carry `dataVersion` 5.0, 5.1 or 5.2"; true of all records, but no published record is 5.0.)
- **A stale word in the normative text** (our reading). The `versions` item description says a range "must include the 'versionType' property … and 'limit', to indicate the non-inclusive upper limit of the range", but there is no `limit` property; the properties are `lessThan` and `lessThanOrEqual` (`definitions.product.properties.versions.items`).

| Library record | none (RPT-0005 marks it "new, Phase 2") |
| How checked, SHA-256 | Schema `2b9c4e8ab7e6e42aa17ea787f58167beff47c119c6f291405f86ac19c6149e01` (same as RPT-0005's); `cve_affected_1.0.json` `6ad105e90486…ff68ff`; web bundle `dbd9f659695821edbf7f971560639e0dc06945f5052204a36139c6ce41f73daa` (same as RPT-0005's 2026-10-06 copy: unchanged); API records for CVE-2026-54873 (`cb155735…2bfd2c`), CVE-2026-85091 (`54505b26…5f52`), CVE-2025-60876 (`919c198e…68cd1`); all 15,074 CVEs published 2026-09-01 to 2026-09-30, eight pages (`page-0` `a43ec230…b033` … `page-7` `86850277…f433`, all hashes in section 8) |

Findings:

- **A configuration is boolean CPE logic with version ranges, and it carries no source.** Schema `definitions.cpe_match`: `vulnerable`, `criteria`, `matchCriteriaId` (all required), `versionStartExcluding`, `versionStartIncluding`, `versionEndExcluding`, `versionEndIncluding`; `node` has `operator` (AND, OR), `negate`, `cpeMatch`; `config` has `operator`, `negate`, `nodes`. None of `config`, `node` or `cpe_match` has a `source` field, while `definitions.weakness` requires `source`, `type` and `description`. Our reading: who wrote a configuration is not recorded in the API.
- **NVD's own words on ranges.** Bundle, vulnerability API page: "In some cases, the CPE match string indicates a range of product versions. Notice in the following example that the version is not specified in the `cpe23Uri` element; instead, the `versionEndIncluding` indicates the last vulnerable version. Other possible elements are `versionEndExcluding`, `versionStartIncluding`, and `versionStartExcluding`." The match criteria API returns "an array of paired CPE Names and IDs within the CPE Dictionary that `matches` the CPE Match Criteria".
- **The API passes the CNA's and ADPs' `affected` through, but not the CNA's `cpeApplicability`.** `cve_affected_1.0.json` (title "Product information") has the same 13 product properties as CVE 5.2.0, `packageURL` included. CVE-2025-60876 `affected`: `[{"source": "cve@mitre.org", "affectedData": [{"vendor": "n/a", …}]}, {"source": "0b142b55-0307-4c5a-b3c9-f314f3fb7c5e", "affectedData": [{"vendor": "Siemens", "product": "RUGGEDCOM RST2428P", …}]}]`. CVE-2026-85091 (zlib, CNA VulnCheck) has `cpeApplicability` in the CVE record (1.1) but `vulnStatus: "Awaiting Analysis"` and no `configurations` in the API.
- **Scope since April 2026, and the status names.** Bundle, "NVD Scope of Coverage": "CVEs appearing in CISA’s Known Exploited Vulnerabilities (KEV) Catalog. Within one business day of addition to the KEV Catalog; CVEs for software used within the federal government; CVEs for Critical Software as defined by Executive Order 14028". The status table maps the web status "Not Scheduled" to the API status "Deferred": "Not Scheduled | Deferred | The CVE is not currently scheduled for NVD enrichment efforts." (and "Enriched" to "Analyzed", "Awaiting Enrichment" to "Awaiting Analysis"). So the API's `Deferred` is NVD's documented API name for "Not Scheduled", not a lag (correction to RPT-0005 pilot's "The API still says `Deferred`, not the announced 'Not Scheduled'"; section 9). Nothing newer than the 2026-04-15 change was found: the bundle is byte-identical to the 2026-10-06 copy, and three web searches returned only secondary reports of the April change (section 7).
- **Enrichment is concentrated on a few CNAs.** September 2026 publications (15,074 CVEs, API read 2026-10-08): `Deferred` 5,776, `Analyzed` 4,251, `Awaiting Analysis` 2,415, `Received` 1,990, `Undergoing Analysis` 375, `Modified` 135, `Rejected` 132. 4,408 (29.2%) have `configurations`. Analyzed by source: `secure@microsoft.com` 982 (of 1,000 Microsoft CVEs), `chrome-cve-admin@google.com` 434, `secalert_us@oracle.com` 278, `psirt@us.ibm.com` 247, `product-security@apple.com` 219. Deferred by source: VulnCheck 1,150, VulDB 887, GitHub 834, WPScan 551, Wordfence 401. The Linux kernel CNA's 2,117 CVEs: 1,990 `Received`, 29 with configurations. RPT-0005's one-day sample (2026-09-20: 102 CVEs, 96 Deferred, 4 Awaiting Analysis, 2 Analyzed) is reproduced exactly; the month shows large day-to-day swings (2026-09-08: 1,571 CVEs, 1,308 Analyzed).
- **CNA CPE data and NVD CPE data often differ.** Of the September 2026 CVEs, 5,267 have CNA `cpeApplicability` (cvelistV5 snapshot); 3,722 of them have no NVD configuration (Received 1,990, Deferred 1,111, Awaiting Analysis 481, Undergoing 140) and 1,545 have one. Comparing the vulnerable match entries of both (script `cna_vs_nvd_cpe2.py`): same set of vendor:product pairs in 617 (identical ranges and version field in 375, different ranges in 242), overlapping but different sets in 796, disjoint sets in 132 (Microsoft 51, Oracle 31, MITRE 15). Examples: CVE-2026-3416, CNA `cpe:2.3:a:wso2:wso2_api_manager` versus NVD `cpe:2.3:a:wso2:api_manager`; CVE-2026-64195, CNA vendor `measx` versus NVD `ni`; CVE-2026-85165 (n8n), CNA `versionEndExcluding "2.36.2"` versus NVD `versionStartIncluding "2.36.0", versionEndIncluding "2.36.2"` on `cpe:2.3:a:n8n:n8n:*:*:*:*:*:node.js:*:*`, so the two disagree on whether 2.36.2 is affected. Caveat: the snapshot is from 00:00 UTC and the API pages from about 17:50 UTC on the same day.
- **Who is "Primary".** Bundle, `weaknesses`: "`source` identifies the organization that provided the weakness information and `type` identifies whether the organization is a primary or secondary source. Primary sources include the NVD and CNA who have reached the provider level in CVMAP. 10% of provider level submissions are audited by the NVD. If a submission has been audited the NVD will appear as the primary source and the provider level CNA will appear as the secondary source." September 2026: 553 CVEs have a Primary CWE, from `security-advisories@github.com` 135, `nvd@nist.gov` 121, `disclosure@vulncheck.com` 86, `audit@patchstack.com` 53, `cna@vuldb.com` 39; 12,837 have at least one `CWE-` id from any source; 19 carry an `NVD-CWE-*` placeholder.

### 1.3 CPE matching specifications: NIST IR 7696 and NIST IR 7698

| field | value |
|---|---|
| Citation, URL | Parmelee, Booth, Waltermire, Scarfone, *Common Platform Enumeration: Name Matching Specification Version 2.3*, NIST IR 7696, August 2011, https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir7696.pdf. Waltermire et al., *Common Platform Enumeration: Applicability Language Specification Version 2.3*, NIST IR 7698, https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir7698.pdf |
| Version pinned | CPE 2.3 (2011); NIST's CPE 3.0 effort has no text yet (RPT-0005 fanout-vuln-data §1.8) |
| Steward | NIST (SCAP) |
| What it is | IR 7696 defines how two CPE names compare (attribute by attribute, as set relations). IR 7698 defines logical tests (AND, OR, negate) over CPE names |
| Licence | US government publication (not checked further) |
| Library record | none (agent 2 covers IR 7695, CPE naming) |
| How checked, SHA-256 | IR 7696 `966eecc18a0d94c1e1c035994a633c4adee790c83d122bad2a79ac7ce4981a45`, IR 7698 `d08fc0e17dfcaf05fdfa4541a00c2d1ad2c5e601b32b383fd12c5d41479b91f3`; text extracted with `pdftotext`; searched for "range", "greater", "lesser", "<=", ">=", "ordered", "sort", "versionStart", "versionEnd", "less than", "greater than" |

Findings:

- **CPE matching compares names, not versions in order.** IR 7696 §6, Table 6-1: four set relations, "SUPERSET", "SUBSET", "EQUAL", "DISJOINT". §5: "CPE’s developers have chosen not to define a single notion of “name match” because experience has shown that name matching distinctions are often use-case dependent", and "the CPE Name Matching specification leaves the majority of decisions about what constitutes a “name match” to CPE implementers at design time."
- **Neither specification defines a version range.** The searches above found no version-range or version-ordering construct in IR 7696 (the only hits are a character counter and a substring routine in the pseudocode) or in IR 7698 (which has "Definition of test using logical operators (AND, OR, negate)"). Our reading: `versionStart…`/`versionEnd…` are NVD's addition (copied into CVE 5.1.1's `cpeApplicability`), and how two version strings are ordered is left to each tool. Dependency-Track, for example, converts them into `vers` constraints with a scheme guessed from the purl (1.13).

| field | value |
|---|---|

| Steward | OpenSSF (`ossf/osv-schema`); osv.dev run by Google (RPT-0005) |
| What it is | A record format for open-source vulnerabilities in which `affected[]` names a package in an ecosystem and the affected versions as ranges or lists; osv.dev aggregates records from many databases |
| Licence | Schema Apache-2.0; records per source database (RPT-0005 fanout-vuln-data §1.1) |
| Library record | `osv-schema` (`openssf/osv-schema`), `summarized` |
| How checked, SHA-256 | Spec text `e5b87d6258f133f2fb146661b4d7ee7d6c1ffb15f7b752d49b1b790ea683307e`, schema `15b10dbb4c4e31c7aae11d22cdd991a9a374758db7c8389e62b3cc37cac92653` (both equal RPT-0005's). osv.dev exports downloaded 2026-10-08: Alpine `48f6f58b…126b`, Debian `0fed876c…57df`, PyPI `1949265a…e957`, Maven `d535035a…1390`, Go `fc84deb9…076c`, crates.io `36133b84…e6e6`, Red Hat `20973ab3…f6a6`; parsed with `osv_stats.py` |

Findings:

- **A package is an ecosystem plus a name; the purl is optional and version-less.** Spec, "affected[].package field": "The object itself has two required fields, `ecosystem` and `name`, and an optional `purl` field." "The `purl` field is a string following the Package URL specification that identifies the package, without the `@version` component. This field is optional but recommended." The JSON Schema types `purl` as a plain string (`"purl": {"type": "string"}`), with no pattern.
- **Distribution ecosystems name the source package.** Spec, "Defined ecosystems": Alpine, "the `name` is the name of the source package. The ecosystem string must have a `:v<RELEASE-NUMBER>` suffix"; Debian and Ubuntu likewise source packages; Red Hat, "the `name` field is the name of a binary or source RPM. The ecosystem string has a `:<CPE>` suffix to scope the RPM to a specific Red Hat product stream." 52 ecosystem names in `$defs.ecosystemName`.
- **Ranges are typed timelines.** "`SEMVER`: The versions `introduced` and `fixed` are semantic versions as defined by SemVer 2.0.0, with no leading "v" prefix." "`ECOSYSTEM`: The versions `introduced` and `fixed` are arbitrary, uninterpreted strings specific to the package ecosystem". "`GIT`: The versions `introduced` and `fixed` are full-length Git commit hashes." Events are `introduced`, `fixed`, `last_affected`, `limit`; "`introduced` allows a version of the value `"0"` to represent a version that sorts before any other version"; "Entries in the `events` array may be "last_affected" or "fixed" events, but not both." The evaluation pseudocode `IsVulnerable` is normative ("Evaluation" section).
- **osv.dev adds purls that some sources lack.** In the osv.dev exports, every or nearly every `affected[].package` carries a purl and none carries a version: Alpine 44,287 of 44,287, Debian 188,840 of 188,843, PyPI 31,768 of 31,768, Maven 13,551 of 13,551, Go 14,810 of 14,812, crates.io 4,072 of 4,072, Red Hat 631,373 of 631,373. GHSA-jfh8-c2jp-5v3q as served by osv.dev has `"purl": "pkg:maven/org.apache.logging.log4j/log4j-core"` and `schema_version` 1.9.0; the same advisory in GitHub's repository has no `purl` and `schema_version` 1.4.0 (1.5). Our reading: osv.dev computes the purl on import.
- **The query API matches versions loosely.** `post-v1-query.md`: "`version` … The version string to query for. A fuzzy match is done against upstream versions." "Package Objects can be described by package name AND ecosystem OR by the package URL." A separate experimental endpoint maps "Ubuntu binary package names to their corresponding source package names" (`post-v1-ubuntu-binary-to-source.md`, `f79999c3…96e7`).
- **No CWE in the schema; only GHSA records carry one.** In the exports, `database_specific.cwe_ids` appears only on GHSA records (Maven 7,185, PyPI 6,526, Go 4,906, crates.io 1,601); ALPINE, DEBIAN, DSA, DLA, RHSA, PYSEC, GO and RUSTSEC records have none, and the Alpine, Debian and Red Hat exports have no `database_specific` keys at the record level at all.

Findings:

- **CycloneDX ranges are `vers` strings with a status.** `vulnerability.affects[].versions[]`: `oneOf` `version` or `range`; `range`: "A version range specified in Package URL Version Range syntax (vers) which is defined at https://github.com/package-url/vers-spec"; `status` defaults to `affected`. `definitions.versionRange` is a string of 1 to 4096 characters with no pattern; examples include `vers:npm/1.2.3|>=2.0.0|<5.0.0`. `affectedStatus` uses the same three values and the same description text as CVE 5.x `status` ("The statuses 'affected' and 'unaffected' indicate that the version is affected or unaffected by the vulnerability. The status 'unknown' indicates that it is unknown or unspecified whether the given version is affected."). Unchanged between tags 1.7 and 1.7.2. Real use: Grype's CycloneDX output for the pilot writes `vers:apk/>=1.3.2-r1` with `unaffected` for zlib ([pilot.md](pilot.md) §3).
- **`vers` leaves ordering to each type, and few types are defined.** Clause 5: a type defines "how two versions are compared to determine if a version is inside or outside a range". Clause 1: "This Standard specifies the syntax for VERS and the schema for defining VERS types, but it does not include any specific VERS type definitions." and "This edition of the Standard supports linear versioning where the software versions do not branch to form a tree of versions." At v1.2.1 `vers-types-index.json` lists two types: `["npm","pypi"]`.
- **dpkg (Debian, Ubuntu).** "[epoch:]upstream_version[-debian_revision]"; "epoch is compared numerically"; "a tilde sorts before anything, even the end of a part. For example, the following parts are in sorted order from earliest to latest: ~~, ~~a, ~, the empty part, a." (Policy §5.6.12). So `3.5.7-1~deb13u3` sorts below `3.5.7-1`.
- **rpm (Red Hat, SUSE).** "\[_EPOCH_*:*]_VERSION_[*-*_RELEASE_]"; "Numeric segments are considered newer than alphabetic segments regardless of the actual content." "The segment _separator_ characters are not compared, so they can be used interchangeably … Thus, *1.0* is equal to *1+0* and *1+.+0*." "The tilde operator causes a segment to sort older … The caret operator is essentially the opposite of tilde." Its BUGS section: "Non-ASCII characters are ignored and thus equal".
- **apk (Alpine).** "The Alpine version specification originally followed the Gentoo package version specification. Currently the APK version specification is as follows: *number{.number}...{letter}{\_suffix{number}}...{~hash}{-r#}*", with suffix order "*alpha*, *beta*, *pre*, *rc*, <no suffix>, *cvs*, *svn*, *git*, *hg*, *p*".
- **PEP 440 (Python).** "[N!]N(.N)*[{a|b|rc}N][.postN][.devN]"; "Semantic versions containing a hyphen (pre-releases - clause 10) or a plus sign (builds - clause 11) are not compatible with this specification and are not permitted in the public version field."
- **Maven.** "The Maven version order algorithm is not compatible with Semantic Versioning 2.0.0. In particular, Maven does not special case the plus sign or consider build identifiers." "Maven compares version strings using case-insensitive rules. Semver is case-sensitive. Thus in Semver, 3.2-ALPHA1 compares greater than 3.2-alpha1. In Maven, 3.2-ALPHA1 compares equal to 3.2-alpha1." Qualifier order: "alpha < beta < milestone < rc = cr < snapshot < = final = ga = release < sp".
- **semver.** "Precedence MUST be calculated by separating the version into major, minor, patch and pre-release identifiers in that order (Build metadata does not figure into precedence)." "Build metadata MUST be ignored when determining version precedence."
- **Missing epochs are a matcher setting.** The pilot's Grype configuration records `"dpkg": {"missing-epoch-strategy": "zero"}` and `"rpm": {"missing-epoch-strategy": "auto"}` (`descriptor.configuration.match`): when an SBOM drops the epoch, the result depends on a tool default (our reading).

## 2. Dimension questions answered

**5.0 (0.1.0's question: CPE versus purl, NVD versus distribution feeds, where CWEs come from, NVD placeholders).** Still two naming systems, but the CVE record now carries both: CNAs can write CPE applicability (5.1.1, 26.8% of 2026 records) and purls (5.2.0, 5.3% of 2026 records) beside vendor and product (1.1). NVD writes its own CPE configurations only for CVEs in its scope (29.2% of September 2026 CVEs by 2026-10-08), and these differ from the CNA's CPE data for most CVEs where both exist (1.2). Placeholders: Grype keeps `NVD-CWE-Other` and drops `NVD-CWE-noinfo`; Trivy drops both; Dependency-Track and CycloneDX store integers only, so neither fits (1.11 to 1.13, 1.15). They are now rare in new data: 19 of 15,074 September 2026 CVEs (1.2).

**5.1 How each source names affected software, and what it needs from an SBOM.** CVE records: vendor and product, or collection URL and package name, optionally `packageURL` (no version) and CPEs; many records name nothing usable ("n/a", 144,341) or name a repository with a text range (GitHub's CNA) (1.1). NVD: CPE 2.3 match criteria with four range keys; an SBOM needs a CPE whose vendor and product equal NVD's dictionary names (1.2, 1.3). OSV: ecosystem and package name, with an optional version-less purl that osv.dev fills in; distributions name source packages (1.4). GHSA: ecosystem and package name only, no purl in the repository (1.5). Alpine: origin package name per release branch (1.6). Debian: source package per release (1.7). Ubuntu: source package per release, binaries as a side list, versioned purls (1.8). Red Hat: product stream CPE (from the repository the RPM came from) plus RPM name (1.9). So, from an SBOM, a match needs: for NVD, a correct CPE; for ecosystem databases, the ecosystem and the name as the registry writes it (purl type, namespace, name); for distributions, the source (origin) package name, the distribution release, and for Red Hat the repository. Syft's apk purls carry `distro=` and `upstream=`, which is what Grype uses (1.6, 1.11).

**5.2 Match provenance.** Grype records the most: match type (ranked, with Anchore's guidance that `cpe-match` "requires verification"), matcher, what it searched by (package, distro, exact CPEs), what it found (record id, version constraint and its format, CPEs), the advisory namespace and URL, the database build and capture times, and the matcher configuration; its internal `Confidence` is "currently unused". It does not record whether an `nvd:cpe` range came from NVD or from Anchore's overrides (1.11). Trivy records the data source of the advisory and the severity source, not the method, and drops the source of CWEs (1.12). Dependency-Track records one attribution per analyzer with a date, a reference URL and a 0 to 100 match percentage, which source asserted which version range, and whether a finding is still active (1.13). OSV-Scanner records the package coordinates, the input source and alias groups; the method is implicit (1.14). All of this can become an Assertion with a confidence (section 5), but the LinkML draft's Assertion has only `subject`, `predicate`, `object`, `confidence` and `assertion_status`, so method, evidence, data source and database snapshot need homes.

**5.3 Version ranges.** NVD and CVE `cpeApplicability`: start and end, each including or excluding, on a CPE whose version is `*` (1.2); CPE's own specifications define no ranges or ordering (1.3). OSV: typed event timelines (`SEMVER`, `ECOSYSTEM`, `GIT`) with `introduced`, `fixed`, `last_affected`, `limit` and a normative evaluation (1.4). CVE 5.x: `version` with `lessThan` or `lessThanOrEqual`, a free-text `versionType`, `status` (affected, unaffected, unknown), `changes` (used in 11,961 records, 10,653 by Patchstack) and `defaultStatus` (per product: unaffected 139,065, affected 50,501, unknown 23,636) (1.1). CycloneDX: `vers` strings with the same three statuses (1.15). Comparison differs by ecosystem: dpkg and rpm epochs and tildes, rpm's ignored separators and caret, apk suffix order and `-r` revisions, PEP 440's refusal of semver pre-release syntax, Maven's case-insensitivity and qualifier order, semver's build metadata (1.15). Distribution backports make upstream ranges wrong for distribution packages (Debian 3.5.7-1~deb13u3 fixed while NVD says below 3.5.9 is affected, 1.7).

**5.4 Disagreement.** Yes, published and measured, though mostly as counts or set overlaps rather than ground truth. Same image, two scanners: Trivy and Grype overlap with a Jaccard index of 0.694; on the same SBOM, as low as 0.026 to 0.101 (Churakova et al.). Same image, two SBOM generators: only 2% (Grype) to 12% (Trivy) of SBOMs gave the same count (O'Donoghue et al.). Nine SCA tools on one application: 17 to 332 vulnerable dependencies (Imtiaz et al.). A CPE-based scanner had precision 0.34 against code-level ground truth (Dann et al.). NVD's version data matched other reports strictly for 59.82% (Dong et al.), and about 10% of NVD vendors had naming inconsistencies (Anwar et al.). Our measurement: where both a CNA and NVD wrote CPE applicability for a September 2026 CVE, only 375 of 1,545 agree on vendor, product and range (1.2). Section 1.16 gives each study's data set and tool versions.

**The CWE side.** CVE records: CNA `problemTypes` (CNA-assigned; 159,816 published records), CISA-ADP (fills gaps: 38,251 records), supplier ADPs (`redhat-SADP` 1,124); 186,234 published records have none, 7,776 of the 75,545 from 2026 (1.1, 1.10). NVD: `weaknesses` with `source` and `type`, Primary meaning NVD or a "provider level" CNA (1.2). OSV: no field; GHSA puts GitHub curators' CWEs in `database_specific.cwe_ids`, missing in 1,420 live reviewed advisories (1.4, 1.5). Alpine and Debian: none (1.6, 1.7). Ubuntu: none (1.8). Red Hat CSAF: one CWE per CVE, Red Hat's (1.9). Grype passes NVD's CWEs with source and type; Trivy picks one source's list by precedence and drops the source; Dependency-Track stores integers (1.11 to 1.13).

Candidate fields for an Assertion that represents a match (evidence for #15 and #17; nothing chosen):

1. `subject`, `predicate`, `object`: Vulnerability, `affects` (name open), Component, as the pilot proposes. The Component is keyed by its purl; Grype's CycloneDX `affects[].ref` values do not equal Syft's `bom-ref` values ([pilot.md](pilot.md) §3).
2. `confidence` (draft slot, string): first from the match type ranking (`typeOrder` 1 to 3) and Anchore's guidance; Dependency-Track's `matchingPercentage` (0 to 100) is a second published scale. Grype's own `Confidence` ratio is unused, so no tool publishes a calibrated probability today (1.11, 1.13).
3. Method (no slot): identifier scheme used (distribution package name, ecosystem name, purl, CPE, git commit), matcher name, and whether the match went through an origin (upstream) package.
4. Search key (no slot): Grype `searchedBy` (package name and version, distro and version, the exact CPE strings searched).
5. Evidence (no slot): the advisory record id, its namespace or feed, its URL (`dataSource`), the version constraint as written with its scheme, the CPE criteria matched (`found.cpes`), and the enrichment layer that supplied the range (NVD analysis, CNA `cpeApplicability`, Anchore override, distribution feed). The last one is not recorded by Grype (1.11).
6. Provenance (proposal §4, PROV-O): the generating Activity (scan) with tool, version, run time, database build time and provider capture times, and the Agent (the tool, the operator).
7. Fix information (no slot; pilot row "Fix information"): suggested version, fix state, first-observed date (Grype `fix.available[]`).
8. Lifecycle (`assertion_status`, plus `valid_from`/`valid_to` if added): first seen, last confirmed, and lapsed, as Dependency-Track's active and inactive findings do (1.13).
9. A Review (separate node, R-018) for the human verdict, and the VEX override as the proposal's §5 says; vendor VEX data (Ubuntu OpenVEX, Red Hat CSAF) arrives as other parties' Assertions, not as Reviews (our reading).

## 10. Open items, and notes for other agents

Open items (what would close each):

1. **Alpine's own definition of the secdb format** (the `"0"` key, `security-rejections`): wiki.alpinelinux.org returned 403 and gitlab.alpinelinux.org 418 to `curl`. A person with a browser could read the APKBUILD reference and the `security-rejections` README.
2. **Debian's JSON export format** (`fixed_version` "0", `scope`): the tracker code on salsa.debian.org is behind a proof-of-work page. The mapping was confirmed for one CVE against the HTML page (1.7), not from a format definition.
3. **Zhao et al. (FSE 2023)**, the largest SCA comparison found (21,130 Maven modules per the search summary, not verified): full text not fetched (ACM, SMU, NTU all refused). A library copy would close it.
4. **Tool versions** not stated by Dann et al., Benedetti et al. and Javed and Toor (checked by text search); Churakova et al.'s supplementary material expired.
5. **Whether NVD now imports CNA `cpeApplicability`.** 375 of 1,545 September 2026 CVEs have identical CNA and NVD CPE data (1.2); NVD's documentation in the bundle does not say whether NVD copies CNA data. An NVD statement or a time-series comparison would settle it.
6. **Ubuntu's versioned purls** in OSV `package.purl`: whether the OSV maintainers accept this (the schema does not check it). An osv-schema issue search would settle it.
7. **A ground-truth rate for CPE matching versus ecosystem matching on current tools.** No published study measures it for Grype or Trivy at current versions. Anchore publishes labelled match data (`anchore/vulnerability-match-labels`, CC0-1.0, 24,004 label files at `d6b9bb2c…`; README `f48f8760…`), each label naming the tool version, image, package, vulnerability and `TP`/`FP`, but not the match type; measuring it would need Grype runs (agent 5).
8. **Red Hat's own statement on how it assigns CWEs**: not found in the files fetched; the CWE is attributed to the document publisher (1.9).
9. **Licences** of the Alpine secdb and the Debian tracker data: not found.
10. **The `vers` scheme guessed by tools**: Dependency-Track maps purl types to `vers` schemes with the `versatile` library; its type list was not checked.

Notes for other agents:

- **Agent 5 (tools):** newer versions than the report's runs exist: Grype 0.120.1 (2026-10-06), Trivy 0.75.0 (2026-10-01), Dependency-Track 5.2.0 (released 2026-10-08) and 4.14.5. Grype's match-model and apk-matcher files are byte-identical between 0.119.0 and 0.120.1. Grype's `nvd:cpe` namespace includes Anchore's overrides (1.11); Trivy's NVD source does no CPE matching (1.12).
- **Agent 1 (formats):** CycloneDX 1.7.2 is a GitHub release (2026-09-17) with the schema RPT-0005 analysed; `affects` and `versionRange` are unchanged since tag 1.7 (1.15, section 9).
- **Agent 2 (identifiers):** CVE 5.2.0 `packageURL` is checked only as a URI; Ubuntu's OSV purls carry versions; osv.dev adds purls that GitHub's files lack; Syft's apk purls carry `distro=` and `upstream=`, which Grype uses; vers v1.2.1 registers only `npm` and `pypi`; CPE vendor naming inconsistency in NVD measured by Anwar et al. (about 10% of vendors in 2018).
- **Agent 4 (hardware):** CISA-ADP adds hardware CPEs to CVE records (for example `cpe:2.3:h:dlink:dir-645`, 1.1), and supplier ADPs (Siemens) state the status of downstream firmware products inside upstream CVE records (1.10).
- **RPT-0005 (via the main session, for DL-0013 or DL-0015):** the "Not Scheduled" to "Deferred" mapping; `dataVersion` 5.0 only on rejected records; the supplier ADP pilot (`x_adpType: supplier`) as a new container kind; the CISA-ADP orgId behind the pilot's "unknown UUID".

**What could change dimensions.md (suggestions only):** question 5.1 could name the CVE record's `cpeApplicability` and `packageURL` and the supplier ADP containers as sources in their own right, since a match can now be made against the CVE record without NVD; question 5.2 could add "which enrichment layer supplied the range (NVD, CNA, a scanner vendor's override)", because Grype's `nvd:cpe` merges them; and question 5.4 could separate published studies from our own measurements, since the strongest current evidence on CPE disagreement (1.2) is ours.
