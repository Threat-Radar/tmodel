**What Table 2 shows.** Every data field has a CycloneDX 1.7 field, Component Producer only as our closest match. SPDX 3.0.1 has no field for SBOM Author Signature, SBOM Tool Version or SBOM Version, and SWID with CoSWID has none for a creation timestamp, the tool's name and version, or a component licence; CISA 2026 also drops SWID as a format. No format can say "withheld" as distinct from "unknown", and none uses IANA's lowercase hash names exactly as CISA 2026 asks: CycloneDX's names differ only in case, SPDX drops the hyphen (`sha256`), and CoSWID uses integer ids. Syft's output met the format, tool, timestamp, name, version, identifier and licence elements. It missed the SBOM author, the package hash, the producer, the generation context, a signature and any completeness claim, so it falls short of NTIA 2021, CISA 2024, CISA 2026, BSI, CERT-In and FDA on at least one element each of them requires: the SBOM author, which all six require. §8 compares the baselines themselves.

### VEX statuses

**VEX statuses.** CISA's four VEX statuses are the reference (CISA, Minimum Requirements for VEX, §2.7.1; see `sources.md`). Each SPDX class states which VEX status it represents, and SPDX's five justifications are CISA's five. CycloneDX publishes no normative mapping to these statuses (neither CISA's document nor CycloneDX's VEX page gives one), but CycloneDX's own examples for CISA's VEX use cases, which CISA's document links to, use `exploitable` for affected, `resolved` for fixed, `not_affected` for not affected and `in_triage` for under investigation (CycloneDX bom-examples, `VEX/CISA-Use-Cases/Case-1`; the example files are CycloneDX 1.4, unchanged since 2022-03-23, and all four states are still in CycloneDX 1.7). The CycloneDX column follows those examples; the Match column is our rating of how closely the written definitions agree. CycloneDX's nine justifications are cut differently and are not mapped.

| CISA status | SPDX 3.0.1 | CycloneDX 1.7 (per its CISA examples) | Match |
|---|---|---|---|
| `not_affected` | `VexNotAffectedVulnAssessmentRelationship` | `not_affected` | same meaning |
| `under_investigation` | `VexUnderInvestigationVulnAssessmentRelationship` | `in_triage` | same meaning |
| `fixed` | `VexFixedVulnAssessmentRelationship` | `resolved` (`resolved_with_pedigree` adds proof; our addition) | close: "has been remediated" is broader than "contain fixes" |

## 1. SBOM formats (CycloneDX, SPDX, SWID)

Input to DEC-002.

**Where each format stands as a standard.** CycloneDX 1.7 is Ecma standard ECMA-424, 2nd edition (`cyclonedx-1-7`), and CycloneDX is also moving through ISO as ISO/IEC DIS 27055, "CycloneDX Bill of Materials (BOM) specification", a draft international standard at stage 40.00 ("DIS registered"). SPDX's current ISO standard, ISO/IEC 5962:2021, covers SPDX 2.2.1 and is under revision (stage 90.92); ISO lists its replacement as ISO/IEC PRF 5962, "SPDX® Specification V3.0", now past the draft stage at stage 50.20 ("Proof sent to secretariat or FDIS ballot initiated: 8 weeks"). SWID is ISO/IEC 19770-2:2015 (1.3). Two identifiers used below are standards too: SWHID is ISO/IEC 18670:2025 ("SWHID Specification V1.2"), and purl, already ECMA-427, is ISO/IEC DIS 27056, also at stage 40.00 (ISO Open Data, `iso_deliverables_metadata`, file of 2026-10-21, checked 2026-10-22; the file of 2026-10-14 had PRF 5962 at 50.00, on 2026-10-07 SPDX 3.0 was DIS 5962 at 40.99, and 0.1.0, checked 2026-09-30, had CycloneDX and purl as committee drafts at 30.99 and DIS 5962 at 40.60; stage names from ISO's stage-codes page).

Sections 1.1 to 1.3 answer the five questions in [`dimensions.md`](dimensions.md) for each format. Sections 1.4 to 1.6 are new in 0.2.0: the SPDX 3 RDF model, what each format's validation checks, and what changed between versions.

### 1.1 CycloneDX 1.7 (`cyclonedx-1-7`)

**Naming a component.** A component needs only a `type` and a `name`; every identifier is optional. The table lists the fields the spec itself treats as identity fields (the allowed values of `evidence.identity.field`), plus the local `bom-ref`.

| Field | What it identifies | Kind |
|---|---|---|
| `name`, `version` | the component's name and version | assigned name |
| `group` | the maker or namespace, e.g. `org.apache` | assigned name |
| `purl` | a package in a package ecosystem, e.g. `pkg:apk/alpine/zlib@1.3.2-r0` | assigned name |
| `cpe` | a product, in the CPE naming scheme the NVD uses | assigned name |
| `swid` | an ISO/IEC 19770-2 software identification (SWID) tag | assigned name |
| `hashes` | the exact bytes | computed from bytes |
| `omniborId` | the exact bytes (an OmniBOR artifact ID) | computed from bytes |
| `swhid` | files, directories or commits, via a Software Heritage ID | computed from bytes |
| `bom-ref` | a component within this one SBOM; another file can reach it only through a BOM-Link | local |

Two things stand out. First, the spec words five of the six global identifiers as claims: `purl`, `cpe`, `swid`, `omniborId` and `swhid` each "asserts the identity of the component", and an optional `evidence.identity` field can back the claim up (`cyclonedx-1-7`). Second, only three identifiers are computed from the bytes (`hashes`, `omniborId`, `swhid`; see `cisa-framing-software-component-transparency`, §2.2.2.4); the rest are assigned names, which can be wrong or guessed.

Even `hashes` has limits: the spec does not say which bytes are hashed, so two SBOMs of the same artifact can carry different hashes, and the allowed algorithms still include MD5 and SHA-1, which CISA notes "will be formally discontinued in 2030" (`cisa-framing-software-component-transparency`, §2.2.2.5). All of this matches the names-versus-bytes gap the library's SBOM topic describes (library topic `sbom`), and it matters for DEC-002 (which formats tmodel imports).

**Hardware and firmware.** CycloneDX can describe hardware, but little of it is built into the spec. `device` is the only component type described as hardware ("a hardware device such as a processor or chip-set"); `firmware` and `device-driver` are each "a special type of software", and `platform` is a runtime environment (`cyclonedx-1-7`). The `device` description adds one rule: a device containing firmware "SHOULD include a component for the physical hardware itself and another component of type 'firmware' or 'operating-system'", and nested `components` can show an assembly, "similar to system → subsystem → parts assembly in physical supply chains". There are no hardware-only fields: details such as a serial number, MAC address or location on the board go in the generic `properties` field, which the spec describes as a place for "data not officially supported in the standard", under names from CycloneDX's separate property taxonomy, such as `cdx:device:serialNumber` (see `sources.md`). Because those names live outside the schema, a schema check cannot catch a missing or misspelled one, which matters for DEC-001 (tmodel's core object model) if hardware becomes part of it.

**Dependencies.** CycloneDX separates three kinds of structural relationship between components (`cyclonedx-1-7`), shown below; a component's history, such as what it was forked or derived from, is recorded separately in `pedigree`.

| Relationship | Field | Meaning |
|---|---|---|
| depends on | `dependencies[].dependsOn` | the component's direct dependencies; indirect ones come from following the chain |
| provides | `dependencies[].provides` | the component implements a standard or algorithm, which "does not imply that the implementation is in use" |
| contains | nested `components` | an assembly, "similar to system → subsystem → parts assembly"; "This is not a dependency tree" |

Three details matter for anyone reading the graph. First, a missing entry should be read as "unknown", not "none": components with no dependencies "must be declared as empty elements", while components left out of the graph "may have unknown dependencies", to be treated as "opaque and not an indicator of an object being dependency-free". Second, `dependsOn` and `provides` point by `bom-ref` "in the same BOM document"; unlike a vulnerability's `affects`, they cannot use a BOM-Link into another SBOM, so a dependency cannot cross files; separate SBOMs can only be connected in other ways, such as an external reference of type `bom` or matching components by their global IDs. Third, `scope` says whether a component is reachable at runtime (`required`, `optional` or `excluded`); when it is missing, consumers "SHOULD" assume `required`, and a component that is installed but blocked from being called still counts as `required`. These typed relations bear on DEC-001 (tmodel's core object model and its typed relations), and the same-file limit bears on DEC-002 (which formats tmodel imports).

**Completeness.** A separate top-level `compositions` list says how complete the relationships are (`cyclonedx-1-7`). Each entry names what it covers by reference (nested parts in `assemblies`, dependency links in `dependencies`, or the list of `vulnerabilities`) and gives one required `aggregate` value. The table aligns the ten values with CISA's four completeness levels (`cisa-framing-software-component-transparency`, §2.2.2.6.4); the alignment is ours, based on the definitions, not an official crosswalk:

| CISA | CycloneDX `aggregate` |
|---|---|
| Known | `complete` |
| Partial | `incomplete`, or one of six narrower variants such as `incomplete_third_party_only` |
| Unknown (the CISA default) | `unknown` ("a 'best-effort'... but the completeness is inconclusive") or `not_specified` (the CycloneDX default) |
| None | no value of its own; an empty `dependsOn` entry, as described under Dependencies |

Two things stand out. First, CycloneDX splits CISA's Unknown in two: `unknown` usually signals a best-effort attempt that was inconclusive, while `not_specified` means no one said anything, and leaving `compositions` out entirely makes no completeness claim at all. Second, both standards limit the claim to direct relationships: CycloneDX references "do not cascade to transitive dependencies", matching CISA's rule that a "Known" component can have upstream components that are only "Partial" or "Unknown". So an SBOM can be complete at the top and still have gaps further down, and while it can state that a list is complete, it cannot prove that a component is absent (library topic `sbom`). This matters for DEC-001: a model that reads an SBOM as a full list will draw wrong conclusions whenever completeness is unknown or unstated.

**Vulnerabilities and weaknesses.** A top-level `vulnerabilities` list records "vulnerabilities identified in components or services" (`cyclonedx-1-7`). Each entry points at what it hits through `affects`, lists the weakness types behind it in `cwes`, and can carry an `analysis`: the author's answer to "does this actually affect us?", known as VEX (VEX itself is in scope for RPT-0005, #39). The analysis has a `state` (for example `exploitable`, `not_affected` or `false_positive`), a `justification` (for example `code_not_reachable` or `protected_by_mitigating_control`), a `response` (for example `update` or `will_not_fix`), a free-text `detail`, and timestamps for when it was first issued and last updated.

Three things stand out. First, `cwes` is the only CWE field, so a component links to a weakness only through a vulnerability entry, and each CWE is a bare integer ("For example 399") rather than a string like "CWE-399". Second, unlike `dependsOn`, `affects` accepts a BOM-Link, so a vulnerability report can live in a separate file and still point into a product's SBOM. Third, the analysis is again a claim: `not_affected` "should" come with a justification, but the schema does not require one. Several justifications (`code_not_reachable`, `requires_configuration`, `protected_at_perimeter`, `protected_by_mitigating_control`) are threat-model conclusions in their own right, which makes this a direct link between an SBOM and tmodel's model (DEC-001) and its CWE/NVD integration (DEC-008).

**Takeaway:** CycloneDX 1.7 can express identity, hardware, three kinds of relationship, completeness and vulnerability status, but almost all of it is optional, and most of it is a claim by whoever wrote the SBOM: identifiers are asserted, a missing dependency entry means "unknown", completeness can simply be left unstated, hardware details live outside the schema, and exploitability is the author's assessment. What a real SBOM actually contains depends on the tool that wrote it (section 3).

### 1.2 SPDX 3.0.1 (`spdx-3-0-1`)

**Naming a component.** In SPDX a software package is a `Package` element, and its model text requires only three things: an `spdxId`, a `name` and a `creationInfo` (the SHACL shapes and the JSON Schema do not enforce `name`; fanout-formats-baselines.md, test M4); even `packageVersion` is optional (`spdx-3-0-1`). The `spdxId` is the big difference from CycloneDX: it is a URI that "uniquely identifies an Element", and references to it "may be internal or external": an `spdxId` is global in itself, while a CycloneDX `bom-ref` is unique only within its file and needs a BOM-Link to be reached from another. The other identifiers live in four places:

| Where | What goes there | Kind |
|---|---|---|
| `packageUrl` | the package's purl | assigned name |
| `externalIdentifier` | an ID typed from a fixed list: `cpe22`, `cpe23`, `packageUrl`, `swid`, `gitoid`, `swhid`, plus types for other kinds of element such as `cve` and `email` | mostly assigned names |
| `contentIdentifier` | "a canonical, unique, immutable identifier of the content": a `gitoid` or `swhid` | computed from bytes |
| `verifiedUsing` | a `Hash` (an `algorithm` plus a `hashValue`) or another integrity method | computed from bytes |

Three things stand out. First, SPDX treats content-based IDs as a way to verify, not just to name: `ContentIdentifier` and `Hash` are both kinds of `IntegrityMethod`, "an independently reproducible mechanism that permits verification", while CycloneDX words `omniborId` and `swhid` as identity claims. Second, one ID can go in two places: a purl fits both `packageUrl` and an `externalIdentifier` of type `packageUrl`, and neither entry says which to use, whereas gitoid gets an explicit rule (a gitoid of the artifact goes in `contentIdentifier`, one of its input manifest in `externalIdentifier`). Third, the same name points to different standards: SPDX's `swid` is a CoSWID tag (RFC 9393), the CBOR-based concise form of SWID, while CycloneDX's `swid` holds the fields of an XML ISO/IEC 19770-2 SWID tag; the two are closely aligned but encoded differently (see 1.3). For DEC-002, a tool importing both formats has to read purls from two SPDX places and reconcile SPDX's global `spdxId` with CycloneDX's file-local `bom-ref`.

The hash lists differ too. SPDX defines a hash algorithm as "a one-way function", yet its list includes the Adler-32 "checksum", MD2 and MD4 (both moved to Historic status by the IETF in RFC 6149 and RFC 6150), and Kyber and Dilithium, which NIST standardizes as a key-encapsulation mechanism and a digital signature scheme rather than as hashes (FIPS 203, FIPS 204). Ten SPDX values have no match in CycloneDX's list (`adler32`, `md2`, `md4`, `md6`, `sha224`, `sha3_224`, the three post-quantum values and `other`), and CycloneDX's Streebog can only become SPDX's generic `other`, so converting between the formats can lose a hash or its algorithm name.

**Hardware and firmware.** SPDX 3.0.1 has no hardware profile or hardware element: none of its ten profiles covers hardware, so a chip can only be described as a software artifact, such as a `Package`, whose `primaryPurpose` is `device` ("The Element refers to a chipset, processor, or electronic board") (`spdx-3-0-1`). `firmware` and `deviceDriver` are purposes too, and the spec calls a purpose "a reasonable estimate of the most likely usage of the Element", "intrinsic to how the Element is being used rather than the content of the Element", so `device` is a usage label, not a hardware type. There are no hardware fields either: the model has nothing for a serial number, MAC address or manufacturer, and defines no hardware property names of its own, so such details would have to go in an `extension`, for example a `CdxPropertiesExtension`, which the spec says is intended to be compatible with CycloneDX properties and so could carry CycloneDX's `cdx:device` names. Assemblies can be written with the generic `contains` relationship ("The `from` Element contains each `to` Element"), but unlike CycloneDX's `device`, SPDX's `device` and `firmware` entries give no rule for separating a device from its firmware. For hardware, SPDX 3.0.1 offers even less than CycloneDX (DEC-001).

**Dependencies.** In SPDX a relationship is an element of its own (`Relationship` is a subclass of `Element`, so it has its own `spdxId`), with one `from`, one or more `to`, and a required `relationshipType` chosen from 59 values (`spdx-3-0-1`). The dependency-related types are finer-grained than CycloneDX's single `dependsOn`:

| SPDX type | Meaning |
|---|---|
| `dependsOn` | "depends on each `to` Element" |
| `hasStaticLink`, `hasDynamicLink` | links the `to` element in statically or dynamically |
| `hasOptionalDependency` | "optionally depends on" |
| `hasProvidedDependency` | the dependency "is not in the distributed artifact, but assumed to be provided" |
| `hasPrerequisite` | "has a prerequisite on" |
| `contains`, `hasOptionalComponent` | containment, like CycloneDX's nested `components` |

Three things stand out. First, "none" and "no claim" are explicit: to assert that no such relationships exist, `to` holds the special `NoneElement`, and to make no assertion it holds `NoAssertionElement`, where CycloneDX relies on an empty `dependsOn` versus a missing entry. Second, because every element has a global `spdxId`, a relationship's `from` and `to` can name elements in other documents, which CycloneDX's `dependsOn` cannot. Third, `LifecycleScopedRelationship` adds a `scope` of `design`, `development`, `build`, `test`, `runtime` or `other`, which says when a relationship applies; CycloneDX's `scope` (`required`, `optional`, `excluded`) says instead whether a component is reachable at runtime, so the two "scopes" do not map one to one. The richer relationship vocabulary bears on DEC-001, and the cross-document links on DEC-002.

**Completeness.** SPDX states completeness on each relationship rather than in a separate list: `completeness` is an optional property of `Relationship` with three values, `complete` ("known to be exhaustive"), `incomplete` ("known not to be exhaustive") and `noAssertion` (`spdx-3-0-1`). Because it sits on the relationship itself, it can be stated for any of the 59 relationship types, not only dependencies. Compared with CISA's four levels (`cisa-framing-software-component-transparency`, §2.2.2.6.4; as in 1.1, the alignment is ours, based on the definitions):

| CISA | SPDX 3.0.1 | CycloneDX 1.7 (see 1.1) |
|---|---|---|
| Known | `complete` | `complete` |
| Partial | `incomplete` | `incomplete` and six narrower variants |
| Unknown | `noAssertion`, or `NoAssertionElement` in `to` | `unknown` or `not_specified` |
| None | `NoneElement` in `to` | an empty `dependsOn` entry |

Two things stand out. First, SPDX has a named value for "none" (`NoneElement`) that works for any relationship type, but it merges what CycloneDX splits: `NoAssertionElement` covers a creator who "attempted to but cannot reach a reasonable objective determination", one who "made no attempt", and one who "intentionally provided no information", so a reader cannot tell a failed search from no search. Second, `completeness` is optional, neither its property page nor its value list states a default, and unlike CycloneDX, SPDX's `dependsOn` does not say whether it lists only direct dependencies, so "complete" does not say how deep the list goes. As in CycloneDX, "none" and "complete" are the author's assertions, not proof (DEC-001).

**Vulnerabilities and weaknesses.** In SPDX a vulnerability is an element of its own (`Vulnerability`, a kind of `Artifact`), named like anything else through `externalIdentifier`, for example of type `cve` (`spdx-3-0-1`). Everything else is a relationship: `hasAssociatedVulnerability` links "a `from` Artifact with each `to` Vulnerability"; other types record who found, reported, published or republished it ("i.e. NVD"); and each assessment is a relationship class of its own, running from the vulnerability to the products it concerns:

| Assessment | SPDX 3.0.1 relationship class |
|---|---|
| VEX affected | `VexAffectedVulnAssessmentRelationship` (requires an `actionStatement`) |
| VEX not affected | `VexNotAffectedVulnAssessmentRelationship` (optional `justificationType`, one of five) |
| VEX fixed | `VexFixedVulnAssessmentRelationship` |
| VEX under investigation | `VexUnderInvestigationVulnAssessmentRelationship` |
| Severity and priority | CVSS v2, v3 and v4, EPSS, exploit catalog (`kev` or `other`), SSVC |

Three things stand out. First, SPDX supports CWEs but has no dedicated CWE field: a weakness is attached as an external reference (`externalRef`) of type `cwe` ("a reference to a source of software flaw defined within the official CWE List"), whose value goes in a free-text `locator`, where CycloneDX has a dedicated `cwes` list of integers. Second, the VEX vocabularies differ: SPDX has four statuses and five justifications (`componentNotPresent`, `vulnerableCodeNotPresent`, `vulnerableCodeNotInExecutePath`, `vulnerableCodeCannotBeControlledByAdversary`, `inlineMitigationsAlreadyExist`), CycloneDX six states and nine justifications, and neither specification maps its values onto the other's. SPDX's four statuses and five justifications match those in CISA's Minimum Requirements for VEX (§2.7.1); the comparison table shows how CycloneDX's own examples line its states up with them. Third, SPDX is stricter in one place and not in another: an "affected" statement must carry an `actionStatement` (CycloneDX's `response` is only "strongly encouraged", and only when a vulnerability is exploitable), but for "not affected" the spec says one of `impactStatement` or `justificationType` "MUST be defined" while giving both a cardinality of 0..1, "making them optional". SPDX also covers EPSS and exploit catalogs such as KEV, which CycloneDX 1.7 has no field for. This bears on DEC-008 (CWE/NVD integration) and, since VEX statuses become typed links between vulnerabilities and products, on DEC-001.

**Takeaway:** SPDX 3.0.1 is built as a graph: every package, vulnerability and relationship is an element with a global `spdxId`, so it can link across documents, and it offers far more relationship types (59) and more kinds of vulnerability assessment (adding EPSS and exploit catalogs) than CycloneDX. It is weaker where CycloneDX is strong: hardware is only a purpose label, a CWE has no dedicated field (only an external-reference type), and completeness has three values with no stated default. As with CycloneDX, almost everything beyond an ID, a name and creation information is optional and asserted by the author, and some rules the text states (a "MUST" that a not-affected statement give a justification or an impact statement) are not enforced by the model.

### 1.3 SWID (ISO/IEC 19770-2)

The SWID standard itself, ISO/IEC 19770-2:2015, is paywalled and was not read for this report. ISO's own metadata lists this second edition, published 2015-09-30, as current: nothing replaces it, and its stage code 90.60 marks the close of a review whose outcome the metadata does not show (ISO Open Data, `iso_deliverables_metadata`, checked 2026-09-30 and again 2026-10-18; stage names from ISO's stage-codes page. 0.1.0 cited ISO Guide 69:1999 here, which ISO withdrew on 2014-06-18). This section relies on two public sources: NIST IR 8060, NIST's guidelines for creating interoperable SWID tags, which reports the standard's requirements for each tag element, and RFC 9393, which defines Concise SWID (CoSWID) tags as a CBOR-based "more concise representation of SWID information" whose data definition "is aligned with" the standard's XML schema. Where only CoSWID is described, the text says so.

SWID also has a different shape from the other two formats. A tag describes one piece of software, and a primary tag "is intended to be installed on an endpoint along with the corresponding software component" (RFC 9393 §1.1), so an inventory is a collection of tags rather than one document. There are four tag types: primary, patch, corpus (software before installation) and supplemental (extra information about another tag).

**Naming a component.** The standard requires a `name` and a `tagId`, and "every tag contains an <Entity> element identifying the tag creator"; `version` is optional and "defaults to "0.0"", although NIST's guidelines require it in primary and corpus tags (NIST IR 8060 §3.1.1, §3.1.2). The `tagId` is a built-in global identifier: RFC 9393 says it "MUST be globally unique" and "serves as the global key for matching and lookups", written for example as a UUID or as a DNS domain name followed by "/" and a string (§2.3). There is no purl or CPE field (neither word appears in RFC 9393); NIST IR 8060 instead describes generating a CPE name from a tag's metadata (§5.2.4). Content enters through file lists: in an authoritative tag, "Every <File> element within a <Payload> element MUST include a hash value" (GEN-16, §4.6.1), where an authoritative tag creator is the software's creator or a party that aggregates, distributes or licenses it on the creator's behalf (§4.2). CoSWID accepts only hash algorithms from IANA's "Named Information Hash Algorithm Registry": "other hash algorithms MUST NOT be used" (RFC 9393 §2.9.1).

**Hardware and firmware.** SWID covers software only: neither "hardware" nor "firmware" appears in RFC 9393, the four tag types all describe software, and NIST IR 8060 mentions hardware only when defining which files count as executable (§5.2.3). A device cannot be described.

**Dependencies.** Relationships are `link` entries with an `href` and a `rel`, and RFC 9393 says its rel values "match the link rel values defined in the ISO/IEC 19770-2:2015 specification" (§2.7, §4.4). The dependency-like links are about installation rather than running: `requires` "references a prerequisite for installing this software", and a link's optional `use` (`optional`, `required` or `recommended`, each quoted "From [SWID]") says whether the linked software "has to be installed before installing" this one (§2.7, §4.5). The other values cover bundles (`component`, `parent`), history (`ancestor`, `patches`, `supersedes`), installers (`installationmedia`, `packageinstaller`), `feature`, `see-also` and `supplemental`, and `rel` may also be any name from IANA's "Link Relation Types" registry (§2.7); none of the registered values describes using another component at runtime. Because an `href` can name another tag as `swid:` plus its tag ID, links cross tags by design.

**Completeness.** Neither source describes a completeness field. RFC 9393 warns that "any collection of CoSWID tags cannot automatically be assumed to represent either a complete or fully accurate representation of the software inventory of the endpoint", partly because "not all software products automatically install CoSWID tags" (§9). Within a tag, NIST's guidance is that `<Payload>` and `<Evidence>` "SHOULD list every file comprising the product described by the tag", with executable files as the minimum (NIST IR 8060 §5.2.3, PRI-8).

**Vulnerabilities and weaknesses.** SWID carries no vulnerability data: CoSWID's data definition has no field for CVEs, CWEs or VEX. Tags are meant to be matched against vulnerability information instead. RFC 9393 lists "Vulnerability Assessment, which requires a semantic link between standardized vulnerability descriptions and software components" among the uses of SWID tags (§1), a `link` can point to a "vulnerability database association" (§2.3), and NIST IR 8060 describes forming CPE names from tags so that bulletins naming products by CPE can be matched to endpoints (§6.1.3).

**Takeaway:** SWID is an identification and inventory format rather than a composition graph: each tag names one piece of software with a globally unique `tagId` and lists its files with hashes, its dependency-like links are about installation, and it has nothing for hardware, completeness or vulnerabilities. Its most useful idea here is the explicit difference between authoritative tags, made by the software's creator or its distributors, and non-authoritative tags, typically made by discovery tools (NIST IR 8060 §4.2), which bears on how much an imported identity can be trusted (DEC-002). The standard itself was not read (paywalled).

### 1.4 The SPDX 3 RDF model

SPDX 3.0.1 is defined as an RDF model: an OWL ontology with SHACL shapes, in one Turtle file (`spdx-3-0-1`). Documents are JSON-LD, and the specification counts a document as conformant only if it passes two checks: structural validation against the SPDX JSON Schema, and semantic validation against the OWL ontology with its SHACL shapes (`serializations.md`, "JSON-LD validation"). This bears on DEC-004 (graph substrate) and on ADR-0004's RDF adapter. Phase 1 loaded nine official examples (the specification's own and eight from SPDX's examples repository) with rdflib, tried PyLD on the specification's example, and ran test documents that each break one rule (`fanout-formats-baselines.md`, section 7).

**Can a document be loaded into an RDF store as it is?** Yes, with four caveats.

1. **The context is remote.** Every document names `https://spdx.org/rdf/3.0.1/spdx-context.jsonld`, which redirects to `spdx.github.io`. rdflib 7.6.0 followed the redirect and loaded all nine examples (47 to 983 triples each). PyLD 3.3.0 needed a document loader set up first, and then produced the same triples for the specification's example, apart from how it typed plain strings (tests T1, T4).
2. **Unknown keys vanish.** The context has no top-level `@vocab`, so a key it does not define is dropped without a warning (test M9).
3. **Relative identifiers depend on the file's location.** A relative `spdxId` such as `Package1` becomes an IRI relative to wherever the file was loaded from, and a misspelt `type` becomes a relative class IRI (tests M11, M20).
4. **Each version has its own vocabulary.** Term IRIs carry the version (`/3.0.1/`, `/3.1/`, and `/3.0/` planned for 3.0.2; §1.6), so a store holding documents of several versions holds several vocabularies, and the model files map none of them onto another.

**What each layer checks.** The JSON Schema checks structure: the exact `@context` string, each object's `type`, known keys only, required properties, enumerations, and patterns for IRIs, timestamps and versions. It cannot check that a reference points to an element of the right class. In one place it is stricter than the text: the text allows extra namespace mappings in the context, and the schema rejects them (test M10). The SHACL shapes check the graph: the class of each referenced element, that every Element is an IRI, cardinality (for example exactly one `relationshipType` and one `creationInfo`), vocabularies, datatypes, timestamp patterns and abstract classes (tests M1 to M3, M8, M14, M17). They cannot see keys that JSON-LD processing has already dropped, and they reject any reference to an element defined in another document: plain pySHACL fails two of the nine official examples for that reason, while spdx3-validate 0.0.7, which the SPDX specification repository uses to check its examples, works around it (tests T2, T3; M15, M16).

**What neither layer checks.** The 14 cardinality rules written under "External properties restrictions" (for example, that a Package has a `name`); every profile-conformance rule (AI, Dataset, Licensing, Lite); the VEX "not affected" rule that one of two properties "MUST be defined", and the same class's limits on its relationship type and its `from` element; the rule that a serialization "MUST NOT contain more than one SpdxDocument"; and value-level rules such as a valid purl or a hash of the right length (tests M4 to M6, M12, M13, T7 to T9). One official example declares conformance to the AI profile, breaks that profile's MUST, and still passes the JSON Schema, pySHACL and spdx3-validate (test T7). §1.5 sets this against the other formats.

**Which model file.** The model served at the 3.0.1 URL is not the file at tag 3.0.1. Apart from the ontology's label, they differ in one shape, the one for the `extension` property of `Core/Element`: the tagged file requires the value to be an `Extension`, while the served file only excludes 54 classes known not to be extensions, so a validator that fetches the served model accepts more (`fanout-formats-baselines.md` §1.3; `sources.md` pins both files by hash).

**For DEC-004 and ADR-0004 (our reading).** An RDF import of SPDX should run the JSON Schema before JSON-LD expansion, to catch the dropped keys and relative IRIs that SHACL can no longer see; it should use a cached context and model pinned by hash rather than the live URLs; and it should handle references to other documents (`ExternalMap`) the way spdx3-validate does, or plain SHACL validation will reject valid documents.

**The pattern (our reading).** In all three formats the machine layer checks each object's shape: structure, types and vocabularies. Rules that involve two objects (uniqueness, references, "one of", "exactly one per package", "not with that type"), the whole document, or the meaning of a value exist only in the text. SPDX is the only format with a second, graph-level layer (SHACL), and even that holds none of its profile rules. ECMA-424 says as much about CycloneDX: it "does not define enforcement mechanisms for verifying the accuracy or completeness of a BOM" (§1, NOTE 2).

**How the rules are worded.** The three texts mark requirements differently. ECMA-424 uses ISO's verbal forms: lowercase "shall" occurs more than 700 times, and its only two uppercase BCP 14 keywords (the IETF convention of MUST, SHOULD and MAY) are in licence boilerplate. The CycloneDX 1.7.2 JSON Schema has 29 uppercase keywords, all SHOULD, beside more than 50 lowercase "must"; its uppercase MUSTs became lowercase in 1.6.1. SPDX 3.0.1 mixes the two, and 3.1-RC1 moves to "shall". RFC 9393 declares BCP 14 and uses its keywords 99 times. A count of uppercase keywords, such as the one the library's FX-1 check makes, therefore misses almost all of ECMA-424's requirements.

**For DEC-002 (our reading).** Passing a format's schema says little about whether an SBOM can be used. An importer has to check for itself what the schemas leave to the text: unique `bom-ref`s, dependency targets that exist, valid purls, real timestamps and the profile rules. It also has to read a missing dependency entry as "unknown" (X15).

### 1.6 What changed, and what comes next

For an importer, versions matter as much as formats. This section lists the changes that affect one, and where the next versions stood on 2026-10-22.

**CycloneDX 1.6 to 1.7.** Between the JSON Schemas at tags 1.6.2 and 1.7.2, 17 definitions were added and none removed, and no `required` list changed (`cyclonedx-1-7`). The additions include a top-level `citations` list, a TLP distribution constraint in `metadata`, `isExternal` and `versionRange` on components, patent fields, many cryptographic-asset fields, and two hash algorithms (Streebog-256 and Streebog-512). Two changes need importer code (our reading). First, licences: 1.6.2 allowed either a list of licences or a single expression, and 1.7.2 allows an array whose items may each be a licence or an expression, so several expressions, or licences mixed with expressions, are now valid. Second, a component may carry `versionRange` (a `vers` string) instead of `version` when it is external. The patch releases change nothing structural for a JSON importer: 1.7.1 changed only descriptions and comments (five typo fixes and one new SHOULD sentence on `ratings`), and 1.7.2 only the XML schema.

**The next CycloneDX.** Version 2.0 is being written in the open: pull request #652 was still a draft on 2026-10-22, and its milestone, due 2026-08-31, still had 87 of its 183 issues and pull requests open. The draft drops the XML and Protocol Buffers schemas, splits the schema into modules, and moves a component's identifiers into `identifiers[]` entries, each naming the party that asserts them; the 1.x fields `purl`, `cpe`, `swid`, `omniborId`, `swhid`, `supplier`, `manufacturer`, `authors` and `publisher` are not in its component (`fanout-formats-baselines.md` §1.2, at the `2.0-dev` commit of 2026-10-07). It also adds hardware fields and threat, risk and weakness modules. Our reading: an importer written for 1.x will not read 2.0 unchanged. There is no 1.8 milestone; a 2.1 milestone is due 2027-04-16. One tool already writes the draft: cdxgen's `--spec-version` accepts "1.6, 1.7, and 2.0" (its README at commit 388f434, 2026-09-30; no library record), so CycloneDX 2.0 draft documents can already exist (our reading). In ISO, CycloneDX is DIS 27055 at stage 40.00 (§1).

**SPDX 2.3 to 3.0.** SPDX's annex "Differences from previous editions" (informative; cited under `spdx-3-0-1`) lists breaking changes for a 2.3 importer. References to other documents become `NamespaceMap` and `ExternalMap`; creators become Agent and Tool elements; supplier and originator become `suppliedBy` and `originatedBy`; external references split into `externalIdentifier`, `contentIdentifier` and `externalRef`, with purl getting its own `packageUrl` property; Annotation and Relationship become Elements; the specification version and licence-list version must be SemVer; and the Tag/Value, YAML, RDF/XML and spreadsheet formats are no longer supported. In the annex's 45-row relationship mapping, 34 types reverse direction (for example, `DEPENDENCY_OF` becomes `dependsOn` with `from` and `to` swapped). One row looks wrong (our reading): it swaps `DYNAMIC_LINK` but not `STATIC_LINK`, although both 2.3 definitions and both 3.0.1 definitions run the same way, so an importer that follows the table would reverse dynamic links. The annex also mentions a completeness default that the 3.0.1 model does not define (§1.2), and calls RDF/XML unsupported while the serialization text lists it.

**SPDX 3.0 to 3.0.1.** Several terms were renamed (`imports` to `import`, `parameters` to `parameter`, `hasInputs` and `hasOutputs` to `hasInput` and `hasOutput`, and the misspelt `hasPrerequsite` to `hasPrerequisite`), `contentType` was removed from the Software profile, and the namespace became `https://spdx.org/rdf/3.0.1/terms/`, so 3.0 and 3.0.1 documents do not share term IRIs.

**The next SPDX.** 3.1 exists only as a release candidate: 3.1-RC1, a pre-release of 2026-01-24. On 2026-10-22 the 3.1-rc2 milestone, due 2026-09-27, still had 27 of its 110 issues and pull requests open in the model repository. RC1 adds Hardware, Service, SupplyChain, Operations and FunctionalSafety namespaces; relaxes the AI and Dataset rules (pull request #1158), dropping the required release time and download location from both, the supplier and package version from AI packages, the build time and originator from Dataset packages, and the licence conformance rules, while keeping `primaryPurpose` required; and moves to ISO's "shall". Its namespace is `https://spdx.org/rdf/3.1/terms/`, and the 3.1 context URL already serves the RC1 context, so a document that points at it today is read with a pre-release vocabulary (our reading). The 3.0 maintenance line is going back to `/3.0/` IRIs (pull request #1051, for 3.0.2, whose milestone was due on 2026-04-30 and is still open), so, if 3.0.2 is released, its documents would not share term IRIs with 3.0.1 ones (our reading). In ISO, SPDX 3.0 is ISO/IEC PRF 5962 at stage 50.20 (§1).

**For DEC-002 (our reading).** An importer has to pin the exact version of each document and keep a mapping per version, because SPDX's term IRIs change with every version and CycloneDX 2.0 renames the identity fields. SPDX 2.3 still matters while tools write it (see "Formats not in Table 1").

## 2. HBOM (hardware and firmware)

Input to DEC-001.

**The reference.** The main public guidance is CISA's *A Hardware Bill of Materials (HBOM) Framework for Supply Chain Risk Management* (September 2023; `cisa-hbom-framework-2023`), written by the HBOM working group of the ICT Supply Chain Risk Management Task Force "to create a consistent, repeatable way for vendors to communicate with purchasers of hardware components" (§1). NTIA's SBOM minimum elements leave hardware out of scope (`ntia-sbom-minimum-elements`, §III). The framework sorts HBOM use cases into three categories (Appendix A, Table 1): Compliance, for example laws that may prohibit certain components; Security, meaning "exposure to known vulnerabilities and/or high susceptibility to untrusted entities/geolocations"; and Availability, the effect of world events and of too little supplier diversity. CISA has not updated the framework since it was published.

**What an HBOM records that an SBOM does not.** The framework's taxonomy has 47 fields in seven categories: header information, finished-good product details, entity names, entity locations, component part information, component part details and production details (Appendix C.1 to C.7). Most describe the physical supply chain rather than code: the contract manufacturer and the assembly-and-test supplier; the locations of the product's supplier, its manufacturers, the component manufacturer and the assembly-and-test site, with coordinates and location codes; the manufacturer's part number; the semiconductor technology node; the share of a part sourced from a supplier; lead times, quantities and date codes. For semiconductors it asks for the supplier and the fab or foundry "as separate data points" (Appendix B.1.3). Parts are typed only loosely: `COMP_TYPE` is "hardware", "software" or "service", and `COMP_PART_TYPE` is a free-text "Component category (e.g., semiconductor, antenna, etc.)", so the parts issue #8 names, such as buses and compute cores, have no field of their own. Firmware is covered thinly: the framework "provides basic information about including the firmware associated with the products' components (i.e., the provider of the firmware), but stops short of proposing a framework for examining the provenance and other attributes of that firmware" (§1.3). It also describes product and part types, not single units: there is no serial-number field, and its only firmware field is a version string shared by hardware, software and firmware versions. Its hash fields do not clearly hold a digest (our reading): `FGA_HASH` and `COMP_HASH` are each described as "An intrinsic identifier", with a UUID as the example, although CISA maps `COMP_HASH` to CycloneDX hashes and SPDX's PackageChecksum. Two kinds of source fill those gaps: CERT-In's guidelines list unit facts such as serial numbers and manufacturing dates (Table 11; `cert-in-2025-aibom-guidelines`), and attestation standards record what a device reports about itself, signed (Table 4b).

**How it fits the SBOM formats.** The framework defines fields and a nesting layout rather than a file format, and its layout example "is suggested for spreadsheet HBOMs": each assembly gets its own HBOM, joined to its parent through part-level information (Appendix B.1.1). It maps its fields to CycloneDX and SPDX "where possible", but of the 47 fields, 37 list no CycloneDX equivalent and 36 no SPDX equivalent (the SPDX mappings use older SPDX 2.x field numbers). Fields such as country of origin cannot be mapped one to one, and where no field exists "the developer should create a user-defined field" (Appendix B.2). The framework calls this area immature, since "further work will be required to achieve the necessary maturity for true interoperability" (§1.2), and it leaves SBOM information out of scope while recommending future work so it "can merge with emerging SBOM frameworks" (§1.3). Those counts are CISA's own 2023 mapping, made against CycloneDX 1.5-era fields and SPDX 2.2 clause numbers. Our reading of the 47 fields against the current schemas finds a native field, exact or close, for 24 in CycloneDX 1.7.2 (9 exact, 15 close) and 19 in SPDX 3.0.1 (7 exact, 12 close); the others need properties or extensions (field by field in `fanout-hardware.md` §3.3). The unreleased next versions cover far more (also our reading): the CycloneDX 2.0 draft 40 fields, and SPDX 3.1's development model, with its Hardware and SupplyChain profiles, 38.

**What the formats offer today.** Of the three formats in section 1, only CycloneDX has hardware support beyond a purpose label: a `device` type, a rule for separating a device from its firmware, nesting for assemblies, and hardware details as `cdx:device` properties outside the schema (1.1; `cyclonedx-property-taxonomy`). CycloneDX presents HBOM as covering "processors, embedded systems, IoT devices, and industrial control systems" (CycloneDX HBOM capability page). Its property list covers a few of the framework's fields, such as quantities (`cdx:device:quantity`) and lot or date codes (`cdx:device:lotNumber`, `cdx:device:prodTimestamp`), and adds details the framework does not ask for, such as serial numbers, board locations and GS1 product codes. CISA's mapping lists no CycloneDX field for locations, but in CycloneDX 1.7 an organization, such as a component's `manufacturer` or `supplier`, can carry a postal `address` with a `country`, which covers part of the location fields; coordinates, location codes, technology node, sourcing share and lead times still have no field. SPDX 3.0.1 has only purpose labels (`device`, `firmware`, `deviceDriver`) and no address field, and SWID has nothing for hardware (1.2, 1.3).

**How firmware is tied to its device.** The sources tie firmware to hardware in six ways, from weakest to strongest (our ordering): by prose only (the CISA framework); by containment with a recommendation (CycloneDX's `device` rule and a nested `firmware` component; in SPDX 3.0.1 only a generic `contains`); by a typed relation (SPDX 3.1's `runsOn`, Redfish's `SoftwareInventory.RelatedItem`, CoRIM's reference triples; SUIT's vendor, class and device conditions are compatibility checks, not identity); by construction, with the SBOM embedded in the firmware image itself (below); by a signed report from the device (SPDM measurements signed with the device's identity key, EAT measurements in a signed token); and by key derivation (DICE, where the firmware's measurement feeds the key that signs the next certificate).

**Buses, compute cores and firmware components.** Of the parts issue #8 lists, firmware components are the easy case: almost every source can name them (the CISA framework and CERT-In only in prose or a version string). Buses are the hard one. Only Redfish has first-class interconnect resources (`PCIeDevice`, `PCIeFunction` with bus, device and function numbers, `Port`, `PCIeSlots`, cables); TCG derives component ids from PCIe configuration space but records no topology; and no SBOM format, current or draft, nor the CISA framework or CERT-In, has a bus or interconnect relation. Compute cores appear only in Redfish (`ProcessorType` values `Core` and `Thread`, with `SubProcessors`). TCG and the CycloneDX 2.0 draft classify processors (CPU, GPU, SoC) but not cores, and CycloneDX's and SPDX's `device` cover a processor only as a broader type.

**Firmware bills in practice.** Open firmware projects publish composition as CoSWID tags (RFC 9393) in CBOR, embedded in the firmware image: in a PE `.sbom` section or behind a uSWID header (`osfw-firmware-embedded-sbom-0-10`; `rfc-9393`, whose recorded implementations include python-uswid and coreboot's SBOM support), or, in coreboot, as a file in its CBFS ("The final SBOM file is located inside the CBFS", coreboot's SBOM documentation). uSWID is a header defined by the python-uswid tool and required by the Open-Source Firmware Foundation's Firmware Embedded SBOM Specification 0.10 (§4.6), a 2024 pre-release, not a standard. That specification asks for a GUID tag id, a name, a version, tag-creator and software-creator entities and, for built binaries, hashes of the source file and the source tree, which it stores in CoSWID's `colloquial-version` and `edition` fields, although RFC 9393 defines those fields differently. LVFS, the Linux firmware update service, scans every upload for these tags (`lvfs`) and "generates a HTML page with SPDX, SWID and CycloneDX download links" (`osfw-firmware-embedded-sbom-0-10`, §7.6); python-uswid itself exports CycloneDX 1.6 and SPDX 2.3. coreboot's SBOM is opt-in, and its templates name coreboot as the tag creator even for Intel's binary blobs. The UEFI Forum's SBOM sub-team proposed this approach in 2023, and a 2024 Plugfest deck asks vendors for firmware SBOMs in SWID, SPDX or CycloneDX (`uefi-firmware-sbom-proposal-2023`). Embedded Linux and RTOS builds write SPDX instead: the Yocto Project's OpenEmbedded-Core does so by default, SPDX 3.0.0 in Yocto 5.1 and 3.0.1 from 5.2 (an implementation listed under `spdx-3-0-1`), and Zephyr writes SPDX 2.3 by default, with 3.0 and 3.1 options only on its development branch (no library record). In all of them the hardware appears at most as a build input (`MACHINE`, `BOARD`, the target processor), never as a hardware element.

**Device identity and attestation as measured bills.** Attestation and device-identity standards do record what a device contains, but each records a different slice (Table 4b). TCG's platform certificate and Redfish list hardware parts; DICE, SPDM and EAT measure firmware and report it signed by the device; CoRIM and the platform certificate hold a supplier's signed expectations, against which a verifier compares what the device reports. Only the TCG Platform Certificate Profile 2.1 (country of origin, entity locations) and Redfish (an assembly's country of origin) record any supply-chain origin. Their status varies. The platform certificate profile 2.1 was published on 2026-01-27; of the NSA's open-source tools, PACCOR (v2.0r16) supports 2.1 but by default writes version 1.1 certificates, and HIRS (v3.2.0) validates version 1.1 certificates, with 2.0 support in development and not 2.1 (`tcg-platform-certificate-profile-2-1`; the PACCOR and HIRS READMEs and HIRS documentation). CoRIM is an Internet-Draft in working-group last call (draft-11, 2026-07-06), and the SUIT manifest draft is in the RFC Editor's queue, waiting on five unpublished SUIT drafts it cites.

**ISO/IEC 19770-6:2024.** ISO also publishes a hardware counterpart to SWID: ISO/IEC 19770-6:2024, *Hardware identification tag*, published 2024-01-26, 41 pages, at stage 60.60 (`iso-iec-19770-6-2024`). According to ISO's own metadata, it "provides specifications for a transport format" for "hardware identification (HWID) data", which it calls "a HWID tag, just as ISO/IEC 19770-2 refers to software identification (SWID) tags", and it "deals only with hardware device or component identification" (ISO Open Data, `iso_deliverables_metadata`). The standard is paywalled. BSI's 8-page public preview shows its contents list, foreword and part of its introduction; the contents list names primary and system HWID types, a clause on systems of systems, signatures in XML and JSON, and data definitions named `HWID`, `HWIDMeta`, `Entity`, `Link`, `LinkContent`, `Meta`, `OrderInfo` and `Location`. Which fields these hold, which are required, and whether any tool writes HWID tags is unknown; whether the project can get a copy is sponsor question 4 in `dimensions.md`.

**Hierarchical systems.** Every source has some way to say that one part contains another: CycloneDX's nested `components` and `compositions[].assemblies` (with `boardLocation` in the 2.0 draft); SPDX's `contains` (and assembly processes in the 3.1 draft); the CISA framework's one HBOM per assembly; CERT-In's recursive sub-component element; Redfish's `Chassis` links (`Contains`, `ContainedBy`), `Assembly`, `SubProcessors` and `PartLocation`; TCG's flat component list, which can point to a component's own platform certificate (`componentPlatformCert`) and records later changes in Delta certificates; CoRIM's domain-membership graphs; EAT's nested `submods`; the composite device of the RATS architecture (`rfc-9334`); and ISO/IEC 19770-6's system HWIDs, known only from its contents list. For vehicles, no public HBOM guidance for a vehicle or its control units was found. Auto-ISAC's SBOM report covers software SBOMs across supplier tiers and recommends SPDX or CycloneDX JSON (`auto-isac-sbom-ir-v3`). UN Regulation No. 155 does not mention SBOMs (`unece-r155`), and No. 156 requires the hardware and software of a type-approved system to be uniquely identified and, "For every RXSWIN" (a software identification number the manufacturer defines), "an auditable register describing all the software relevant to the RXSWIN", with software versions and integrity validation data, but it names no format (`unece-r156`). RXSWIN and ISO 24089 belong to build identity (§6) and to RPT-0007.

**Guidance beyond CISA.** CERT-In's guidelines, version 2.0 of 2025-07-09, are the only national guidance found with an HBOM element list (Table 11); they define no format and point to "extended SBOM formats like CycloneDX or custom XML/JSON schemas" (`cert-in-2025-aibom-guidelines`). Korea has proposed an ITU-T work item, X.hbomsec, on minimum HBOM requirements (SG17 contribution 548, 2026-05-19; its text is restricted; `itu-t-sg17-c548-2026`). ISO/IEC 19770-6 is the international tag standard (above).

**Takeaway:** An HBOM is mostly supply-chain data (who made a part, where, and how concentrated its sources are), and the main public framework for it is a field list built around spreadsheets. Today's SBOM formats hold more of its fields than CISA's 2023 mapping says, but no SBOM format, current or draft, has a bus or interconnect relation or a compute core, and none records what a device reports about itself: that lives in attestation and inventory standards (DICE, SPDM, EAT, Redfish, TCG). For tmodel, hardware needs object types or attributes of its own (DEC-001); importing it today means CycloneDX `device` components plus properties, and CycloneDX 2.0 and SPDX 3.1 would add native hardware classes once released (DEC-002). Firmware is where hardware links back to software and its vulnerabilities, and firmware bills already exist (CoSWID tags inside the image, SPDX from Yocto); attestation could later let tmodel compare a device's measured firmware with its declared bill (our reading).

**Syft produces the SBOM.** It writes CycloneDX (JSON or XML), SPDX 2.1 (tag-value only), 2.2, 2.3 or 3.0.1, and its own JSON format. In the CycloneDX output of every run, each package got a purl and at least one CPE, and no package got a hash or a supplier; file components got hashes (SHA-1 and SHA-256 for all 78 Alpine files). Syft's SPDX output, by contrast, carries package-level integrity values for the image packages (verification codes) and for the jar (its SHA-1), and suppliers where the package metadata names one (the apk or dpkg maintainer for 13 of 16 Alpine and 48 of 88 Debian packages, the owner of each of tradar's 9 GitHub Actions, the vendor in the jar's manifest), so the same scan carries different data depending on the output format. The Alpine, Debian and log4j packages got licences, and tradar's did not. The three multi-package SBOMs have dependency links (24 edges for Alpine, 216 for Debian, 104 for tradar; the one-package log4j SBOM has none), and no SBOM has `compositions`, `lifecycles`, `formulation`, `scope` or `evidence`. Trivy matches Debian's feed by source package, and when it reads Syft's SBOM it gets no separate source names: the source name differs from the package name for 62 of the 88 packages in Trivy's own scan, and for none when it reads Syft's SBOM. On tradar, `trivy fs` reported 12 CVEs in the first round and 14 in the second, all in `uv.lock`, and `trivy sbom` on Syft's SBOM 13 and 15; the extra one is a `python-dotenv@1.0.0` CVE from `docker/requirements-docker.txt`, which Trivy's own scan did not report. All of Trivy's tradar findings carry CWE IDs and come from GitHub advisory data (`ghsa`). On the log4j jar, `trivy rootfs` and `trivy sbom` found the same 7 CVEs as Grype, while `trivy fs` reported no language files and found none.

**The tools disagree on the same input.** Python and Java packages give the same answers: for tradar, every CVE `trivy sbom` reported is among Grype's (by CVE alias), and Grype adds only the GitHub Action advisory; for the log4j jar both found the same 7. Alpine and Debian do not. On Alpine, Grype's CPE matching against NVD data adds 14 CVEs that Trivy does not report: 13 OpenSSL CVEs on `libcrypto3` and `libssl3`, and busybox's CVE-2025-60876. On Debian, the two agree when Trivy scans the image itself (all 229 of Grype's package and CVE pairs are among Trivy's findings, and Trivy adds 6 more), but Trivy reading Syft's SBOM finds only 31. Changing the SBOM's format also loses data: Trivy finds nothing in Syft's SPDX 2.3 files of the two images (it detects no operating system in them), though it reads the Python and Java packages in the other two, and it cannot read SPDX 3 at all; Grype loses the GitHub Action matches when it reads either SPDX file. Section 5 looks at why the matching method, more than the SBOM, decides the result.

Syft, Trivy and GUAC depend on one library, spdx/tools-golang. Its SPDX 3.0.1 support was merged to its main branch on 2026-09-30 and is in pre-release tags up to `v0.6.0-rc4` (2026-06-18), but on 2026-10-22 its latest final release was still `v0.5.7` (2026-01-12). Syft uses the pre-release; Trivy 0.75.0 and GUAC's `main` pin `v0.5.7` (GUAC v1.1.0 pins `v0.5.5`), and both projects tie their SPDX 3 support to that library's (`fanout-tools.md` §2, Q4). Dependency-Track's SPDX 3 issue (#1746, "on hold") and GUAC's (#1850) were both still open on 2026-10-22. Three of the four tools added after the adversarial review (#152) write SPDX 3 without that library: sbom-tool (.NET) and cdxgen (JavaScript) with their own code, cdxgen by converting its CycloneDX output, and OpenEmbedded-Core from Python, with SPDX 3's Build and VEX elements, which Syft's output, converted from the 2.3 model, does not have. protobom, a library for reading and writing SBOM documents in either format, lists SPDX 3.0 and 3.1 as planned. None of the four was run, and none has a library record yet.

**Dependency-Track 5 (not run; from its documentation).** Dependency-Track is a server that tracks SBOMs across many projects; its current release is 5.2.0 (2026-10-08, still current on 2026-10-22), and version 4 "will reach end-of-life in December 2026" (Dependency-Track README, 5.2.0). Version 5.0 (2026-06-07) moved it to PostgreSQL only, broke parts of its REST API v1 and added a REST API v2. Two of its changes matter for composition data: the internal analyzer lost its fuzzy fallback for components without a CPE, and a new integrity check compares a BOM's hashes with those the package registry publishes (Maven, npm, PyPI). Version 5.1 added CycloneDX 1.7 uploads, mirrors of known-exploited-vulnerability lists (CISA's and ENISA's by default), a JVN data source, a Checkmarx analyzer and VEX semantics aligned with CISA's guidance; 5.2 added opt-in checksum-qualified purl matching for the Snyk analyzer (Maven components, PR #6835), PyPI name normalisation, and size limits for BOM and VEX uploads. Its formats did not change: "CycloneDX is the only format supported for uploading SBOMs to Dependency-Track", including CycloneDX 1.7; it removed its old SPDX support in 4.3.0. Its internal analyzer "Uses both CPE and PURL matching", but it "skips components that lack a valid CPE when evaluating NVD data", and "A component with neither a CPE nor a PURL is not evaluated"; its OSS Index, Snyk and Trivy analyzers use purl matching. It keeps one CPE and one purl per component and each vulnerability's CWEs, exports findings as CycloneDX VEX or VDR and "imports CycloneDX VEX documents", and lists hardware and firmware among its component types. Its documentation calls NVD "the broadest source for non-package software (operating systems, firmware, network equipment)", and it matches NVD data only through a CPE; its version 4 documentation said directly that "Non-application dependencies such as operating systems, hardware, firmware, etc, should have valid CPEs" (best practices, 4.14.5).

**GUAC (not run; from its documentation and code).** GUAC (OpenSSF; v1.1.0 of 2026-03-13, still the latest release on 2026-10-22) is not a scanner but a graph built from many documents: CycloneDX, SPDX 2.x, SLSA, in-toto, DSSE, OpenVEX, CSAF, OSV, deps.dev, OpenSSF Scorecard, ClearlyDefined and end-of-life data. Its schema has 6 noun types, among them packages (a tree of purl parts: "We represent a package by a pURL"), sources (version-control repositories) and artifacts ("we separate the algorithm used for the checksum from the digest value", GUAC GraphQL docs), and 17 evidence types, linked by 86 named kinds of edge, almost all named in both directions. Documents about the same package meet at one node through these canonical keys, while each claim stays separate, because every evidence node records its `origin`, `collector` and `documentRef`; that two names mean the same thing is itself evidence (`PkgEqual`, `HashEqual`, `VulnEqual`). That makes it the closest existing composition graph to tmodel's (our reading), but it has no product, party, completeness or review verdict, and the actor tree its documentation describes is not in its schema. Vulnerabilities come from an OSV certifier that works by "Package identification through PURL" and from ingested advisories and VEX; its deps.dev certifier adds dependency, source and Scorecard data, not vulnerabilities. Its SPDX parser reads only SPDX 2.x, and its default storage is "a non-persistent in-memory backend". It describes itself as "under active development" and an OpenSSF incubating project (README).

**deps.dev (queried, not run).** deps.dev (Open Source Insights, from Google) takes no input from users and answers queries. It holds package versions with their requirements and resolved dependency graphs (npm, Cargo, Maven and PyPI through the API; Go too in the BigQuery dataset), licences, OSV advisories, OpenSSF Scorecard and OSS-Fuzz results for projects, and SLSA and PyPI attestations (`docs-deps-dev-api-v3`, `docs-deps-dev-bigquery-v1`). It is keyed on ecosystem, name and version, on a purl without qualifiers (in its v3alpha API), on file hashes (MD5, SHA-1, SHA-256, SHA-512) and on project ids. It can answer "which package version has this hash" for six package registries: in our 15 live calls on 2026-10-08, the log4j-core jar's SHA-256 and the hash of a wheel from tradar's `uv.lock` both resolved to their package versions. Its graphs are generic resolutions of a package version, not a product's locked composition: 0 of the 4 resolved versions we compared matched tradar's `uv.lock` (`fanout-tools.md` §1.6).

**Takeaway:** No single tool covers the whole chain. Syft writes the SBOM, with mostly guessed CPEs, and puts different data in different formats; it writes SPDX 3 only on request and with SPDX 2.3's feature set. Grype and Trivy match it against different data, and they agree on Python and Java packages but not on Alpine or Debian. Dependency-Track reads only CycloneDX, GUAC reads SPDX only in version 2, and deps.dev holds generic graphs, not a product's. So an SPDX 3.0.1 import path (DEC-002) is supported by Syft, which writes and reads it, and by Grype, which reads it through Syft's decoders, but not by Trivy or GUAC, which wait on spdx/tools-golang's next release, nor by Dependency-Track. Outside radar's chain, sbom-tool and cdxgen also write it, and Yocto builds write it by default with SPDX 3's own Build and VEX elements, so an SPDX 3 importer will meet features that radar's tools never emit (our reading). Radar (tradar), which ADR-0001 makes tmodel's source of composition data, inherits the choices its Syft and Grype defaults make (§4). GUAC's per-document evidence keys are the nearest existing design for keeping each claim's source when documents about the same package are merged (DEC-001, DEC-004; our reading).

## 4. How tradar uses these today

Input to the radar-to-tmodel data contract. ADR-0001 accepted DEC-007 on 2026-09-30: tradar becomes "radar", the composition and finding tool whose output tmodel consumes, and "the interface is the composition→model-input mapping surveyed in RPT-0004 (#8)".

This section describes `tradar` (`threat-radar-tradar`) at commit `26d9c76` (2026-09-10, Pacific time), which was still the head of its `main` branch on 2026-10-22 (GitHub API). Phase 1 re-checked 19 of the section's claims against the code on 2026-10-08: all hold, three with the nuances added below (`fanout-tools.md` §1.7). Paths are relative to its `threat_radar/` package.

**Tools and formats.** tradar runs Syft and Grype as command-line programs: `syft scan <target> -o <format> --scope <scope>` (`core/syft_integration.py:109-123`), with CycloneDX JSON as the default format (`cli/sbom.py:95`), and `grype <target> -o json` (`core/grype_integration.py:172`). Its format option (CycloneDX JSON or XML, SPDX JSON or tag-value, Syft JSON, table or text) has no version suffix (`core/syft_integration.py:14-23`), so any SPDX it asks Syft for is 2.3, never SPDX 3. It reads SBOMs back only as JSON (`utils/sbom_utils.py`, `load_sbom`), and it never matches components to vulnerabilities itself: `cve scan-sbom` hands the SBOM file to Grype as `sbom:<file>` (`core/grype_integration.py:282`).

**What it keeps.** From SBOM components, tradar's helpers read name, version and type, plus Syft's own `syft:package:*` and location properties, which they use to filter and group components (`extract_component_metadata`, `utils/sbom_utils.py:353`); purl and licenses are used only for display (`sbom components --details`), a CSV export and license statistics (`utils/sbom_utils.py`). The details view also shows a component's `cpe`, `author` and `bom-ref`, and a parser that reads the purl and the first CPE (`parse_syft_json`, `core/syft_integration.py:214-238`) is called only from a test. An SBOM converter that also parses the purl (`core/sbom_package_converter.py`) is called, outside its tests, only from `analyze_container_with_sbom`, which nothing calls. Its code never reads an SBOM's `dependencies`, `compositions`, `serialNumber`, `hashes` or `supplier` (none of these keys appears outside its environment-config code). From Grype's JSON it keeps the vulnerability ID, severity, first fix version, description, URLs, data source, namespace, one CVSS base score (the highest in the first related record that has scores), the package's name, version, type and location, and Grype's `source` and `descriptor` blocks (`core/grype_integration.py:335-430`). Its convenience field for the database date (`grype_db`) is empty with current Grype versions, whose JSON moved that date to `descriptor.db.status.built`, although the raw `descriptor` block is kept. It does not read how Grype made each match (`matchDetails`), related CVE IDs, the fix state, the package's purl or CPEs, or any CWE.

**What reaches the graph.** The graph is a NetworkX directed graph saved as GraphML (`graph/graph_client.py:107, 329`). `graph build` creates it from Grype results, not from an SBOM: for each vulnerability it adds a vulnerability node and, if missing, a package node with only `name`, `version` and `ecosystem` (`graph/builders.py:166-186`). Only vulnerable packages, plus one node for each fix version (marked `is_fix`, `graph/builders.py:211-237`), therefore become package nodes, and purl, CPE, licenses, hashes, supplier and the SBOM's dependency links never reach the graph. A vulnerability node's id is `cve:` plus the vulnerability's id even when that id is a GitHub advisory (GHSA) id, as all 17 tradar matches are, and an existing node is never updated, so the first scan's data source wins (`graph/builders.py:239-262`). Package node ids are `package:<name>@<version>`, without the ecosystem, so packages from two ecosystems with the same name and version would share a node (our reading; not tested). `graph build` accepts raw Grype JSON or tradar's own scan files that carry a `target` key (`cli/graph.py:65-68`); the file saved by `cve scan-sbom` carries `sbom_file` instead (`cli/cve.py:321`) and is rejected as an "Unsupported scan result format" (`cli/graph.py:125`). Fed raw Grype JSON, it reads `fix.versions[0]` (`cli/graph.py:82-84`), which fails on an empty list, and 29 of the 30 Alpine matches of 2026-10-08 have one (from reading the code, not run; §10, finding 11). The project's own documentation also lists graph edges, such as `RUNS_ON` and `SCANNED_BY`, that `graph build` does not create (`CLAUDE.md:2542-2543`).

**CWE, NVD and the rest.** The current code has no CWE handling and calls no vulnerability API; a case-insensitive search for "cwe" across its code, tests and docs finds nothing. The git history shows an NVD client that extracted CWE IDs, added on 2025-10-05 (`629d92a`) and removed on 2025-10-09 (`3e26837`, "Remove manual SBOM package converter and replace with Grype integration"). Nothing in the code handles hardware, VEX or completeness. The nearest thing to build identity is a local Docker image ID, which could label a container node (`graph/builders.py:100`), but both CLI paths that build graphs call `build_from_scan` without a container (`cli/graph.py:152`, `cli/env.py:247`). tradar's saved scan files also keep Grype's `source` block (`cli/cve.py:151, 337, 480`), which for a direct image scan includes the image's `manifestDigest`; for `cve scan-sbom`, Grype rebuilds that block from the SBOM's root, so the field holds whatever version the root carried (`12-slim` for `debian:12-slim`). No code reads it.

**Takeaway:** tradar is a thin wrapper around Syft and Grype that never asks Syft for SPDX 3, and whose graph keeps only the name, version and ecosystem of vulnerable packages. Under ADR-0001, tmodel consumes radar's output instead of re-implementing scanning, so what radar's pipeline now drops, such as purl and CPE, dependency links and CWEs, is what the composition-to-model-input contract would have to add if tmodel needs it; Syft's and Grype's JSON outputs already contain all of it (see section 3).

## 5. The bridge: components to CVEs and CWEs

Input to DEC-001 and DEC-008. This section asks what a match between a component and a vulnerability needs, and what a scanner records about it. The structure of CVE, NVD, OSV and CWE records is RPT-0005's (dimension 1), and so are VEX encodings (dimension 3); the VEX status table at the front stays, because RPT-0005 cites it. Phase 1's notes are in `fanout-bridge.md`. Its counts for CVE records come from the CVE List as of 2026-10-08 (402,861 records; `cvelistv5`), and its NVD counts from NVD's API for the 15,074 CVEs published in September 2026, read on 2026-10-08.

**How each source names affected software.** A vulnerability record names what it affects in one of three ways: by CPE (NVD), by ecosystem and package name (OSV and GitHub advisories), or by a distribution's own package name (Alpine, Debian, Ubuntu, Red Hat). The CVE record itself now allows all of these. CVE Record Format 5.2.0 names a product by `vendor` and `product`, or by `collectionURL` and `packageName`; version 5.1.1 added CPE applicability statements, and 5.2.0 added a `packageURL` that "MUST NOT include a version", although the schema checks it only as a URI (`cve-json-5`). In practice most records give an SBOM nothing to match (our reading): 26.8% of the records published in 2026 carry CNA CPE applicability statements (35.7% counting the older `cpes` list) and 5.3% a purl, 144,340 published records name every product only as `n/a` (CVE-2025-60876, the BusyBox CVE in our runs, is one), and GitHub's CNA writes version ranges as text in the `version` field (11,212 of the 12,205 such records of 2026, by a heuristic count; `fanout-bridge.md` §1.1). What each source needs from an SBOM:

| source (record) | key it needs from an SBOM | how it writes affected versions | where its CWE comes from |
|---|---|---|---|
| CVE record, CNA container (`cve-json-5`) | vendor and product strings, or collection URL and package name; optionally a versionless purl (5.2.0), CPE names (`cpes`) or CPE applicability statements (5.1.1) | `versions[]` with `lessThan` or `lessThanOrEqual`, a free-text `versionType` and a `status`, plus a per-product `defaultStatus`; or CPE ranges; or text | the CNA's `problemTypes` |
| CVE record, ADP containers (`cisa-vulnrichment`) | CISA's ADP: CPEs (in 20,175 records); supplier ADPs: the supplier's own product names | the same `versions[]` model | CISA's ADP where the CNA gave none (38,251 records); Red Hat's supplier ADP (1,124) |
| NVD (`nvd-cve-api-2-0`; added by Threat-Radar/library#25, merged 2026-10-21, after this report's pin `a28a013`) | a CPE whose vendor and product are names in NVD's dictionary | start and end, each including or excluding, in AND/OR configurations | `weaknesses`, each with a source and a Primary or Secondary type |
| OSV (`osv-schema`, a summary at `a28a013`, with a full extraction in Threat-Radar/library#28; `osv-dev`) | ecosystem and name (for distributions, the source package); optionally a versionless purl | typed ranges (`SEMVER`, `ECOSYSTEM`, `GIT`) of `introduced`, `fixed`, `last_affected` and `limit` events | none in the schema; GitHub records carry `database_specific.cwe_ids` |
| GitHub advisories (`github-advisory-database`) | ecosystem and package name; no purl in GitHub's own files | `ECOSYSTEM` ranges only | GitHub's curators (`cwe_ids`) |
| Alpine (`alpine-secdb`) | origin (source) package, release branch and repository | the first fixed version per CVE; a `"0"` key, which tools read as not affected | none |
| Debian (`debian-security-tracker`) | source package and release | one `fixed_version` per release; `"0"` means not affected | none |
| Ubuntu (`ubuntu-security-notices`) | source package and release, with the binary packages listed beside it | `ECOSYSTEM` ranges that always start at 0 | none |
| Red Hat (`redhat-csaf-vex`) | the product stream's CPE, which depends on the repository the package came from, plus the RPM name | a status list per full package version | Red Hat's, one per CVE |

So an SBOM feeds a match only if it carries the key each source understands: a correct CPE for NVD; the ecosystem and the package name as the registry writes it (a purl's type, namespace and name) for OSV and GitHub; and for distributions the source package and the release, plus, for Red Hat, the repository (`redhat-2021-oval-rpm-matching`). Syft's apk purls carry the release and the source package as `distro=` and `upstream=` qualifiers, and Grype searches Alpine's feed by the source package (`fanout-bridge.md` §1.6, §1.11).

**NVD's part has shrunk.** Since 2026-04-15, NVD prioritizes for enrichment only CVEs in CISA's Known Exploited Vulnerabilities catalog, CVEs for software used in the federal government and CVEs for critical software as Executive Order 14028 defines it; the rest are not scheduled for immediate enrichment. CVEs it has not scheduled appear in its API as `Deferred`, its documented name for the web status "Not Scheduled". Of the CVEs published in September 2026, 29.2% had NVD configurations on 2026-10-08. Where both a CNA (in CPE applicability statements) and NVD wrote CPE data for one of those CVEs (1,545 of them), the two agreed exactly on vendor, product and range for only 375 (our measurement; `fanout-bridge.md` §1.2). Since 2026-06-17, NVD also passes on the record's `affected` data (the CNA's and the ADPs'), purls included, but its API does not accept a purl as a query: `purl=` returns "Invalid parameter: purl." (`fanout-identity.md` §9). On 2026-10-22, NVD's news page listed nothing newer than 2026-08-26.

**Which route the scanners take.**
- *Grype.* Grype 0.119.0 turns CPE matching off by default for the language ecosystems GitHub advisories cover (Python, JavaScript, Java, Go, Ruby, Rust, .NET, Hex) and for Debian and RPM packages, and keeps it on for its catch-all `stock` matcher and its `jvm` matcher (`grype config`). For the GitHub-advisory ecosystems, the change dates from 2023 (Grype pull request #1412).
- *Grype's apk matcher.* It has no switch. Alpine's feed "is the authority for an apk", and "NVD counts only where the feed is silent". The matcher searches by the source package, which is how "an openssl CVE for a libssl3 APK whose origin is openssl" surfaces. It drops NVD's fix versions, because "an inferred NVD fix is an upstream release number rather than an apk version" (`grype/matcher/apk/matcher.go`, the same in 0.119.0 and 0.120.1; `anchore-grype`).
- *Grype's `nvd:cpe` data.* What Grype labels `nvd:cpe` is not only NVD's data: Anchore's database build applies its own overrides, "CPE configurations for vulnerabilities not yet analyzed by NVD" and corrections (`anchore-nvd-data-overrides`; `overrides_enabled: true` in grype-db's configuration).
- *Trivy.* For operating-system packages, Trivy takes the other route: it "uses the advisory database from the appropriate OS vendor", because "OS vendors usually backport upstream fixes". Its NVD source holds no CPE data at all (Trivy documentation; trivy-db `vulnsrc/nvd/nvd.go`; `aquasecurity-trivy`).
- *Dependency-Track.* Its internal analyzer "Uses both CPE and PURL matching": NVD data needs a CPE, and GitHub and OSV data a purl (§3; `dependencytrack-dependency-track`).
- *OSV-Scanner.* It sends "package names, versions, ecosystems, and file hashes" to osv.dev (`google-osv-scanner`). osv.dev's API does "a fuzzy match" of the version against upstream versions (`osv-dev`).

**What that meant in our runs.** This explains the Alpine results in §3:
- *2026-09-28.* Grype matched two CVEs, four times, all through CPEs, because Alpine's feed listed neither. The version range for the zlib CVE (CVE-2026-85091) came from Anchore's override, committed on 2026-09-17, because NVD's record was still "Awaiting Analysis", with no configurations. This settles the open point of 0.1.2 (our reading; `fanout-bridge.md` §1.11).
- *The BusyBox CVE (CVE-2025-60876).* Its CNA container names no product, only `n/a` (a Siemens supplier ADP adds Siemens products). Grype matched it through NVD's configuration, which ends at 1.37.0 inclusive.
- *2026-10-08, zlib.* Alpine's feed now listed the zlib CVE as fixed in 1.3.2-r1, so Grype reported it from the feed, and Trivy reported it too.
- *2026-10-08, OpenSSL.* Grype's 13 OpenSSL CVEs came from NVD data, reached through the source package `openssl`. Alpine's feed lists ten other OpenSSL CVEs as fixed in the installed version, and none of these 13 (`alpine-secdb`, 2026-10-08).
- *Debian, Python and Java.* On Debian, Grype matched only through Debian's feed (229 matches, none by CPE). For Python and Java packages, both scanners used GitHub advisory data.

**What a scanner records about a match.** The scanners record different amounts, and none records everything (`fanout-bridge.md` §1.11 to §1.14).
- *Grype* records the most:
  - a ranked match type (`exact-direct-match`, `exact-indirect-match`, `cpe-match`) and the matcher;
  - what it searched by: the package, the distribution, and the exact CPE strings it built;
  - what it found: the record, and the version constraint with its scheme, such as `< 1.3.2-r1 (apk)`;
  - the advisory's namespace and URL;
  - in `descriptor`, the database's build time and each provider's capture time.

  Anchore's guidance is that "exact-direct-match and exact-indirect-match are high confidence, cpe-match requires verification". Grype's own `Confidence` field is "currently unused, reserved for future use" and is not exported. Nothing in its output says whether an `nvd:cpe` range came from NVD or from Anchore's overrides.
- *Trivy* records where the advisory came from and the source of the severity, but not how it matched, and it drops the source of each CWE.
- *Dependency-Track* keeps one attribution per analyzer, with a date and a reference URL, and records which source reported which version range. It marks a finding inactive "when no analyzer reports it anymore". Its 0 to 100 `matchingPercentage` is stored but not exposed in its Finding API.
- *OSV-Scanner* records the package and the input it came from, and leaves the method implicit. Version 2.7.0 (2026-10-12) adds purls to its JSON output "when available" (release notes).

The database is part of the result: the same SBOM gave 4 matches on 2026-09-28 and 30 on 2026-10-08, with the same Grype version ([pilot.md](pilot.md) §3). The accepted core can hold a match as an Assertion (subject, predicate, object, `confidence`, `assertion_status`). But it has no place for the method, the search key, the evidence, the data source or the database snapshot (§10: finding 5, Table 6d, and candidate rules R-MATCH-1 and R-PROV-2).

**How affected versions are written and compared.** Each source writes ranges its own way (`fanout-bridge.md` §1.15):
- *NVD, and CPE data in CVE records:* a start and an end, each including or excluding, on a CPE whose version is `*`. The CPE specifications themselves define no ranges and no version ordering (`nistir-7696`, `nistir-7698`), so the four range keys are NVD's addition (our reading).
- *OSV:* typed timelines (`SEMVER`, `ECOSYSTEM`, `GIT`) with a normative evaluation; `introduced: "0"` means from the first version.
- *CVE records:* a `version` with `lessThan` or `lessThanOrEqual` and a `versionType`, which is a free string ("custom" in 70,257 published records, "semver" in 57,008, "git" in 18,893).
- *CycloneDX:* `vers` strings with a status. vers defines the syntax and leaves comparison to registered version types, of which v1.2.1 has two, `npm` and `pypi`; it covers only linear versioning (`vers-spec`).

How two versions compare differs by ecosystem:
- Debian's epochs and tildes, so `3.5.7-1~deb13u3` sorts before `3.5.7-1` (`debian-policy-version`);
- RPM's uncompared separators, tilde and caret (`rpm-version-7`);
- Alpine's suffix order and `-r` revisions (`apk-package-5`);
- Python's rejection of SemVer's pre-release and build syntax (`pypa-version-specifiers`);
- Maven's case-insensitive comparison and its own qualifier order (`maven-version-order`);
- SemVer's ignored build metadata (`semver-2-0-0`).

Three more things break ranges:
- *Backports.* For CVE-2026-54873, NVD says OpenSSL from 3.5.0 up to, not including, 3.5.9 is affected, while Debian fixed it in trixie as `3.5.7-1~deb13u3` (`debian-security-tracker`). A range check against NVD would call Debian's fixed package vulnerable (our reading).
- *Disagreeing sources.* For CVE-2026-85165 (n8n), the CNA's range and NVD's disagree on whether 2.36.2 is affected.
- *Dropped epochs.* When an SBOM drops a package's epoch, the result depends on a matcher setting (Grype's `missing-epoch-strategy`).

**How often the methods disagree.** Published studies mostly measure disagreement as counts or overlaps, not against a ground truth, and most used older tool versions (`fanout-bridge.md` §1.16):
- On the same container images, Trivy's and Grype's findings overlapped with a Jaccard index of 0.694; when both read the same SBOM, the overlap fell to between 0.026 and 0.101, depending on which tool wrote it (Churakova et al., 2025 preprint; `churakova-2025-vexed-by-vex`).
- When only the SBOM generator changed, just 2% (Grype) to 12% (Trivy) of the CycloneDX 1.5 SBOMs (from a corpus of 1,303) gave the same number of findings (O'Donoghue et al., 2024; `odonoghue-2024-sbom-generation`).
- For 1,000 PyPI packages, Grype's findings from Syft's SBOMs had an average Jaccard similarity of 26.33% to a `pip-audit` ground truth, and 97.8% of the misclassified vulnerabilities were false positives (Benedetti et al., 2024 preprint; `benedetti-2024-sbom-python`).
- Nine composition-analysis tools reported from 17 to 332 vulnerable dependencies for the Maven projects of one application (Imtiaz et al., 2021; `imtiaz-2021-sca-comparison`).
- Against code-level ground truth, a CPE-based scanner (OWASP Dependency-Check) had a precision of 0.34 (Dann et al., 2022; `dann-2022-oss-scanners`).
- On 16 crafted SBOMs, only Dependency-Track passed the baseline test for CPE support, and Grype 0.87.0 and dep-scan ignored the version inside a purl (Rosso et al., 2026; `rosso-2026-svs-test`).
- About NVD itself: only 59.82% of vulnerability reports and CVE summaries strictly matched NVD's entries (Dong et al., 2019; `dong-2019-viem`), and about 10% of about 19,000 vendors had inconsistent names in a 2018 snapshot (Anwar et al., 2020; `anwar-2020-cleaning-nvd`).

We found no published study that gives a ground-truth rate for CPE matching against ecosystem matching with current Grype or Trivy versions. Anchore's labelled match data could support one, but it would need new runs. Two 2026 studies come closest without separating the two. In one, Trivy and Grype agreed almost perfectly when given the same accurate SBOM, yet manual inspection confirmed only 9 of the 113 vulnerabilities they reported across four repositories, mostly because the vulnerable code was unreachable (Zhou et al., CODASPY 2026, arXiv 2511.20313; Trivy 0.66.0 and Syft 1.33.0). The other measures several tools, Trivy v0.69.1 among them, against a ground truth derived from OSV rather than from manual validation (Mandl et al., arXiv 2604.21111, a preprint). Their honest stubs, `zhou-2025-sbom-reality-check` and `mandl-2026-ground-truth-vuln-detection`, are in Threat-Radar/library#33, which is open.

**Weaknesses (CWEs).** A CWE reaches a component only through a vulnerability in CycloneDX and in all the scanner data we saw; SPDX can also attach a `cwe` external reference to a package directly. Each CWE assignment has a source, and sources can disagree: for CVE-2022-37434, NVD gives CWE-787 and a second source CWE-120.
- *In CVE records.* CNAs assigned CWEs in 159,816 published records. CISA's ADP adds one where the CNA gave none (38,251 records); its stated rule is to fill gaps, and where both give one, "the originating CNA's data should take precedence" (1,320 records carry both). Red Hat's supplier ADP added CWEs to 1,124 records, and 186,234 published records have none (`cvelistv5`, `cisa-vulnrichment`).
- *In NVD.* Each source is labelled "Primary" or "Secondary", and "Primary sources include the NVD and CNA who have reached the provider level in CVMAP". When NVD cannot classify a weakness, it uses placeholders instead of CWE numbers: `NVD-CWE-noinfo` ("There is insufficient information about the issue to classify it") and `NVD-CWE-Other` (NVD's CWE Slice page). These are now rare: 19 of the 15,074 CVEs published in September 2026 carry one.
- *In the feeds.* Ecosystem and distribution feeds mostly carry no CWE. OSV has no field for one; GitHub's curators put theirs in `database_specific.cwe_ids`, which 1,565 reviewed advisories leave empty. Alpine's, Debian's and Ubuntu's data have none, and Red Hat states one per CVE.
- *In the tools.* Grype passes on NVD's CWEs with their source and type, keeping `NVD-CWE-Other` and dropping `NVD-CWE-noinfo`. Trivy takes the list from the first source in a fixed order, with NVD first, and drops the source. Dependency-Track stores CWEs as integers, so NVD's placeholders do not fit there, nor in CycloneDX's integer `cwes` field (1.1).
- *In our data.* In the re-run for Table 6 (2026-10-18), all 30 Alpine matches carried CWEs, each from a Secondary source: the OpenSSL project (26), CISA's ADP (3) and VulnCheck (1) (Table 6d, §10).

**Takeaway:** A match needs the key each source understands: a correct CPE for NVD, the ecosystem and package name for OSV and GitHub, and the source package and release for distribution feeds. NVD now prioritizes only some new CVEs for enrichment. CNAs now write CPEs and purls into CVE records themselves, and their CPE data and NVD's seldom agree exactly. Which key, which source and which day's data a scanner used decide the result. Only Grype records its method in detail, and even Grype does not say whether NVD or Anchore supplied a range. A version range keeps its meaning only with its scheme, because ecosystems order versions differently and distributions backport fixes. CWEs arrive second-hand, from sources that can disagree. For DEC-008 and the input contract, a match is a claim with a method, a source and a date, not a fact (our reading).

## 6. Build identity and the radar → tmodel input contract

Input to DEC-001 and DEC-009, and to the radar-to-tmodel data contract (ADR-0001). Phase 1's notes are in `fanout-identity.md` (dimension 6, with a second agent's re-check in its section 9), and §10 applies them to the accepted core (ADR-0010).

**The document versus the product.** An SBOM identifies two different things, and the formats keep them apart. The first is the SBOM document itself. CycloneDX says "Every BOM generated SHOULD have a unique serial number, even if the contents of the BOM have not changed over time", and its `version` "SHOULD be incremented by 1" whenever an existing BOM is modified (`cyclonedx-1-7`). An SPDX document has an `spdxId` like any other element, and Syft's SPDX output gets a new random namespace on every run (§10, rule R-PROV-1). The second is the product the SBOM describes, CISA's "Primary Component": CycloneDX's `metadata.component` or SPDX's `Sbom.rootElement`. A serial number therefore identifies an SBOM, not a build: two SBOMs of the same build carry different serial numbers.

**What pins the product.** A version string names a release; a content digest pins exact bytes. CISA's framing asks, at its Recommended Practice level, for "at least one hash of the Primary Component" (`cisa-framing-software-component-transparency`, §2.2.2.5). For container images the natural pin is a digest. In the OCI specifications, a digest is "a unique identifier created from a cryptographic hash of a Blob's content", a tag is "a custom, human-readable pointer to a manifest", and "A manifest digest may have zero, one, or many tags referencing it". Only when a manifest is requested by digest do the rules say "clients SHOULD verify the returned manifest matches this digest" (`oci-distribution-spec-1-1-1`). For source code the pin is a commit, which SLSA records as a build dependency: "a build that takes a git repository URI as a parameter might record the specific git commit that the URI resolved to as a dependency" (`slsa-1-2`).

**One image, five digests.** "A digest" is not enough, because an image has several (`fanout-identity.md` §1.20; `oci-image-spec-1-1-1`):
- *Index.* On 2026-10-08, the pilot image's tags `latest`, `3.24.2`, `3.24` and `3` all resolved to one image index (`sha256:294b683c…`), which lists eight platform manifests and eight attestation manifests.
- *Platform manifest.* The linux/arm64 manifest Syft scanned is `sha256:260479a1…`.
- *Configuration.* Its digest, which the OCI specification calls the image's ID, is `sha256:33bee74c…`.
- *Layer.* The image's one layer has a compressed digest (`sha256:a9986cd6…`) and an uncompressed one (`sha256:1b349a33…`).
- *A sixth, outside the image.* deps.dev keys images on an "OCI Chain ID" computed over the ordered layers (its v3alpha API; `docs-deps-dev-api-v3`).

Syft's SBOMs keep few of these, unlabelled, and which ones depends on the format and on how the image was named. Syft writes the platform manifest digest into CycloneDX's `metadata.component.version` when the image is named `latest`, keeps any other tag as written (`3.24.2`), and keeps a digest reference as given (the index digest, for `alpine@sha256:294b683c…`) (Syft 1.52.0 source and runs; `fanout-identity.md` §9). Named by a tag other than `latest`, the CycloneDX file holds no image digest at all. Syft's SPDX 2.3 output always puts the platform manifest digest in its root package's checksum and `pkg:oci` purl, and the tag or digest the user gave in `versionInfo` (Syft 1.52.0 runs, 2026-10-22). Syft's own JSON labels the manifest and configuration digests. But it carries the index digest only inside `repoDigests`, and it has no tags or time. Grype, reading Syft's CycloneDX file, copies the root's `version` into `manifestDigest` and the document-local `bom-ref` into `imageID`. The two container purl types also point at different levels. `docker` prefers "the image id", which is the configuration digest (our reading), while `oci`, Syft's SPDX output and the attestations use the manifest digest.

**Which identity anchors which model type.** In the schema whose core types ADR-0010 accepted, Product, ProductInstance and Component have one identity slot, `identifiers`, which its description calls an "Additive DRAFT slot". It holds opaque "Scheme-prefixed" strings, and "The scheme is NOT pinned". There is no version or kind slot, and `composed_of` belongs to Product and Component, not to ProductInstance (`spec/schema/tmodel-object-model.linkml.yaml` at `main`; §10, findings 1, 3 and 9). The example vectors write identifiers in ten styles (`pkg:`, `cpe:2.3:`, `sha256:`, `build:` and others), so nothing says which digest a bare `sha256:` names. The ARCH-0001 proposal, still a draft, asks for more: an "identity-by-hash `ProductInstance`", with state "carried by a (ProductInstance, time) pair, not by the hash alone" (§3b). The evidence offers these keys (`fanout-identity.md`, dimension 6):

| model type | candidate keys | assigned or computed |
|---|---|---|
| Product (a design or product line) | a versionless purl (for an image, its repository); an official CPE vendor and product; a CoSWID `persistent-id`; a vehicle type | assigned |
| ProductInstance (one build) | the platform manifest or index digest; an attestation's subject digest; a source commit with its build provenance; a firmware image's digest and size; an RXSWIN with its register | computed, except the RXSWIN |
| ProductInstance (one physical unit) | a serial number, a UEID or a device identity key (Table 4b) | assigned, or built into the device |
| Component | a versioned purl; package or file hashes; gitoids and SWHIDs for files and source trees; CPEs, as a matching attribute; a SWID tag id where the tag is authoritative | mixed |

**When a rescan is the same instance.** Phase 1 weighed six options (`fanout-identity.md`, dimension 6, Q1):
- *The platform manifest digest.* It is computed and checkable, it is what in-toto and SLSA verification match, and BuildKit uses it as an attestation's subject. But one release becomes one instance per platform (eight for alpine 3.24.2).
- *The index digest.* Tags resolve to it, so one multi-platform release is one instance. But Syft's CycloneDX and SPDX outputs carry it only when the image is named by that digest (named by tag, only Syft's JSON has it, inside `repoDigests`), and re-attesting an image may change it (our reading; not tested). A single-platform image may have no index.
- *The name and tag.* Tags move: four tags named one index on 2026-10-08, and by 2026-10-22 three of them (`latest`, `3.24`, `3`) named a newer one.
- *The source commit and build definition.* These stay the same across rebuilds. But they need provenance, which the proposal puts after the MVP (§7), and builds are often not reproducible: the alpine image's own provenance says `"reproducible": false`.
- *The SBOM.* A serial number identifies a document, and two tools describe the same bytes differently (Syft lists 16 packages, Docker's own SBOM 20 entries).
- *A domain key.* An RXSWIN names a vehicle's type-approved software, and a SUIT image digest names firmware.

The options combine. §10 proposes the platform manifest digest as the key, with the index and configuration digests, the platform, the repository and the tags (with the time seen) kept beside it. Another tool's rescan is then a new claim about the same instance, not a new instance (candidate rules R-ID-1 and R-MERGE-1). A firmware digest names a build that many units run, while a serial number names one unit, so the two need separate keys; one hardware vector, mvp-02, puts both on one ProductInstance (§10, finding 10 and rule R-HW-1).

**How SBOMs and provenance attach to an artifact.** Every attestation carrier binds by digest. They differ in which digest, in where the attestation is stored, and in how its type is named (`fanout-identity.md`, dimension 6, Q2):

| carrier (version read) | binds by | where it is stored | SBOM and provenance types |
|---|---|---|---|
| in-toto Statement (framework v1.2.0; `in-toto-attestation-v1`) | `subject[].digest`; subjects are "matched purely by digest", and two digest sets match "if ANY acceptable field matches" | not specified | `https://spdx.dev/Document` (`/v3` is new in v1.2.0), `https://cyclonedx.org/bom`; SLSA `https://slsa.dev/provenance/v1` |
| SLSA 1.2 provenance (`slsa-1-2`) | the verifier checks that the subject "matches the digest of the artifact in question" | "MUST publish attestations in at least one place"; lookup is "TBD" | provenance v1 |
| Sigstore bundle v0.3 (`sigstore-bundle-v0-3`) | one DSSE envelope with exactly one signature | a file or a registry | any in-toto predicate |
| OCI manifest `subject` and the referrers API (`oci-image-spec-1-1-1`, `oci-distribution-spec-1-1-1`) | the `subject` descriptor's digest | the registry, listed by `GET /v2/<name>/referrers/<digest>` | given by `artifactType` |
| BuildKit v0.34 (`buildkit-attestations`) | an attestation manifest in the image index, pointing at the platform manifest | inside the image index | SPDX JSON SBOM; SLSA provenance v1 by default |
| cosign v3.1 (an implementation of `sigstore-bundle-v0-3`) | the image digest | by default, an OCI 1.1 referrer holding a Sigstore bundle | SPDX, CycloneDX; SLSA v0.2 or v1 |
| GitHub `actions/attest` v4.2.2 (also under `sigstore-bundle-v0-3`) | "identified by the supplied digest" | GitHub's attestations API; a registry only with `push-to-registry` | SPDX or CycloneDX SBOM; SLSA provenance |

**Discovery binds differently.** RFC 9472 (Standards Track, October 2023; an honest stub, `rfc-9472`, is in Threat-Radar/library#33, which is open) extends the schema of a device's MUD file (Manufacturer Usage Description, RFC 8520) "to provide the locations of software bills of materials (SBOMs) and vulnerability information", and defines a well-known endpoint, `/.well-known/sbom`, from which a device can serve its own SBOM. The Transparency Exchange API, which Ecma TC54 is working on, looks bills up by a product identifier, its Transparency Exchange Identifier; on 2026-10-22 its only release was a beta (0.1.0-beta.1, 2025-05-22). Neither binds a bill to an artifact's digest. For hardware, RFC 9472 gives a unit a way to point to its own bill, which nothing in Table 4b or Table 6e does (our reading).

The pilot image shows the gaps (`fanout-identity.md` §1.20):
- *Not found where a consumer may look.* Its index holds an SBOM and a provenance attestation for each platform, in BuildKit's older form: plain in-toto Statements rather than signed envelopes, with no `subject` link in the attestation manifest. So the referrers API returned an empty list for both the index and the platform manifest, and a consumer that looks only there finds no SBOM.
- *Many names, a different count.* The SBOM attestation names the one manifest digest under nine different names. Its SPDX 2.3 SBOM, written by Docker Scout, lists 20 packages: the 16 Syft found, plus four source packages.
- *A narrow provenance.* The provenance (SLSA v0.2) covers assembling the image from a tarball, not building the packages in it.
- *No rule for which field.* in-toto leaves it to each predicate to say which field a digest matches, and its SBOM predicates say only that the subject "contains whatever software artifacts are to be associated with this SPDX document" (the SPDX 2 predicate; the SPDX 3 and CycloneDX predicates say the same).

BuildKit 0.34.1 (2026-10-20) has "no functional changes"; cosign 3.1.4 (2026-10-20) was checked only through its changelog (2026-10-22).

**Records of the build itself.** Some formats describe the build, not just its output.
- *SPDX.* SPDX 3.0.1's Build profile has a `Build` element that "describes a build instance of software/artifacts". Beyond the `spdxId` and `creationInfo` every element needs, only `buildType` is required. It can record a `buildId`, the digest of the build configuration (`configSourceDigest`), parameters, environment and start and end times, and it links to inputs and outputs through `hasInput` and `hasOutput` relationships (`spdx-3-0-1`).
- *CycloneDX.* Its `formulation` can describe how "any referencable object within the BOM" was "created, assembled, deployed, tested" (`cyclonedx-1-7`).
- *SLSA.* SLSA provenance is "an attestation that a particular build platform produced a set of software artifacts through execution of the buildDefinition" (`slsa-1-2`).
- *Reproducible builds* close the loop: a build is reproducible if "any party can recreate bit-by-bit identical copies of all specified artifacts" (`reproducible-builds-definition`).
- *SWID* has no build record. Its `tagVersion` only lets a newer tag replace an older one "without suggesting any change to the underlying software product" (NIST IR 8060 §3.1.1; `nistir-8060`).

In our runs, neither Syft nor Grype wrote a build record, and neither fetches attestations.

**What the contract would have to ask radar for.** ADR-0001 owns the contract: tmodel "does **not** re-implement scanning/composition; it consumes radar's results through a composition→model-input contract". The proposal puts build provenance after the MVP (§7). The evidence above says what the contract would have to ask for, because no current output carries all of it (`fanout-identity.md`, dimension 6, Q3; Table 6a, §10):
1. *The subject's identity at every level, labelled:* what the user named; each digest with its algorithm and media type (index, platform manifest, configuration); the platform; the repository; and the tags seen, with the time. Syft's JSON comes closest, but it has no tags, no time and no labelled index digest; CycloneDX keeps at most one digest and SPDX the platform manifest digest, neither labelled with its level.
2. *Who made each claim, and when:* the SBOM's format and version, its serial number or namespace, the generator and its version, the time, and the SBOM file's own digest (GUAC's `HasSBOM` keeps the last). For findings, the scanner's database build time and each provider's capture time.
3. *Each component's identifiers, raw and parsed:* the purl exactly as emitted, and its parts; each CPE, with whether it came from a dictionary or was generated; each hash, with its algorithm and what was hashed; the source package; and the distribution release, which OSV needs as part of its ecosystem key.
4. *The relationships:* depends on, contains, and which package owns which file.
5. *After the MVP, any attestation found for the subject digest:* its type, where it was found, and whether it was signed and verified; from provenance, the builder, build type, source, commit, times and the `reproducible` flag.
6. *A binding:* every carrier above puts an SBOM in an in-toto Statement whose subject is the artifact digest. If radar wrapped its output the same way, tmodel could match it by digest, as verifiers do (our reading).

Today radar keeps none of this beyond Grype's `source` block, which it saves but never reads, and its graph path cannot carry an SBOM scan at all (§4; §10, finding 11). Table 6 (§10) maps each field to the accepted core.

**Firmware and vehicles.**
- *Firmware is identified by its bytes.* SUIT names an image by "A fingerprint computed over the component itself" and its size. Its vendor and class identifiers "MUST NOT be used as assertions of identity", and updates are ordered by an anti-rollback sequence number, not a version (`draft-ietf-suit-manifest`). CoSWID gives a firmware release a `software-version` with a version scheme, and firmware SBOMs usually reuse the UEFI ESRT GUID as the tag id (§2).
- *Physical units.* For one physical unit, the attestation standards in Table 4b supply serial numbers, UEIDs and device identity keys.
- *Vehicles add an assigned name for a set of software.* UN Regulation No. 156 defines the RXSWIN as "a dedicated identifier, defined by the vehicle manufacturer, representing information about the type approval relevant software" of an electronic control system, and its duties apply "Where a vehicle type uses RXSWIN" (§2.2, §7.2.1.2). Each RXSWIN "shall be uniquely identifiable". It must be updated when a change to type-approval-relevant software "leads to a type approval extension or to a new type approval" (our reading: not with every software change). It is read over the standard (OBD) interface; if RXSWINs are not held on the vehicle, the manufacturer declares the software versions of the vehicle or its ECUs instead. "For every RXSWIN" there must be "an auditable register" of the relevant software versions and their "integrity validation data", which "may include checksums and hash values" (§2.11, §7.1.2.3, §7.2.1.2.1, §7.2.1.2.2; `unece-r156`). Our reading: an RXSWIN is a regulator-facing name for a set of software, coarser than a digest, and the register behind it is the computed part.
- *ISO 24089:2023* was not read (paywalled), and its public scope does not mention identification (`iso-24089-2023`). RPT-0007 covers both for ISO/SAE 21434.

**Takeaway:** Build identity involves three separate things that the formats keep apart: an id for the SBOM document, an identity for the product (a name and version, pinned by a digest when one is recorded) and, optionally, a record of the build. "A digest" is not one thing: one container image has at least five, and the SBOMs keep one or two of them, unlabelled, depending on the format and on how the image was named. Every attestation carrier binds by digest, but they differ in which digest and in where they are stored, so a consumer that checks one place can miss an SBOM that exists. The accepted core holds identity only as opaque strings whose scheme is not fixed. For DEC-001 and the contract, the evidence favours a labelled set of digests captured at scan time, one level of it chosen as the key (the candidate is the platform manifest digest), with build identity and unit identity kept apart (our reading).

**Assigned names and computed ones.** The schemes are of two kinds.
- *Assigned names* (purl, CPE, SWID tag ids, tags) say which package or product something is, and they can be wrong or guessed.
- *Computed ids* (hashes, OCI digests, gitoids, SWHIDs) are derived from the bytes, so anyone with the bytes can check them. But they name bytes, not a component: one package version has different bytes as an archive, as installed files and inside an image layer (`fanout-identity.md`, dimension 7).

Each assigned scheme also names something different. A CPE names a product class, never an instance (`nistir-7695` §5). A purl names a package in an ecosystem, and names a version only when it has one. A SWID tag id names one release as one tag describes it, while CoSWID's `persistent-id` names a set of related releases (`rfc-9393`). Only CPE has a central minting point, NVD's dictionary, whose official names change only through deprecation (`nistir-7697` §6.2). Anyone can write a purl, a SWID tag id or a computed id.

**Who keys on each.** Each database keys on a different scheme:
- *NVD:* CPEs. Since June 2026 it also carries purls, but it does not query by them.
- *OSV and GitHub advisories:* an ecosystem and package name. OSV also takes a versionless purl and git commits.
- *deps.dev:* name and version, file hashes for six registries, and purls without qualifiers.
- *GUAC:* purl parts, digests and source commits.
- *Dependency-Track:* in its version 4 documentation, coordinates, purl, CPE, SWID tag id and hashes.
- *Attestation verifiers:* only digests.

None of the six databases and tools keys on OmniBOR ids or SWHIDs. Only the formats and the policy documents mention them (CISA 2024 and 2026, and for SWHID also NTIA's 2021 framing).

**How each fails in practice.** Table 3b lists the documented cases. Three patterns recur:
- *Assigned names are guessed.* All 81 CPEs Syft produced for the Alpine image were generated, 13 of its 16 vendor and product pairs are not in NVD's dictionary, and none of the 16 full names is. The Alpine version suffix explains only one of those misses (`fanout-identity.md` §1.7, §9).
- *One thing gets several names.* Two tools gave the same Alpine packages different purl qualifiers. OSV.dev found 52 advisories for a Debian package under one purl spelling and none under another, and GUAC treats two spellings as two packages. Syft gives every Alpine release the SWID tag id `alpine`.
- *Computed ids leave open which bytes.* A CycloneDX issue asks "for **what** the hash has been calculated" (open since 2021). The OmniBOR id of one file changed between spec versions. One image has five digests (§6).

Phase 1 also found five failure modes the plan now requires, all in bold in Table 3b:
1. purl types that are not registered but that policy prescribes;
2. purl-shaped strings that are not purls;
3. copies of one record that disagree;
4. placeholder hashes;
5. inconsistent vendor names inside NVD.

**A stable key for a shared graph.** No single scheme serves every purpose, and the evidence points to keeping several, each with its context (`fanout-identity.md`, dimension 7, Q5):
- *A purl, normalized by its type definition,* is the closest thing to a shared name for a package version. Anyone can mint one, and OSV, deps.dev, GUAC and Dependency-Track use it. Kept with it: the raw string as emitted, the producer, the purl edition and type-definition version used, and the qualifiers, separately, because tools disagree on them. Distribution packages also need the release stated in a form each database reads.
- *Computed ids* are stable and checkable by anyone. Each needs its scheme and version (`swh:1`, the OmniBOR spec version), its algorithm, and what was hashed (a file, an archive, a manifest, a configuration, a layer).
- *A CPE* is a matching attribute, not a key: it names a class, is often guessed, and is renamed by deprecation. Kept with it: whether it came from the dictionary, NVD's `cpeNameId`, its deprecation flag and the lookup date.
- *A SWID tag id* works as a key only for authoritative tags, kept with the tag creator's `regid` and the tag version.

CISA 2026 asks for the same breadth: "If there are multiple software identifiers, the SBOM author should include all of them." Two existing designs already store identity this way. GUAC keeps packages, artifacts and sources as separate nodes, linked by evidence with a justification (`guac`; §3). The CycloneDX 2.0 draft moves identifiers into entries that name the party asserting them (§1.6). The accepted core's `identifiers` slot, by contrast, holds bare strings, with no source and no scheme version (§6). §10 proposes the normalized purl as the Component key, with the other identifiers kept beside it, and merging only through an equivalence Assertion that gives its reason (candidate rules R-ID-3 and R-MERGE-2).

**Takeaway:** Identifier schemes are either assigned names, which say what a thing is and can be guessed or misspelled, or computed ids, which pin bytes but do not say which package those bytes belong to. Each database keys on a different scheme: NVD on CPEs, OSV and GitHub on ecosystem names, verifiers on digests. purl is the closest to a shared key for packages, but its canonical form is only partly defined, tools disagree on its qualifiers, and its standard is changing (a second edition due in December 2026, and an ISO draft). Policy names purl and CPE most often. CISA's 2024 framing lists OmniBOR ids and SWHIDs as examples and CISA 2026 allows them, yet no database we checked keys on either. For DEC-001, the evidence supports storing every identifier with its scheme, its version, its source and what it covers, rather than choosing one (our reading).

**What changed from NTIA 2021 to CISA 2026.** CISA 2026's Appendix B lists the changes, and its element definitions (pp. 10 to 14) give the reasons quoted below (`cisa-2026-sbom-minimum`):
- *New elements.* Ten: SBOM Author Signature, SBOM Data Format Name and Version, SBOM Generation Context, SBOM Tool Name and Version, SBOM Version, Component Hash Value and Algorithm, and Component License.
- *Producer for supplier.* Supplier Name became Component Producer, because "Supplier Name has proven ambiguous in practice, particularly around distributors of software", and "Only one organization should be identified as the component producer for a given component".
- *All identifiers.* Other Unique Identifiers became Component Identifiers: at least one, and "If there are multiple software identifiers, the SBOM author should include all of them" (Table 3b lists which schemes each baseline names).
- *Coverage.* Depth became Coverage: "There is no minimum depth", transitive dependencies included.
- *Unknown versus withheld.* Known Unknowns became Explicitly Identifying Unknown Information, which separates information "unknown to the SBOM author" from information the author "is withholding".
- *Other changes.* SWID was dropped as a format (part of the Automation Support change, which CISA calls major), Access Control was folded into Distribution and Delivery, and the timestamp now points to RFC 9557.

Our reading: the shifts that matter most for the model are the hash entering the baseline (as the 2024 framing had already done), one producer replacing the supplier, and the move from an open world to full coverage. The 2024 framing's default for completeness is "Unknown", which "implies the open-world ontological assumption" (§2.2.2.6.4). CISA 2026 instead expects that "the recipient of an SBOM should be able to conclude that a newly reported vulnerability does not affect them if the SBOM does not list the component", a practice, not a data field.

**Hash, producer, depth and completeness.** The four requirements that decide whether a tool's SBOM is enough differ from baseline to baseline (`fanout-formats-baselines.md`, dimension 8):

| CISA 2024 framing | minimum when available, with the algorithm and the object hashed; a hash of the Primary Component recommended | Supplier Name (minimum) | direct dependencies (minimum), more levels recommended | "Relationships and relationship completeness declared for the Primary Component and direct Dependencies" (minimum) |
| CISA 2026 | value and algorithm, for "an executable component artifact" | Component Producer | all; "There is no minimum depth" | unknown versus withheld (a practice) |
| BSI TR-03183-2 2.1.0 | SHA-512 of the deployable component (required) | component creator, as an email or URL | through the scope of delivery, "at least up to and including the first component that is outside the scope of delivery" | "the completeness of this enumeration MUST be clearly indicated" |

**Our tools against them.** Only Syft's output was checked against the baselines; Trivy, which also writes SBOMs (Table 5), was not. Table 2 holds the details: Syft's output met the format, tool, timestamp, name, version, identifier and licence elements, but missed the SBOM author, a package hash, the producer, the generation context, a signature and any completeness claim. So it falls short of every baseline that has data fields, at least on the SBOM author. BSI and CERT-In ask the most of it (our reading). BSI wants a SHA-512 of each deployable component, the component's creator, its filename and three file properties (executable, archive, structured); Syft's CycloneDX output has none of these, and its SPDX package verification codes are SHA-1 values over files (§3). Syft can at least write the SPDX version BSI accepts, 3.0.1, though only with SPDX 2.3's feature set (§3).

**Takeaway:** The baselines move towards SPDX and CycloneDX, a hash, a named producer (CISA 2026 asks for exactly one organization), deeper coverage and saying what is unknown (our reading). They differ in force, from an optional contract term (OMB), through guidance with required field lists (BSI, which is "not binding or mandatory", and CERT-In), to law (the CRA, and the statutory duty for cyber devices behind FDA's guidance). They also differ in detail, from any hash algorithm to SHA-512 of the deployable component. CISA 2026 is final and replaces NTIA 2021 as the US baseline; the CRA's elements are still undefined. An SBOM straight from Syft meets none of the six baselines that list data fields in full: it lacks the SBOM author all six require. Our reading: for DEC-001, a component needs a producer, hashes with their algorithm and what they cover, and all its identifiers; for the input contract, radar would have to add an SBOM author, a hash of each delivered component and a completeness statement, or state that they are unknown.

| SPDX Lite profile | nothing new: a licensing-focused subset of Package fields | conformance rules only, none in the SHACL shapes |
| CERT-In QBOM, CBOM and AIBOM (`cert-in-2025-aibom-guidelines`) | quantum devices, cryptographic assets, AI models, datasets and compute hardware | element tables, with no format (its HBOM table is in §2) |

**Does tmodel's Component cover them?** ARCH-0001 §3 defines a Component as "A part of the system (service, container, dependency, source module)", and the proposal adds chips and cores (§0). Our reading, kind by kind:
- *Services* fit Component by name (`=`). Their endpoints, trust zones and data flows need TrustBoundary and DataFlow, which the accepted core lacks; pull request #130 adds both (DL-0024; ADR-0011, marked accepted on its branch but not merged).
- *Models* (the weights files) fit Component (`≈`), but their training lineage (`trainedOn`, `modelCard` datasets) needs an edge the core does not have.
- *Datasets* are often not deployed artifacts. They fit ARCH-0001's Asset ("Something worth protecting") better than Component, and #130's Asset class would hold them.
- *Cryptographic assets* split. A certificate or a key is closer to an Asset; an algorithm or a protocol is a capability a component "provides" (CycloneDX's own `provides` edge), not a part of it.
- *Builds and formulation* are activities, not parts (our reading; in PROV-O, which the proposal's §4 adopts as its provenance model, a build would be an Activity). The proposal leaves compile and SLSA build provenance to the radar → tmodel contract and puts it after the MVP (§4, §7).
- *OBOM content* maps to Deployment and Environment, which the accepted core has.

#130's `ComponentKind` (CycloneDX 1.7's 13 component types, plus `service` and `interconnect`) would let a Component say which of these it is.

**Two cautions about the AI-BOM sources.**
- *The Linux Foundation guide disagrees with the model.* Its guide to SPDX 3.0's AI profile lists `buildTime` (1..1), `downloadLocation` (1..*) and `suppliedBy` (1..*) as mandatory for an AIPackage (`lf-2024-spdx3-aibom`, the guide's Table 8). The 3.0.1 model names the property `builtTime` and requires it only for a DatasetPackage; it does require `downloadLocation` and `suppliedBy` for an AIPackage, but allows at most one of each (`spdx-3-0-1`). RPT-0014's summary of the guide repeats the error, and SPDX 3.1's release candidate relaxes the AI and Dataset rules further (§1.6).
- *The G7 guidance is unread.* The G7's *Software Bill of Materials for AI: Minimum Elements* (2026-05-12; `g7-sbom-for-ai-2026`) says its elements are "in addition to the general SBOM minimum elements" (§1). It groups its elements in seven clusters: metadata, system-level properties, models, datasets, infrastructure, security properties and key performance indicators. Its element tables were not read.

**Takeaway:** The other bills add five kinds of thing: services, models and datasets, cryptographic assets, builds or running environments, and (in CERT-In's bills) quantum and compute hardware. Only services, models and that hardware are components in tmodel's sense (our reading). Datasets and keys are closer to Assets, algorithms to capabilities a component provides, and builds to activities. For DEC-001, importing these bills needs a component kind and the Asset, TrustBoundary and DataFlow classes, which #130 adds, plus two edges the core lacks: training lineage and "provides" (our reading).

### Candidate rules

Evidence only. Each rule names its source in the fan-out notes, which hold the full arguments.

**Identity**

- **R-ID-1. ProductInstance key = the platform manifest digest.** Store it as `sha256:<hex>` in `identifiers`, and keep the index digest, configuration digest, platform, repository and tags (with the time they were seen) as further identifiers or attributes. A rescan with the same key is the same instance. *Evidence:* Syft JSON labels the manifest and configuration digests, and carries the index digest in `repoDigests` when the image is named by tag or by that digest; scanned by its platform digest (`mapping.md` §11), the index digest is in no output. CycloneDX and SPDX keep only one digest, unlabelled. Verifiers (in-toto, SLSA) match on the manifest digest (fanout-identity.md, dimension 6 Q1, options A to F). *Cost:* one release becomes one instance per platform (eight for alpine 3.24.2), a bare `sha256:` does not say which level it is (finding 9), and the index digest must be captured at scan time, because it cannot be recovered from the outputs.
- **R-ID-2. Product key = the versionless repository purl,** for example `pkg:oci/alpine?repository_url=index.docker.io/library/alpine`; never derive a Product from a tag, because tags move (fanout-identity.md §5).
- **R-ID-3. Component key = the purl, normalized by its type definition** (type, namespace, name, version and the qualifiers the type requires). Keep the raw string as emitted; put every other identifier in its own `identifiers` entry with its scheme prefix; mark which CPEs are generated. *Evidence:* Syft and Trivy agree on purls up to the `?` for 16 of 16 Alpine packages (fanout-tools.md §5). *Cost:* type definitions change: npm and golang changed `case_sensitive` between purl-spec v1.0.0 and v1.1.0 (DL-0015, Phase 2).
- **R-ID-4. Content identity** (a file or a layer) keyed on (algorithm, digest, what was hashed), linked to its Component by an occurrence Assertion, as GUAC's `IsOccurrence` does. Our scoping: post-MVP.
- **R-ID-5. Firmware and vehicle instances.** A firmware instance is keyed by the image digest plus its component id (SUIT); a vehicle software set by (manufacturer, vehicle type, RXSWIN), with the register's software versions as linked Components (fanout-identity.md §5).
- **R-MERGE-1. Each SBOM's inclusion list is a claim about one instance.** Carry it as Assertions (subject ProductInstance, `predicate: composed_of`, object Component) with the SBOM as their evidence, because the slot cannot hang off a ProductInstance (finding 1). Rescans and other tools add Assertions to the same instance; where two correct tools disagree (16 versus 20 package entries for the same digest, fanout-identity.md §1.20), a Review settles it.
- **R-MERGE-2. Merge two Components only through an equivalence Assertion** with its reason ("same normalized purl", "same SHA-256"); heuristic matches (CPE to purl, qualifier spellings) need a Review (GUAC `PkgEqual`, `HashEqual`).

**Provenance**

- **R-PROV-1. An SBOM is evidence, never a key.** CycloneDX writes a new `serialNumber` and Syft's SPDX output a new namespace UUID on every run, so neither identifies a build. Keep the format, version, serial or namespace, tool, creator, time, capture stage and the file's own digest.
- **R-PROV-2. A scan is an activity with its inputs recorded:** tool and version, database build time, each provider's capture time, matcher settings. Without them the same bytes give different answers on different days and nobody can say why.
- **R-BUILD-1. Attach build provenance to an instance only by subject digest match,** keeping the attestation's digest, predicate type and where it was found (fanout-identity.md §5).

**Structure**

- **R-EDGE-1. `depends_on` runs from the dependent to the dependency.** Reverse Syft JSON's `dependency-of` and SPDX 2.3's `DEPENDENCY_OF`; keep SPDX 3's finer type as a qualifier once the schema has edge qualifiers.
- **R-EDGE-2. Never derive `composed_of` from a dependency edge.** Inclusion in a build and a dependency between packages are different facts.
- **R-EDGE-3. Decide where an SBOM's `dependsOn` goes.** Either (a) `depends_on`, and make propagation follow it too, or (b) `uses_component`, as the five vectors that have a dependency do today. Under (a) as the schema stands, a finding on a library might not reach the services that use it (our reading: the schema names only `uses_component` and `composed_of` as propagation paths).
- **R-COMP-1. Completeness defaults to "unknown".** CycloneDX's `dependency` definition says components without dependencies "must be declared as empty elements", that components missing from the graph "may have unknown dependencies", and that implementations should "assume this to be opaque". Syft writes no empty entries, so its 4 packages without an entry are "unknown", not "dependency-free". None of Syft's four outputs states completeness otherwise.

**Vulnerabilities and weaknesses**

- **R-MATCH-1. One Assertion per match:** subject the Vulnerability, a predicate such as `affects` (name open), object the Component, `assertion_status: proposed`. Set `confidence` from the match type at first (exact direct, then exact indirect, then `cpe-match`, which Anchore says needs verification); the scale stays open. The vectors set `affects` on the Product by hand and record propagation as `propagates_to` Assertions from the Vulnerability to a Component that uses the vulnerable one; deriving Product-level `affects` from per-package matches is our proposal, built on proposal §5's propagation along `uses_component` and `composed_of`.
- **R-MATCH-2. Join a scan to its SBOM by purl,** not by the CycloneDX `bom-ref`: Grype rewrites every package ref (none of its 30 `affects` refs matches Syft's), although decoding its `package-id` qualifier recovers the original ([pilot.md](pilot.md) §3).
- **R-CWE-1. One Assertion per (CVE, CWE, source):** subject the Vulnerability, `predicate: instance_of`, object the Weakness. `instance_of` is the name PLAN-0002 §5 gives the Vulnerability-to-Weakness link ("via the BRON backbone"); ARCH-0001 §3 lists the edge without saying what it joins. Keep the source and NVD's `Primary`/`Secondary` type; never merge sources silently. Read CWEs from Grype's JSON, not its CycloneDX output (0 of 30 there). An NVD placeholder (`NVD-CWE-Other`, `NVD-CWE-noinfo`) becomes "no CWE given", not a Weakness.
- **R-RANGE-1. Keep a version range as written, with its scheme** (`vers` type, OSV range type, CVE `versionType`, Grype's `(apk)`); do not recompute it, because version ordering differs by ecosystem (fanout-bridge.md §1.15).

**Hardware**

- **R-HW-1. Separate build identity from unit identity.** A firmware digest names a build that many units run; a serial number, UEID or device key names one unit. mvp-02 puts both on one ProductInstance (finding 10).
- **R-HW-2. A measurement is an Assertion by the device.** Import each signed measurement (SPDM, DICE, EAT) as an Assertion whose provenance is the signing key and time; platform certificates and CoRIM are the manufacturer's Assertions. An automated appraisal stays `proposed` until a human Review accepts it.

**Takeaway:** An importer of radar output can fill Product, ProductInstance and Component, with their identifiers, today. It can also carry per-package matches, CVE-to-CWE links and per-build composition as Assertions. Much is lost on the way: the match method and its provenance, the CWE's source, fix information, version ranges, scores, alias ids, completeness, the SBOM document and the build record have no slots, and the version survives only inside a purl. Five choices come first: the instance key (R-ID-1), where an SBOM's `dependsOn` goes (R-EDGE-3), the predicate name for a match (for CVE to CWE the vectors have used `instance_of` since #128), the `confidence` scale, and an identifier prefix list. If #130 merges, it closes several of the gaps: version, kind, per-build composition, the CVE-to-CWE edge, provenance, aliases and component suppliers (our reading).

## 11. Synthesis and gap analysis

Input to every decision this report bears on. This section gathers the evidence of §1 to §10 by decision, summarizes Table 7, and routes each gap the report found to an open decision or issue: the main ones in Table 8, and the smaller mapping gaps row by row in Table 6's last column. It accepts nothing: only an ADR accepts a `DEC-*` (ARCH-0001 §9). On `main` (ARCH-0001 0.1.8), DEC-001a (ADR-0010), DEC-002 (ADR-0007), DEC-004 (ADR-0008) and DEC-007 (ADR-0001) are among the accepted decisions, and DEC-001b, DEC-008 and DEC-009 are the open ones. Pull request #130 adds ADR-0011, which amends ADR-0010 (DEC-001a) and is marked accepted on its branch; the pull request is not merged, so this section treats its changes as proposed.

**DEC-001, the object model** (DEC-001a accepted by ADR-0010; DEC-001b, the governed layer, open). A change to the accepted core takes a new ADR, worked out in #15 and #17.
- *Identity.* A component carries several identifiers at once, assigned (purl, CPE, SWID tag ids) or computed (hashes, OCI digests, gitoids, SWHIDs), and each database keys on a different one (§7, Table 3). The core stores them as opaque, scheme-prefixed strings, with no pinned list of schemes and no scheme version or source (§6, §7). Table 6's candidate rules key a Component on its normalized purl and keep the rest beside it (R-ID-3, R-ID-4).
- *Instances.* One container image has at least five digests, and Syft's SBOMs keep at most two of them, unlabelled (a CycloneDX file of an image named by a tag other than `latest` keeps none); the candidate instance key is the platform manifest digest, with the others labelled (§6; R-ID-1). A firmware digest names a build that many units run, and a serial number names one unit (R-HW-1).
- *Composition.* Composition for one build has no slot (finding 1). The dependency edge an SBOM gives has two possible homes, `depends_on` and `uses_component` (R-EDGE-3). "None", "unknown" and "withheld" are different claims (§1, §8; R-COMP-1).
- *Matches and weaknesses.* A match is a claim with a method, a source and a date, and a CWE has its own source (§5). The core can hold both as Assertions, as the MVP vectors have done for CVE to CWE since #128, but not their provenance (finding 5).
- *Hardware.* An HBOM is mostly supply-chain data; no SBOM format, current or draft, has a bus relation or a compute core; and attestation standards record what a device reports about itself (§2).
- *Other bills.* Services and models fit Component; datasets and keys are closer to Assets, and builds are activities (§9; our reading).
- *#130.* If it merges, ADR-0011 adds a version, a component kind, per-build composition, the CVE-to-CWE edge, Assertion provenance, alias ids, component suppliers and makers, and the Asset, TrustBoundary and DataFlow classes (§10).

**DEC-002, encoding and interchange** (accepted by ADR-0007). ADR-0007 commits the OTM and STIX 2.1 imports. SBOM and scanner formats are not on its list, and additions "arrive as MAP-NNNN + a vector" (finding 8). The evidence for such a crosswalk:
- *What tools write and read.* CycloneDX 1.7 is what our tools write and what Dependency-Track reads. SPDX 3.0.1 is the more graph-like model. Syft writes it, with SPDX 2.3's feature set; Grype reads it through Syft; Trivy, GUAC and Dependency-Track cannot read it. Outside radar's chain, Microsoft's sbom-tool (since 4.0.2) and cdxgen (since 12.3.0, by conversion from CycloneDX) also write it, and Yocto (5.2 and later) writes it by default with SPDX 3's own Build, SBOM-type and VEX elements, so an SPDX 3 importer will meet those features in embedded products even though radar does not emit them (§3; our reading).
- *Both formats are changing.* SPDX 3.0 is at ISO stage 50.20 and CycloneDX at 40.00. Both have unreleased next versions, CycloneDX 2.0 and SPDX 3.1 (§1.6).
- *What a file carries depends on its format.* The same scan carries different data in different formats (§3), and each format's schema enforces only part of its own rules (§1.5).

**DEC-004, the working store** (accepted by ADR-0008). An SPDX 3.0.1 document loads into an RDF store as it is, with four caveats (§1.4). GUAC shows a composition graph that merges documents' keys while keeping each document's claims apart (§3). Both bear on the edge façade (#52, #65), not on the choice of store (our reading).

**DEC-007, the radar and tmodel split** (accepted by ADR-0001), **and its input contract.** radar's graph keeps only the name, version and ecosystem of vulnerable packages, and it cannot carry an SBOM scan (§4; finding 11). For tmodel to fill Table 6, the contract would have to ask for labelled digests, each component's identifiers raw and parsed, the relationships, who made each claim and when (the SBOM's author included), a hash of each delivered component, and a completeness statement (§6, §8).

**DEC-008, CWE and NVD integration** (open). The evidence (§5):
- NVD now prioritizes only some CVEs for enrichment, and where a CNA and NVD both give CPE data, they seldom agree exactly.
- Scanners match on the day's data: the same image, scanned with the same Syft and Grype versions, gave 4 matches, then 30 ten days later.
- CWEs come from several sources that can disagree, and NVD's placeholders fit no integer field.

Our reading: whichever way DEC-008 goes, live lookup or cached mirror, the evidence favours recording each source's claim with its date and the database snapshot behind it (R-CWE-1, R-PROV-2).

**DEC-009, generic threat to product, and the mitigation lifecycle** (open).
- *Per-package matches.* Scanners match packages, while the core's `affects` points only at a Product (finding 2). The candidate rule records each match as an Assertion and derives the Product's `affects` by propagation (R-MATCH-1).

**Evidence rules.** Every agent worked to the same rules (DL-0015; `dimensions.md`, "Per-source record"):

- quotes with locators, and interpretations marked "our reading";
- no third-party files in the repository: downloads are named by URL and SHA-256 in `searches.md`, which also logs every query and tool run;
- scan results carry their date and database, because vulnerability data changes daily (#38).

**The adversarial review (#152).** One fresh Claude Code agent, which had no part in the drafting, reviewed §1 to §11 on 2026-10-22, under the brief and rules DL-0015 records. It ran the four checks of `dimensions.md` §12:
- *Coverage.* It wrote its own list of what such a survey should cover before reading the report's sources, then compared the two.
