# RPT-0004 Table 6: composition to model-input mapping

This file is Table 6 of [dimensions.md](dimensions.md), the deliverable #38 names for #15 (core objects) and #17 (schema). For every input the object model takes, it says which field of an SBOM (software bill of materials) or a vulnerability scan fills it, what the import loses, and which decision or issue settles the open points. It is also the evidence ADR-0001 points to for the radar → tmodel input contract ("the composition→model-input mapping surveyed in RPT-0004"). For the app, it is the input to an importer of radar output under `engine/load/`, the folder PLAN-0002 §1 reserves for "library loader + importers". No issue owns that importer yet; #60 (library loader) and #61 (CWE import) are the nearest lanes (our reading). Phase 5 moves this table into `report.md` as §10.

It accepts nothing. Every rule is a candidate for #15 and #17, and every "our reading" is ours, not an official crosswalk.

This run named the image by its platform manifest digest, where the pilot named it `alpine:latest`; that changes which digests the outputs carry (Table 6a).
4. **Adds the hardware rows** from agent 4 (fanout-hardware.md §5.1), the identity rules from agent 2 (fanout-identity.md §5), the bridge rows from agent 3 (fanout-bridge.md §5), the radar rows from agent 5 (fanout-tools.md §5) and the format rows from agent 1 (fanout-formats-baselines.md §5), each re-pointed at the accepted core.

## 2. How to read the tables

- **Columns** are the ones dimensions.md fixes: model input; CycloneDX 1.7; SPDX 3.0.1; Syft and Grype output; tradar keeps; rule; lost; routes to.
- **Marks** are dimensions.md's fidelity marks: `=` same concept, no loss; `≈` close, import loses something; `⊂` / `⊃` the source's element is narrower / broader than ours; `ext` absent but the source's extension mechanism could carry it; `txt` prose only; `none` absent.
- **Model input** in **bold** is an accepted class or slot (ADR-0010). "Target: none" marks a gap row: a composition fact the accepted core has no place for.
- **Syft and Grype output** is what the 2026-10-18 re-run contains (Syft 1.52.0, Grype 0.119.0, database built 2026-10-17; §11). Grype figures come from Grype reading Syft's CycloneDX file unless a cell says otherwise; §11 lists what changes when Grype reads the SPDX 3 file instead. **tradar keeps** is what tradar at `26d9c76` passes on to its graph or saved files (fanout-tools.md §1.7, re-read for this table); tradar has not changed since 2026-09-11.
- **Rule** cells cite the candidate rules in §10 by id. SPDX 3.0.1 names are the compact JSON-LD terms its serialization uses (`software_`, `security_`, `build_` prefixes).
- **Routes to** names who decides. DEC-001a is accepted, so a change to a core class needs a new ADR that supersedes or refines ADR-0010, worked out in #15 (core objects) and #17 (schema). DEC-002 is accepted too (ADR-0007), and new imports arrive under it as a `MAP-NNNN` crosswalk plus a vector. DEC-008 (CWE and NVD integration: live lookup or cached mirror) and DEC-009 (generic threat to product mapping, and the mitigation lifecycle) are open. A requirement such as R-018 bounds a choice but decides nothing, so it appears as "bound by".

### New findings

7. **No MVP vector links a CVE to its CWE.** mvp-01 has `vulnerability:cve-2026-30111` and `weakness:cwe-611` but no edge between them. Across the four `mvp-*` files, the Assertions use the predicates `propagates_to`, `exploited_by` (CWE to CAPEC), `realizes_threat`, `rolls_up_to`, `vex_not_affected` and `manufactured_by`. The vectors' own text says otherwise: `spec/vectors/README.md` lists mvp-01 as having "CVE→CWE→CAPEC with propagation as a reviewed Assertion", and mvp-01's header promises "a CVE→CWE finding propagating along composition". ADR-0002's backbone is CVE → CWE → CAPEC → ATT&CK: the vectors carry the CWE → CAPEC step and leave out the CVE → CWE step. Because `predicate` is "Not a closed enum", an Assertion can carry the link today without a schema change (rule R-CWE-1).
8. **SBOM and scanner formats are not on the accepted import list.** ADR-0007 commits OTM and STIX 2.1 as imports and says "interchange additions arrive as MAP-NNNN + a vector, never as silent schema drift". ARCH-0001 R-002 asks to "Ingest components and weaknesses from container/dependency analysis (reuse tradar output; DEC-007)". ADR-0001 calls radar's input a data contract, so whether it takes ADR-0007's `MAP-NNNN` form is for #15 and #17 to say (our reading). If it does, this table is the evidence for that crosswalk, and the pilot's scan is a candidate for its vector.
9. **The vectors write identifiers ten ways.** The `mvp-*` files use the prefixes `pkg:` (purl), `cpe:2.3:`, `sha256:`, `build:`, `swid:`, `oem-part:`, `hw-serial:`, `hw-core:`, `manifest:` and `subsystem:`. The schema calls the values "Scheme-prefixed and OPAQUE" and says "The scheme is NOT pinned", so nothing says which digest a bare `sha256:` names (an image index, a platform manifest, a firmware image) or which prefixes a loader must accept. Phase 2 also found four `oci` purls in the vectors whose namespace the `oci` type definition prohibits (DL-0015).
10. **One hardware vector merges build identity and unit identity.** mvp-02's ProductInstance `tcu-unit-7f21` carries a firmware digest and a hardware serial number, and the same digest also identifies the Component `tcu-firmware`. A firmware digest names a build that many units run; a serial names one unit (rule R-HW-1).
11. **tradar cannot carry this scan into its graph** (from reading tradar's code at `26d9c76`; not run). `cve scan-sbom` saves a file with `sbom_file` and no `target`, which `graph build` rejects as an unsupported format (`cli/graph.py:65-68`, `125`). Fed raw Grype JSON instead, `graph build` reads `fix.versions[0]` (`cli/graph.py:82-84`), which fails on an empty list; 29 of the 30 matches here have an empty `fix.versions` (Table 6d), so the command would stop with "Error building graph". For the contract (ADR-0001), this means radar's current graph path is no model for tmodel's importer, which should read Grype's JSON itself.

## 10. Candidate rules

Evidence only. Each rule names its source in the fan-out notes, which hold the full arguments.

**Identity**

- **R-ID-1. ProductInstance key = the platform manifest digest.** Store it as `sha256:<hex>` in `identifiers`, and keep the index digest, configuration digest, platform, repository and tags (with the time they were seen) as further identifiers or attributes. A rescan with the same key is the same instance. *Evidence:* Syft JSON labels the manifest and configuration digests, and carries the index digest in `repoDigests` only when the image is named by tag (the pilot) *[correction 2026-10-22: also when it is named by that digest]*; scanned by its platform digest (§11), the index digest is in no output. CycloneDX and SPDX keep only one digest, unlabelled. Verifiers (in-toto, SLSA) match on the manifest digest (fanout-identity.md, dimension 6 Q1, options A to F). *Cost:* one release becomes one instance per platform (eight for alpine 3.24.2), a bare `sha256:` does not say which level it is (finding 9), and the index digest must be captured at scan time, because it cannot be recovered from the outputs.
- **R-ID-2. Product key = the versionless repository purl,** for example `pkg:oci/alpine?repository_url=index.docker.io/library/alpine`; never derive a Product from a tag, because tags move (fanout-identity.md §5).
- **R-ID-3. Component key = the purl, normalized by its type definition** (type, namespace, name, version and the qualifiers the type requires). Keep the raw string as emitted; put every other identifier in its own `identifiers` entry with its scheme prefix; mark which CPEs are generated. *Evidence:* Syft and Trivy agree on purls up to the `?` for 16 of 16 Alpine packages (fanout-tools.md §5). *Cost:* type definitions change: npm and golang changed `case_sensitive` between purl-spec v1.0.0 and v1.1.0 (DL-0015, Phase 2).
- **R-ID-4. Content identity** (a file or a layer) keyed on (algorithm, digest, what was hashed), linked to its Component by an occurrence Assertion, as GUAC's `IsOccurrence` does. Our scoping: post-MVP.
- **R-ID-5. Firmware and vehicle instances.** A firmware instance is keyed by the image digest plus its component id (SUIT); a vehicle software set by (manufacturer, vehicle type, RXSWIN), with the register's software versions as linked Components (fanout-identity.md §5).
- **R-MERGE-1. Each SBOM's inclusion list is a claim about one instance.** Carry it as Assertions (subject ProductInstance, `predicate: composed_of`, object Component) with the SBOM as their evidence, because the slot cannot hang off a ProductInstance (finding 1). Rescans and other tools add Assertions to the same instance; where two correct tools disagree (16 versus 20 package entries for the same digest, fanout-identity.md §1.20), a Review settles it.
- **R-MERGE-2. Merge two Components only through an equivalence Assertion** with its reason ("same normalized purl", "same SHA-256"); heuristic matches (CPE to purl, qualifier spellings) need a Review (GUAC `PkgEqual`, `HashEqual`).

**Provenance**

- **R-PROV-1. An SBOM is evidence, never a key.** CycloneDX writes a new `serialNumber` and Syft's SPDX output a new namespace UUID on every run, so neither identifies a build. Keep the format, version, serial or namespace, tool, creator, time, capture stage and the file's own digest.
- **R-PROV-2. A scan is an activity with its inputs recorded:** tool and version, database build time, each provider's capture time, matcher settings. Without them the same bytes give different answers on different days and nobody can say why.
- **R-BUILD-1. Attach build provenance to an instance only by subject digest match,** keeping the attestation's digest, predicate type and where it was found (fanout-identity.md §5).

**Structure**

- **R-EDGE-1. `depends_on` runs from the dependent to the dependency.** Reverse Syft JSON's `dependency-of` and SPDX 2.3's `DEPENDENCY_OF`; keep SPDX 3's finer type as a qualifier once the schema has edge qualifiers.
- **R-EDGE-2. Never derive `composed_of` from a dependency edge.** Inclusion in a build and a dependency between packages are different facts.
- **R-EDGE-3. Decide where an SBOM's `dependsOn` goes.** Either (a) `depends_on`, and make propagation follow it too, or (b) `uses_component`, as the five vectors that have a dependency do today. Under (a) as the schema stands, a finding on a library might not reach the services that use it (our reading: the schema names only `uses_component` and `composed_of` as propagation paths).
- **R-COMP-1. Completeness defaults to "unknown".** CycloneDX's `dependency` definition says components without dependencies "must be declared as empty elements", that components missing from the graph "may have unknown dependencies", and that implementations should "assume this to be opaque". Syft writes no empty entries, so its 4 packages without an entry are "unknown", not "dependency-free". None of Syft's four outputs states completeness otherwise.

**Vulnerabilities and weaknesses**

- **R-MATCH-1. One Assertion per match:** subject the Vulnerability, a predicate such as `affects` (name open), object the Component, `assertion_status: proposed`. Set `confidence` from the match type at first (exact direct, then exact indirect, then `cpe-match`, which Anchore says needs verification); the scale stays open. The vectors set `affects` on the Product by hand and record propagation as `propagates_to` Assertions from the Vulnerability to a Component that uses the vulnerable one; deriving Product-level `affects` from per-package matches is our proposal, built on proposal §5's propagation along `uses_component` and `composed_of`.
- **R-MATCH-2. Join a scan to its SBOM by purl,** not by the CycloneDX `bom-ref`: Grype rewrites every package ref (none of its 30 `affects` refs matches Syft's), although decoding its `package-id` qualifier recovers the original ([pilot.md](pilot.md) §3).
- **R-CWE-1. One Assertion per (CVE, CWE, source):** subject the Vulnerability, `predicate: instance_of`, object the Weakness. `instance_of` is the name PLAN-0002 §5 gives the Vulnerability-to-Weakness link ("via the BRON backbone"); ARCH-0001 §3 lists the edge without saying what it joins. Keep the source and NVD's `Primary`/`Secondary` type; never merge sources silently. Read CWEs from Grype's JSON, not its CycloneDX output (0 of 30 there). An NVD placeholder (`NVD-CWE-Other`, `NVD-CWE-noinfo`) becomes "no CWE given", not a Weakness.
- **R-RANGE-1. Keep a version range as written, with its scheme** (`vers` type, OSV range type, CVE `versionType`, Grype's `(apk)`); do not recompute it, because version ordering differs by ecosystem (fanout-bridge.md §1.15).

**Hardware**

- **R-HW-1. Separate build identity from unit identity.** A firmware digest names a build that many units run; a serial number, UEID or device key names one unit. mvp-02 puts both on one ProductInstance (finding 10).
- **R-HW-2. A measurement is an Assertion by the device.** Import each signed measurement (SPDM, DICE, EAT) as an Assertion whose provenance is the signing key and time; platform certificates and CoRIM are the manufacturer's Assertions. An automated appraisal stays `proposed` until a human Review accepts it.
